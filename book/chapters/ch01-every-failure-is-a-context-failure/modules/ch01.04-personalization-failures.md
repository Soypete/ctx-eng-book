# Personalization Failures as Missing Context

Personalization in AI systems means tailoring responses to a specific user—their preferences, history, permissions, and constraints. When this context is missing, wrong, stale, or over-scoped, the system fails in ways that feel personal but are actually context failures.

## What Is Personalization in AI Systems?

Personalization is the process of binding **authenticated identity + relevant preferences + permissions + task constraints** to context at query time. Persistent preferences may live in a state store; they do not become reliable merely because a framework calls that store “memory.”

The key distinction:
- **Model parameters**: Learned behavior encoded during training; ordinarily unchanged between requests
- **Persistent state**: User or workflow records retained outside the model across requests
- **Context assembly**: Retrieving user-specific data at query time and injecting it into context

Personalization context includes:
- **Who is the user?** (identity, authentication)
- **What do they want?** (intent, current task)
- **What can they access?** (permissions, authorization scope)
- **What do they prefer?** (history, settings, constraints)

Without any of these, personalization fails.

## Missing User Preferences

A user asks the AI for recommendations and gets generic responses instead of personalized ones. The model doesn't know what the user prefers because that context was never assembled.

The gap is that no relevant preference context was provided. Preferences may be declared by the user, derived from observed behavior, or set by policy. Those sources have different authority and should not be collapsed into one profile. **[RESEARCH NEEDED: add a primary source on preference elicitation or personalization failure; `wordnet-anchor-text-notes` does not by itself support this production claim.]**

### The Failure Mechanism

```
User: "What's the best approach for this refactor?"

Without personalization context:
  → Model gives generic best practices
  → Doesn't know user's skill level, language preference, project context

With personalization context:
  → Model knows: user = senior engineer, language = Go, project = backend
  → Model gives Go-specific, senior-level refactoring advice
```

### The Fix

User preference context must be assembled at query time:
- Retrieve preferences from user profile store
- Inject relevant preferences into context
- Scope to current task (don't dump all preferences)

## Wrong User Context (Data Leakage)

A user sees another user's data. This is the most serious personalization failure—a privacy breach that feels like a model bug but is actually a context scoping failure.

RAG systems introduce new attack surfaces where malicious documents can be retrieved and injected into the model's context, leading to data leakage [Shift, 2024]. When personalization context isn't bound to the correct user identity, the model can inadvertently surface another user's information.

### The Security Boundary

The relevant security principle is tenant isolation: a personalization query must be unable to retrieve another subject's state, regardless of what the model requests. The repository notes do not verify the former OWASP taxonomy, incident, CVE, or count claims, so those examples are omitted. When context is not scoped to an authenticated principal, the blast radius of a compromised workflow includes other users' data.

### The Fix: User Identity Bound to Context at Retrieval Time

User identity must be bound to context scope at retrieval time, not assumed from the session:

```python
# Wrong: caller supplies an unchecked identity
context = retrieve_user_context(request.user_id)

# Better: derive identity from verified credentials and enforce scope in storage
principal = authenticate(request.session_token)
context = retrieve_user_context(
    principal=principal,
    capability=issue_task_capability(principal, request.task),
)
# The storage policy verifies that the capability subject matches the record owner.
```

Every retrieval query includes:
- User identity (who is requesting)
- Session token (is this session valid)
- Capability (what is this user allowed to access)

The data layer enforces the binding, not the model.

## Stale Personalization

A user updates their preferences, but the AI still behaves as if nothing changed. Last month's preferences are still being used.

False recollection, summary corruption, stale semantic state, bad procedural generalization, memory poisoning, and unauthorized recall are useful failure categories synthesized in the repository's memory research. They are not all findings attributable to Park et al. Personalization state needs freshness and provenance metadata just like any other retrieved state.

### The Failure Mechanism

```
User preferences stored in a profile index:
  - " prefers dark mode" (set 2024-01)
  - " prefers TypeScript over JavaScript" (set 2024-06)

User updates preferences on 2025-01-15:
  - "prefers Python over all other languages"

Query on 2025-01-16:
  - Retrieval pulls cached embeddings from 2024
  - Returns old preferences
  - Model answers with stale context
```

### The Fix: Freshness Metadata

Timestamp every user preference:
- Set staleness thresholds per preference type
  - "Code style preferences": can be 30 days old
  - "Project context": must be less than 1 hour old
- Trigger refresh when thresholds exceeded

```python
PREFERENCE_STALENESS_THRESHOLDS = {
    "code_style": timedelta(days=30),
    "project_context": timedelta(hours=1),
    "communication_style": timedelta(days=7),
}

def get_fresh_preferences(user_id, current_task, now):
    prefs = retrieve_preferences(user_id)
    current_prefs = []
    for pref in prefs:
        age = now() - pref.timestamp
        if age > PREFERENCE_STALENESS_THRESHOLDS[pref.type]:
            pref = refresh_preference(user_id, pref.type)
        if preference_is_relevant(pref, current_task):
            current_prefs.append(pref)
    return current_prefs
```

## Over-Scoped Personalization

The model accesses more user data than needed for the task. Personalization becomes an attack vector—providing more context than necessary increases the blast radius of any compromise.

The fix: personalization context should be scoped to the minimum required for the current task, with access enforced by the protected service rather than by model instructions.

### The Attack Vector

For personalization, the least-privilege failure is straightforward:
- User has access to 1,000 files
- Task only needs 1 file
- If you load all 1,000 into context, any vulnerability exposes all 1,000
- If you only load the 1 file needed, vulnerability exposes only that 1

This is **least privilege for context**: provide only what's needed for the current task.

### The Fix: Minimum Required Context

```python
def get_task_scoped_context(user_id, task):
    # 1. Determine what context the task needs
    required_context = determine_context_requirements(task)
    
    # 2. Get only that context with capability
    context = retrieve_context(
        user_id=user_id,
        capability=Capability(
            resources=required_context,
            action=task.action,
            expires_in=timedelta(minutes=30)
        )
    )
    
    # 3. Verify scope before injecting
    assert context.resources <= required_context
    
    return context
```

## Summary

Personalization failures are context failures:

- **Missing preferences** → generic output (no user-specific data in context)
- **Wrong user context** → data leakage (identity not bound to retrieval)
- **Stale preferences** → wrong output (no freshness tracking)
- **Over-scoped context** → increased attack surface (more data exposed than needed)

The pattern is consistent: treat personalization as **context assembly at query time**, not as model memory. Bind user identity to every retrieval, timestamp preferences, enforce freshness thresholds, and scope to minimum required.

Personalization is governed context assembly for a specific authenticated subject. Measure whether it works with task relevance, preference freshness, cross-tenant denial tests, provenance coverage, and user-correction rates. Those signals distinguish useful personalization from a system that merely knows more about the user.

Chapter 2 now widens the view: these failures do not live in a single “AI layer.” They emerge from interactions among models, data, orchestration, security, and operations.
