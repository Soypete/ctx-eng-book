# Missing and Incorrect Information

## The Context-Failure Chain

Context failures are easiest to diagnose as a chain rather than as a model
trait:

```text
wrong or missing context
        ↓
wrong interpretation
        ↓
wrong extraction, answer, recommendation, or tool arguments
        ↓
unreliable, over-scoped, or unauthorized consequence
```

The first line can be a Lexicon failure (the source, entity, identity, or
authority is absent or wrong), a Semantics failure (the data's meaning,
relationships, or freshness is unclear), or a Pragmatics failure (the task,
purpose, permitted action, or acceptance criteria are missing). The later
lines are where those gaps become observable behavior. The chain applies to a
search result, classifier, summarizer, recommendation, workflow, or agent;
an agent is only one kind of system that can turn context into an action.

This chain is a debugging model, not a claim that every model error originates
outside the model. If the relevant context and enforcement are adequate and a
controlled evaluation still fails, the residual may be a model-capability
failure.

## The Demo-to-Production Gap

The demo-to-production gap is familiar to anyone who works with data. Production inputs are messier and more varied than the curated examples used in a demo, and user interaction expands the number of cases the system must handle.

Ask ten people what a strawberry tastes like and you will get ten defensible descriptions. Ask a model to solve an underspecified programming problem and there may be many valid implementations. The variability is not proof that “data is probabilistic.” It is evidence that the request, evidence, and acceptance criteria do not determine one answer.

In demos, we deliberately limit outcomes. We choose clean inputs, known questions, and a narrow success case. In production, the system needs explicit handling for inputs and outcomes outside that narrow sample.

### The Concrete Failure Mode

Here's what actually happens in production that doesn't happen in demos:

You build a document Q&A system. In the demo, you show it one clean PDF. The user asks "what is this about?" and it works beautifully.

In production, a user uploads 10 PDFs. Three are scanned images (need OCR). Two are in German. One is a spreadsheet. Another is a contract with a two-page附录 (appendix).

What breaks? The model doesn't "know" it should ask clarifying questions about the German docs. It doesn't know the spreadsheet needs a different processing pipeline than text. It doesn't know the contract appendix is actually the critical part.

The root cause isn't that the model is dumb. It's that the context contract is
missing: the **Lexicon** does not identify the available files and their
authoritative contents, **Semantics** does not describe their formats or
relationships, and **Pragmatics** does not state what the user wants, what
processing is needed, or what format the output should take. The system has to
infer all of it from "answer questions about these files."

This is why the demo-to-production gap exists: demos constrain the input space; production systems must detect, route, reject, or recover from inputs they did not anticipate.

### A Skeptic's Counterargument

Someone might say: "Just use a bigger model with a larger context window. Dump everything in and let the model figure it out."

Larger models may handle more ambiguity, but they do not supply missing authorization, freshness, processing requirements, or acceptance criteria. Those are system responsibilities.

## Missing Context Is One Cause of Hallucination

A hallucination is not simply anything a user dislikes. For this book, the useful operational definition is an output that asserts unsupported or contradictory information as though it were grounded. Missing evidence is one cause. Stale, poisoned, contradictory, or poorly ranked context can cause the same symptom, and some errors remain model-capability failures even when the context is adequate.

### The Attention Mechanism

Here's the key to understanding hallucinations: the attention mechanism automatically focuses on things that statistically matter based on training data. It's designed to route information, not to verify truth.

Vaswani et al. describe attention as a mechanism for relating positions in a sequence; the paper does not claim that attention verifies truth, provenance, authorization, or persistent memory [Vaswani et al., 2017](https://arxiv.org/abs/1706.03762). That distinction is an inference this book makes from the architecture, not a quotation from the paper.

The model still produces a continuation when the supplied evidence is insufficient unless the surrounding system makes uncertainty, refusal, or retrieval the safer path. Better context can reduce unsupported answers. It cannot guarantee truth.

### The Lexicon, Semantics, and Pragmatics Solution

Smaller models may need more explicit instructions and narrower tasks, but capability varies by model and workload. The engineering goal is to remove inference the system can perform deterministically and evaluate the remaining task against the models you can afford to run.

The key insight is narrower: Lexicon, Semantics, and Pragmatics address
different sources of ambiguity. Supplying all three reduces avoidable error,
but the result still requires validation and task-specific evaluation.

This is the first reliability rule of context engineering: the model needs relevant evidence, expressed in a usable form, within an explicit task boundary. A failure in any dimension increases risk; it does not make failure inevitable.

### Computational Pragmatics: Engineering What Works on Any Model

Computational pragmatics gives us a useful engineering question: what must a listener infer about the speaker's intended action? Jurafsky defines computational pragmatics around inference over reference, speech acts, discourse, and abduction [Jurafsky, *Pragmatics and Computational Linguistics*](https://web.stanford.edu/~jurafsky/prag.pdf). Making those variables explicit in an agent interface is this book's engineering inference, not a result established by that linguistics chapter.

1. **Explicitly label intent**: Instead of "Can you help me?" say "This is a request to book a flight from Atlanta to Boston on Tuesday."

2. **Provide action preconditions**: Tell the model what data it needs before it acts. "To book a flight, I need: origin city, destination city, date, and passenger authorization."

3. **Structured prompts that don't require inference**: Use formats the model can parse directly, not natural language it has to interpret.

4. **Decompose the acceptance criteria**: Instead of saying "review code," specify the checks: untested behavior, deprecated APIs, missing documentation, and violations of internal standards. This is task decomposition, not the ReAct pattern; ReAct specifically interleaves reasoning and actions.

This is the pragmatic solution to ambiguity. The user still provides natural language input, but the system transforms it into explicit scoped instructions before the model acts.

### Why Pragmatics Works on Small Models Too

Here's why this is powerful: smaller models are worse at inference. They can't do the complex pragmatic inference that larger models can. But they can follow explicit instructions.

When you provide pragmatics explicitly — "this is a request, not a question" — the small model doesn't have to infer anything. It just acts on the explicit context you provided.

Compare:

| Approach | What the model must do | Works on small models? |
|----------|----------------------|----------------------|
| "Can you review this code?" | Infer intent, scope, format | Struggles |
| "Review code: check for untested functions, deprecated APIs, missing docs" | Follow explicit instructions | Works well |

This pattern can make weaker models useful on bounded tasks, but “works on any model” is not defensible without qualification. Test the structured task on candidate models and measure schema validity, task success, and abstention behavior. You are reducing the inference burden, not eliminating model capability requirements.

### Alternative: Logits and Grammars

Constrained decoding offers another boundary. A grammar masks tokens that would violate an allowed output language during decoding. This constrains generation; it does not manipulate the model's attention mechanism.

Grammars are a more practical version of logit manipulation. At each generation step, the model produces scores for the entire vocabulary. The decoding logic masks out tokens that would violate the structure you want. The model can't drift into invalid formatting because the sampler won't allow it.

Tool calling asks politely. Grammars lock the doors.

But here's the honest assessment: grammars make format reliable. They do not make the model "correct." Constraints can degrade output quality if you make them too tight. You still need validation, bounded retries, and sane stop conditions.

Explicit intent, action preconditions, and scoped subtasks address meaning and workflow. Grammars address output shape. Neither substitutes for authorization, validation, or evaluation.

## Wrong Tool Calls Are Missing Context

The first failure stream is too many tool calls—pulling all the data from MCPs,
searching all the files and all the repos, or expanding every candidate in a
search and recommendation pipeline before understanding the question. The
system retrieves information without direction, and then incorrect
information and incorrect assumptions proliferate in the session. Tool or
source selection requires contextual understanding of what's available, what
the user actually wants, and what information would be relevant versus noise.
Without scoped retrieval, an agent, search system, or RAG pipeline can drown in
data and surface the wrong conclusions.

### The Failure Mode

Here's what happens in practice:

An agent needs to answer a question about a codebase. It has access to 50 MCP tools (file search, git operations, linters, test runners, etc.). It doesn't know which tools are relevant, so it calls 15 of them. Each returns megabytes of context. The relevant signal — a single function definition — is buried in noise.

The agent produces a wrong answer. Not because it couldn't find the right information, but because it retrieved too much and the signal was drowned out.

This is a **control flow bug**, not just a bad answer. The agent isn't failing loudly — it's confidently burning CPU in a loop, retrying the same wrong approach.

### The Real Problem: Models Don't Always Call Tools

Here's the honest truth: even with perfectly defined MCP tools — explicit schemas, clear descriptions, the works — **you cannot guarantee a model will make a tool call**.

The model might:
- Decide to answer from its training data instead of calling the tool
- Partially use the tool's output but fill in gaps with hallucinations
- Ignore the tool entirely and generate a response from parametric knowledge

This is fundamentally different from traditional software, where you call a function and it executes. With tool calling, the model decides *whether* to call, *which* to call, and *how* to use the result.

MCP provides a protocol for discovering and invoking tools. It does not guarantee that a model will choose the right tool, and it does not turn a tool schema into an authorization policy.

This is where pragmatics comes in again. You need to structure the context so that:
1. The model understands it *should* use tools (not answer from memory)
2. The model knows *which* tools are relevant (scoped retrieval)
3. The model understands *how* to use the tool output (explicit instructions)

### MCP as a Contract

MCP (Model Context Protocol) provides a standardized way to expose tools. It's a contract around protocol.

Tool calling is a contract. It's you saying: "If you want to do real work in my system, you have to talk to me in a shape my software can execute."

MCP standardizes that contract. Instead of rewriting the same tool interface for every model provider's format, you bet on a stable tool boundary while models churn underneath you.

This matters because:
- Tool definitions are explicit and machine-readable
- Schema validation can reject malformed requests and responses
- You can evolve the implementation without changing the contract

Retrieved content introduces an untrusted-input boundary: a document can contain instructions that compete with the system's intended task. MCP does not mitigate that risk by itself. The host must enforce tool authorization, validate arguments, isolate untrusted content, and constrain the effect of every call.

Liu et al. formalize prompt injection as attacker-controlled instructions or data entering an LLM-integrated application and evaluate attacks and defenses [Liu et al., 2024](https://arxiv.org/abs/2310.12815). Retrieved-document attacks are one application of that threat model; the paper does not certify any single RAG defense.

## Conclusion: The Fix Isn't Better Models, It's Better Context

“Every failure is a context failure” is a productive debugging provocation, not a literal law. When an AI system fails, inspect the information, state, authority, constraints, and acceptance criteria around the model before assuming the model is the root cause. If those are adequate and the behavior still fails a controlled evaluation, you may have found a model-capability problem.

The fix isn't to wait for better models. It's to engineer better context:

1. **Provide complete pragmatic context**: Explicit intent, action preconditions, scoped instructions
2. **Use structured tools with clear contracts**: MCP or similar protocols with explicit schemas
3. **Constrain retrieval scope**: Don't dump everything; provide only what's relevant
4. **Validate outputs**: Grammars and tool calling aren't perfect; add bounded retries and sanity checks

Many AI failures are not mysterious. They can be traced through the context assembly and execution path, then corrected in software. Better models still matter; the point is not to use them as a substitute for an engineered system.
