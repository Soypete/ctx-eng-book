# Context Failure Case Studies

The scenarios below isolate different failure boundaries. The customer-data pattern is one I have seen engineers build at work. It is a recurring design pattern rather than a report of one identifiable incident. The remaining scenarios are constructed examples based on common production architectures; they are not reported incidents, and their numbers and outcomes should not be read as measurements.

## The Production Debugging Loop

**Failure Mode**: Agent Loop (Missing State)

Consider an AI assistant for production debugging with access to logs, metrics, and a knowledge base. When a user asks “why did service X fail?”, the agent starts querying logs.

Without a terminal condition, the agent can keep querying logs, finding related errors, and following chains of causation. Tool-call and time budgets eventually stop the run, but only after it has spent resources without establishing a useful answer.

Root cause: the agent wasn't given success criteria. "Find the root cause" isn't enough context. The agent needs: what level of confidence constitutes success, what evidence is sufficient, when to stop digging.

The fix is two-layered. Give the model explicit success criteria, then have the harness enforce tool-call, time, and output budgets. A confidence threshold alone is weak because model-reported confidence is not calibrated evidence. Require named supporting signals, record which checks passed, and stop after the enforced limit.

## The Overhydrated Customer Context

**Failure Mode**: Scope and Permission Failure (Unconstrained Context)

I have seen engineers build systems that issue a SQL query for a user, select all data the user is allowed to access, and tell the model to figure out which records are valuable and necessary for the task. That delegates a missing system design decision to inference. A model can act on the instructions and context it receives, but raw rows do not explain what their fields mean, which source is authoritative, why a record matters now, or what the task requires. If the system supplies data without supplying those semantics, the result is still garbage in, garbage out.

The query may satisfy a coarse access check while returning far more information than the task requires. The model is not a reliable substitute for a relevance contract: it can overlook necessary records, retain distracting ones, or use sensitive fields that the task did not require.

This design collapses authorization and relevance into one operation. “The user may read this” is not the same as “the model needs this for the current task.” Irrelevant customer interactions, tickets, and account fields consume context and increase the consequences of prompt injection, logging mistakes, or an overly broad response. If the SQL query also lacks tenant- or resource-level predicates, the same pattern becomes an authorization failure and can return records outside the requester's scope.

Root cause: the system treats the model as both the semantic interpreter and the scope-reduction boundary. It provides data without enough information about meaning, authority, task relevance, or permitted use. A prompt may ask the model to figure it out or ignore irrelevant records, but that instruction does not repair an undefined data contract, minimize retrieval, or enforce access control.

The fix has three parts. First, enforce scoped delegated access: the retrieval request carries server-issued authority constrained to `customer_id=X`, fields `[name,email,tickets]`, action `read`, and a short expiration. Second, derive a task-specific projection and selection before results enter model context. Third, attach the semantic context the task depends on: field definitions, provenance, freshness, relevant relationships, and rules for interpreting values. The protected service enforces authority; trusted context-assembly code enforces minimization and supplies the contract. The model receives an authorized working set whose meaning and purpose are explicit.

## The Unbounded Context Bill

**Failure Mode**: Cost Overrun (Unmeasured Context)

Consider a documentation RAG system that places no bound on query expansion, retrieved results, or assembled tokens. As usage grows, the bill grows faster than the number of useful answers.

One request can fan out into hundreds of retrieval calls and far more context than the model can use. The vector search has no rank limit, context assembly concatenates every result, and the prompt includes full documents when targeted passages would suffice.

Root cause: no context budget controls. No measurement of retrieval efficiency. No cost attribution.

The fix is a context budget at each stage: cap candidates, rerank within a measured latency budget, assemble passages up to a task-specific token limit, and attribute retrieval and inference cost to the request. Verify that the cheaper path preserves task success; a lower bill is not a reliability improvement if recall collapses.

## The Stale Context Poisoning

**Failure Mode**: Missing Information (Temporal)

Consider a sales assistant whose CRM context is refreshed through a daily vector-store sync. A deal closes in the source system but remains “negotiating” in the retrieval index, so the assistant recommends an action for an already-closed deal.

Root cause: the retrieval pulled cached context that was 24 hours old. The CRM updated in real-time but the vector store refreshed daily. The assistant was working with stale information.

The fix: add freshness metadata to context. Timestamp every retrieval. Set freshness requirements per query type—"for pricing questions, data must be less than 1 hour old". Implement freshness-aware retrieval: check staleness before returning, trigger fresh fetch if needed.

## Authorization Drift Across Workflow Boundaries

**Failure Mode**: Permission Failure (Scope Creep)

Consider a system with research, analysis, and reporting components. Research
can read raw data, analysis can read aggregates, and reporting can read only
summaries. The same pattern applies when the components are ordinary services,
workflow steps, or human-facing automation rather than agents.

The reporting component can still obtain raw details through the analysis
component if the callee uses its own broader authority rather than the caller's
delegated scope. This is a confused-deputy failure: permission boundaries are
advisory because they are enforced by prompts rather than at each call or
execution boundary.

Root cause: agents can call each other without delegated-authority verification. The analysis agent does not check what the reporting agent is authorized to receive. Rashidi's 2026 systematization reviews 39 execution-security papers and reports that the surveyed policy-enforcement studies found failure rates from 69% to 98% on real denylists [Rashidi, 2026](https://arxiv.org/abs/2607.05743). This is a reported range across cited studies, not a measured failure rate for the scenario here.

The fix: implement capability passing. When one component calls another, the
caller must present its capability. The callee and the protected execution
service verify that the capability permits the requested data and operation.
The boundary is structural, not advisory.

## Summary

These scenarios share a pattern: the model is operating inside a system that failed to bound information, authority, time, or cost. Prompts can describe the boundary; software must enforce it. The fixes are:

- **Exit criteria**: Agents need to know when to stop
- **Structural permissions**: Capabilities, not prompts, enforce access
- **Budget controls**: Measure and limit context at every stage
- **Freshness requirements**: Timestamp context, enforce staleness limits
- **Capability verification**: Agents verify each other's permissions

For every fix, capture the evidence needed to tell whether it worked: termination reason, tool-call count, authorization decisions, freshness age, retrieved and used tokens, latency, cost, and task outcome. That turns “context failure” from a slogan into a debugging method.
