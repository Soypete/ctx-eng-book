# Missing State and Constraints

## Workflow Loops Are Missing Exit Criteria

Loops happen when an agent, batch workflow, or automated repair process cannot
determine that it has succeeded, failed, or exhausted its budget. Missing
schema context can start the loop, but the durable fix is workflow state and
enforcement: record attempts, classify errors, define terminal conditions, and
stop retrying when another attempt cannot add information.

### The Concrete Failure Mode

Here's what happens in practice. You need to query a database: first get a user ID, then use that ID to get orders, then get order details.

```sql
-- Step 1
SELECT id FROM users WHERE email = 'alice@example.com';
-- Returns: user_id = 123

-- Step 2
SELECT order_id FROM orders WHERE user_id = 123;
-- Returns: order_ids = [456, 457]

-- Step 3
SELECT * FROM order_items WHERE order_id IN (456, 457);
```

Now imagine the database column is `user_id` in one table but `userid` in another (inconsistent schema). The model:
1. Queries the first table, gets user_id 123
2. Tries to query orders with `user_id = 123`, fails
3. Infers from context that maybe it's `userid`, retries
4. Gets results, but now has to verify correctness
5. Might loop indefinitely if it keeps hitting schema mismatches

The first defect is that the model does not know the schema upfront. The reliability defect is that the harness treats repeated schema errors as permission to improvise indefinitely instead of a typed failure that changes state or terminates the run.

### The Fix: Exit Criteria + Guardrails

There are two approaches:

**Approach 1: Exit criteria in system prompt**
```
"Provide a root cause analysis with confidence level. Stop when confidence exceeds 80% or after 10 tool calls. Summarize findings in 200 words."
```

This helps but isn't foolproof — the model might keep retrying for "higher confidence."

**Approach 2: Structural enforcement (Forge guardrails)**
The Forge repo provides guardrails that force tool call expectations:
- Schema validation: reject tool calls that don't match expected parameters
- Output validation: verify tool responses before proceeding
- Loop detection: count tool calls, stop after N attempts
- Constraint enforcement: explicitly define what's allowed

This is more reliable than prompt-based exit criteria because it's enforced at the system level, not relied on from the model.

The comparison:

| Approach | What happens | Reliability |
|----------|-------------|-------------|
| Exit criteria in prompt | Model decides when to stop | Can be ignored or misinterpreted |
| Structural guardrails | System enforces the limit | Deterministic if every execution path passes through the guardrail |

For production systems, use both: explicit exit criteria in prompts for clarity, but structural guardrails for enforcement.

## Missing Authorization Context Is Not the Same as Over-Scoped Context

When agents first started automating jobs, there was a lot of user impersonation—agents acted as the user via prompt instructions, inheriting tokens and credentials. This opened the door to prompt injection: someone could convince the bot to act on behalf of a person they are not [Liu et al., 2024](https://arxiv.org/abs/2310.12815). Access and permissions should be scoped to the authenticated principal and delegated task. Existing authorization mechanisms should enforce data access instead of relying on prompts to convey permission; Chapter 11 develops that boundary from OAuth, OpenID Connect, and capability-security sources.

Authorization is therefore part of context engineering, not a separate concern
added after the system works. An agent can have valid credentials, a valid tool
connection, and a legitimate high-level goal and still act incorrectly. The
missing context is often who it represents, why this action belongs to the
task, which resources are in scope, what operations are permitted, whether
authority may be delegated, and when that authority expires.

Possession is especially easy to confuse with permission. Discovering a credential does not establish that the current task may use it. Authenticating a user does not establish that every resource the user can access belongs in model context. A prompt that says “ask before deleting” does not create an approval boundary. When the model must infer these distinctions, it is being asked to interpret its own authorization envelope.

| Missing authorization context | Resulting ambiguity |
|---|---|
| Principal | Is the agent acting for the user, itself, a service, or another agent? |
| Resource | Which records, systems, and external resources belong to this task? |
| Credential | Does possession authorize this credential's use here? |
| Purpose | Is an otherwise permitted action allowed for this purpose? |
| Action | May the workflow read, write, delete, purchase, or execute? |
| Delegation | Which authority, if any, may a subagent inherit? |
| Time | When does the task's authority expire? |
| Approval | Which operation requires a trusted human decision? |
| Provenance | Did an instruction come from trusted task state or discovered content? |

These are context fields, but they are not ordinary prompt text. Trusted code
must resolve them from authenticated state, policy, workflow state, and
provenance, then enforce the resulting decision at retrieval and execution
boundaries.

Three failures are easy to conflate:

- **Missing authorization context:** the system cannot establish the principal,
  purpose, resource, action, delegation, or expiry, so it cannot make a sound
  access decision.
- **Over-scoped context:** the system knows who may access the data but places
  more authorized data in the working set than the task requires. This is a
  minimization and relevance failure, even when the access check passes.
- **Execution-boundary failure:** retrieval or model context may be correctly
  scoped, but a downstream tool, service, or workflow accepts an operation
  without rechecking the authority and action at the point of effect.

The fixes differ. Supply and resolve authorization context for the first;
project and retrieve the minimum task-relevant working set for the second; and
make the protected service enforce capabilities at execution for the third.

### A Credential Is Not a Task Boundary

Consider an automated workflow that discovers a valid credential while
processing a document or calling an internal service. The credential may
authenticate the workflow, but it does not establish that the current task may
use every resource or operation available through it. A workflow asked to
summarize a customer account should not be able to export unrelated accounts,
modify billing data, or send an external message merely because its credential
would technically permit those actions.

The general principle is simple: possession proves capability, not purpose or
authorization. Bind the principal, resource, purpose, action, delegation, and
expiry to trusted task state. Enforce that binding when data is retrieved and
again when an operation takes effect. This keeps a credential from silently
becoming the task boundary and preserves the Lexicon/Semantics/Pragmatics
distinction: identify the authoritative resource, make its scope and meaning
explicit, and constrain what the actor may do with it.

### The Prompt Injection Problem

The repository notes do not substantiate the manuscript's former malicious-skill campaign names and counts, so they are not used here. The underlying threat model is still useful. A compromised agent becomes dangerous when it combines:

1. **Access to private data** (credentials, keys, files)
2. **Exposure to untrusted content** (skill instructions, memory files)
3. **Ability to communicate externally** (network egress, webhooks)

This combination—private-data access, untrusted input, and external communication—is a permission failure pattern at scale. The root cause is not merely that permissions appear in a prompt; it is that the execution environment grants authority the task does not require.

### The Fix: Structural Authorization, Not Prompt Instructions

Prompt-based permissions inherit user credentials. If the prompt says "you can access customer data," a prompt injection attack can override that instruction.

One useful implementation is **capability-based access**:

```
Every tool call includes a capability token:
  - customer_id=X
  - fields=[name, email, tickets]
  - action=read
  - expires_in=30min

The database enforces the capability.
Even with a malicious prompt, the agent can only retrieve data its capability permits.
```

This is structural enforcement:
- Capability is generated at query time, not stored in prompt
- Database enforces capability, not model
- Even if prompt is compromised, the data layer rejects unauthorized access

One proposed skill-manifest shape expresses filesystem and network policy explicitly:

```yaml
permissions:
  files:
    read:
      - ~/.config/app.json
    deny_write:
      - SOUL.md
      - MEMORY.md
  network:
    allow:
      - api.example.com
    deny: "*"
```

This is a shift from "trust the prompt" to "enforce at the system layer."

The manifest is only a declaration. The runtime must reject undeclared access, prevent confused-deputy calls through other tools, log the decision, and make revocation effective during a run.

## Cost Overruns Are Unmeasured Context

Larger context means larger bills—AI is billed by token. The money optimization question is shorter agent loops. The failures I mostly see are around compaction: how do we shorten context without losing relevant information? Without context budget controls, systems consume unlimited tokens, make redundant calls, or retrieve unnecessary data. The context failure here is failing to measure, limit, and optimize what gets included. Context Precision = Useful Context / Retrieved Context—too much irrelevant context increases cost, latency, attention competition, and hallucination risk [kg-quality-metrics-notes, p.616].

### The Compaction Problem

You have a 100-page document. The user asks a simple question. Do you:
1. Dump the entire document into context (100K tokens, expensive)
2. Summarize the document (5K tokens, might lose relevant detail)
3. Retrieve only the relevant sections (1K tokens, requires good retrieval)

The failure mode: no context budget controls means option 1 happens by default.

As a constructed example, consider a request that triggers 200 retrieval calls and pulls 500,000 tokens because vector search has no rank limit and context assembly concatenates every result. The values are illustrative rather than measurements from an incident. The point is the missing invariant: neither retrieval fan-out nor assembled context has an enforced upper bound.

### The Fix: Context Budget at Each Stage

Implement budget limits at every stage:

1. **Retrieval stage**: Vector search max 10 results, rerank to top 3
2. **Assembly stage**: Truncate to 8K tokens, prefer summaries over full text
3. **Prompt stage**: Use condensed context format, strip redundant boilerplate
4. **Tracking stage**: Add cost tracking per request, attribute to users/queries

The effectiveness of these limits should be measured as task success per request alongside retrieved tokens, model tokens, latency, and cost. The manuscript's former “3 percent of the original” figure is omitted because the repository contains no reproducible calculation or attributable case study.

### Logits and Grammars: Constrained Decoding for Reliability

You can also use logits manipulation and grammars to constrain outputs, but there's a critical constraint: **you can only use this with self-hosted models**.

Here's why: logits are the raw scores before probability distribution. When you call an API like OpenAI or Anthropic, the decoding happens server-side — you never see the logits. You can only constrain outputs through their provided interfaces (tool calling, JSON mode, etc.).

With self-hosted models (llama.cpp, vLLM), you have access to:

1. **Grammars** (GBNF): Define what tokens are valid at each position. At each generation step, the model produces scores for the entire vocabulary. The decoding logic masks out tokens that would violate the structure. The model can't drift into invalid formatting because the sampler won't allow it.

2. **Logit flags**: Directly manipulate the scores to boost or suppress certain tokens.

These mechanisms constrain decoding, not attention. Grammar-constrained generation is an engineering feature exposed by several self-hosted inference runtimes; direct logit manipulation is lower-level and usually less portable.

For practical purposes: tool calling asks politely, grammars lock the doors. But grammars make format reliable, not correctness. Constraints can degrade output quality if too tight. You still need validation, bounded retries, and sanity checks.

The pragmatic approach — explicit context, scoped retrieval, structural guardrails — works on any model, including third-party APIs where you can't touch logits.

## Summary

Loops, permission violations, and cost overruns often expose missing state, boundaries, or exit criteria. Describing those requirements in context helps the model reason about them; enforcing them in software makes them reliable:

- **Exit criteria**: Both prompt-based (for clarity) and structural (for enforcement)
- **Permission guardrails**: Capability-based access, not prompt-based trust
- **Budget controls**: Context limits at every stage (retrieval, assembly, prompt)
- **Constrained decoding**: Grammars and logits for self-hosted models; pragmatic context for all models

Measure the result at the boundary: attempts before termination, unauthorized operations rejected, tokens retrieved versus used, latency, and task success. The next module applies this diagnostic to concrete scenarios—and must distinguish real incidents from teaching examples.
