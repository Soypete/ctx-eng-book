# ch07.03 Freshness, Consistency, and Partial Failure

## A Prompt Can Contain Several Different Pasts

Distributed context has no automatic “now.” A search result may reflect an index built at 10:00, an account row may be read at 10:04, and a fulfillment API may return an event effective at 10:02. If the pipeline records only retrieval time, all three can look equally current even though they describe different versions of the world.

Track the temporal fields the source can defend:

- **event time** — when the underlying event occurred;
- **effective time** — when a value became valid in its domain;
- **source version or snapshot** — which database, API, or projection state was read;
- **indexed or transformed time** — when a derived representation was built;
- **retrieval time** — when the assembler obtained it;
- **freshness policy** — how old or how far behind this task permits it to be.

Not every source exposes every field. Missing temporal metadata is itself a constraint. The pipeline should not label a result “fresh” merely because it arrived quickly.

## Consistency Is a Task Requirement

Strong and eventual consistency are not UI modes selected by waiting longer. Each source offers particular read, write, and ordering guarantees. Independent services may not share a transaction or even the same definition of version. Parallel queries therefore cannot promise a globally coherent snapshot unless the architecture supplies a coordination mechanism designed for one.

Specify the invariant the task needs. A recommendation may tolerate a slightly stale catalog description. Charging an account cannot tolerate a revoked entitlement merely because a cache has not converged. A status explanation may show two attributed observations; an automated side effect may require a read from the authoritative system plus a conditional write against the version that was approved.

Useful strategies include:

- read authoritative state for the fields that gate an action;
- use version tokens or effective times to detect changes between approval and commit;
- read related fields from one snapshot when the database supports it;
- project events into a versioned current-state view;
- allow stale evidence only for tasks whose policy explicitly permits it;
- stop or clarify when required consistency cannot be established.

This is a host-policy decision. Telling a model, classifier, or workflow that a record may be stale can improve disclosure, but it cannot make an unsafe transaction safe.

## Classify Partial Failure

A five-source plan can produce five different outcomes. “Partial failure” is too coarse unless the plan also knows which sources are required for this task.

| Outcome | Meaning | Typical response |
|---|---|---|
| `empty` | successful query found no matching data | proceed if absence is valid evidence |
| `denied` | principal lacks required scope | stop, narrow the task, or request authorized escalation |
| `stale` | data violates the task's freshness policy | refresh, use an authoritative source, or stop |
| `timeout` | result is unknown within the deadline | retry within budget, degrade if optional, stop if required |
| `invalid` | response violated its schema or contract | quarantine result and surface an integration failure |
| `conflict` | sources disagree under the applicable authority rule | resolve deterministically or stop |

Graceful degradation is not “answer with whatever arrived.” It is a predefined reduced behavior. An order assistant may answer with a tracking link when optional support history is unavailable. It should not assert that an order is refundable when the policy source failed.

The user-facing response or workflow status should describe the missing capability at the right level without leaking source names, credentials, or internal topology. The manifest should preserve the precise outcome for operators.

## Retry Under One Deadline

Read operations are often safe to retry, but retries still consume latency, rate limits, money, and shared capacity. They may also observe a newer version and change the assembled context halfway through a workflow.

Give the whole assembly a deadline. Allocate per-source attempts within that budget, retry only failures classified as transient, use backoff and jitter when contention is possible, and respect provider retry guidance. Do not retry authorization denials, schema failures, or valid empty results. A circuit breaker can reduce pressure on a repeatedly failing optional dependency, but it changes the expected availability of that source and must appear in the manifest.

Hedged reads or fallbacks can reduce tail latency when the source contract allows them. They also need an authority rule: two replicas or providers can return different versions. “First response wins” is a latency policy, not a correctness policy.

## Resolve Contradictions Before Serialization

Source attribution helps a reader understand disagreement, but it is not a conflict-resolution algorithm. If a profile projection says `Basic` and the billing authority says `Premium`, the assembler should know which source governs entitlement. It may include the stale projection as diagnostic evidence, but it should not ask the model to choose based on prose.

Some contradictions cannot be resolved automatically. Two human-authored incident reports may be competing claims rather than authoritative state. Preserve both with provenance and label the uncertainty. The important distinction is between conflicts governed by an application invariant and disagreements that legitimately require investigation.

Test both. Inject an outdated cache after a plan upgrade and assert that billing wins. Inject two incompatible witness statements and assert that neither is promoted to fact. Then verify the final context and the machine decision.

## Reliability Comes from an Explicit Degradation Policy

Freshness and consistency requirements should be part of the retrieval plan, not prose added after retrieval. For each required input, define the acceptable version relationship, maximum age or lag, authority, retry class, and behavior when the requirement cannot be met.

Measure stale-result rate, conflicts by source pair, required-source failure, degraded-operation frequency, deadline exhaustion, and incorrect proceed decisions. The last metric is the one that matters: did the pipeline continue when its own policy said the evidence was insufficient?

A distributed context pipeline cannot eliminate partial failure. It can prevent partial failure from becoming invisible confidence by preserving authority, provenance, freshness, identity scope, and semantic status through assembly.
