# ch07.01 Sources of Context

## Context Is a Materialized View for One Invocation

Teams often ask where an agent's context is stored. The question confuses source data with the working set presented to a model. Databases store records. Object stores retain documents. Event logs preserve changes. A model invocation receives a bounded representation assembled from those sources for a particular task, principal, and moment.

That representation is closer to a materialized view than a container. It may combine a user request, system policy, workflow state, database rows, search results, API responses, tool observations, and generated summaries. Not every input requires a remote query, but every input is selected and transformed through a boundary the application should be able to name.

This changes the reliability question. “Do we have the data?” is insufficient. Ask which sources are eligible for this task, which principal may access them, what operation selects from each source, how results are transformed, and which version actually reached the model.

## A Source Contract

Each contributor to context needs a contract. At minimum, record:

- **purpose** — the decision or claim this source can support;
- **authority** — whether it is policy, operational truth, user assertion, historical evidence, or a model-derived hypothesis;
- **scope** — tenant, user, workflow, and purpose restrictions;
- **selection operation** — key lookup, SQL query, search, traversal, subscription, or direct input;
- **temporal semantics** — observed time, effective time, freshness target, and expiration;
- **failure semantics** — empty, denied, stale, timed out, malformed, or unavailable;
- **budget** — latency, result count, and token allocation;
- **provenance** — source identifiers and transformations required for audit or replay.

Without this contract, the assembler produces a pile of plausible text. With it, the system can distinguish an empty result from a failed query, a current policy from a similar old ticket, and an authorized record from one that merely ranked highly.

## Operational Databases: Bounded State

Relational and document databases are useful when the system knows the identity and shape of the state it needs. A support agent answering “Where is my order?” might fetch recent orders with a parameterized query:

```sql
SELECT id, status, status_updated_at
FROM orders
WHERE tenant_id = $1
  AND user_id = $2
ORDER BY status_updated_at DESC
LIMIT 5;
```

The query result, not the whole table, becomes eligible context. The tenant and user filters are part of the authorization boundary; the selected columns are part of the disclosure boundary; the limit is part of the context budget.

A database transaction can provide a defined snapshot within that database, depending on its isolation level. It does not make independently queried services mutually consistent. The context contract therefore needs the snapshot or version information required to interpret a row and must avoid claiming cross-system coherence that the platform cannot provide.

Test these queries like application code. Use fixtures for wrong-tenant IDs, empty histories, superseded rows, pagination boundaries, and concurrent changes. A syntactically valid query can still return context that is complete, current, and precisely wrong for the task.

## APIs: Remote Authority with Local Failure

An API exposes another system's view of its state. That system controls the response schema, availability, rate limits, and often the meaning of freshness. The local context pipeline controls authentication, timeouts, validation, caching, and how failure affects the task.

A typed response should retain more than its payload:

```json
{
  "source": "fulfillment",
  "retrieved_at": "2026-08-06T16:32:00Z",
  "effective_at": "2026-08-06T16:31:42Z",
  "status": "ok",
  "data": {"order_id": "1235", "state": "in_transit"}
}
```

Do not turn timeouts into empty arrays or authorization denials into “not found.” Those outcomes lead to different engineering decisions. Schema validation catches malformed responses, while contract tests and versioning reduce surprises when the provider evolves. Chapter 7.3 addresses what to do when remote sources disagree or fail.

## Documents and Search Indexes: Ranked Evidence

Documents can be retrieved through exact metadata filters, lexical search, dense similarity, or hybrid ranking. These mechanisms solve different problems. Lexical ranking finds matching terms; configured analyzers and expansion may add variants. Dense retrieval finds proximity in a learned representation. Neither establishes that a result is true, current, authorized, or sufficient.

Indexes are derived data. They have an ingestion version, an update lag, a ranking configuration, and a path back to canonical content. Return document IDs, chunk boundaries, scores, source timestamps, and authorization scope alongside text. When a result supports a consequential claim, fetch or validate the authoritative record instead of treating rank as authority.

Evaluate retrieval against task-specific judgments. Top-*k* is a budget, not a quality guarantee. Measure whether required evidence was retrieved, whether irrelevant evidence displaced it, and whether truncation removed the part that justified the answer. Chapter 9 develops ranking and hybrid retrieval in detail.

## Event Streams: Changes, Not Current Truth by Default

An event stream supplies an ordered sequence only within the guarantees of its partitions, producers, and consumer protocol. A bounded read can answer “what changed since this offset?” It does not automatically answer “what is true now.” Current state usually requires a projection with explicit ordering, deduplication, and replay behavior.

For context assembly, preserve event identity, event time, ingestion time, partition or sequence information, and projection version. A consumer crash can cause replay or omission depending on when processing and offset commits occur. Idempotent projection logic and replay tests matter more than telling the model that the events are “recent.”

Raw events are often too verbose for an invocation. A typed projection—recent shipment transitions for this authorized order—is more useful than the last twenty messages from a shared topic.

## Analytical Stores: Useful but Delayed

Warehouses and lakehouses contribute aggregates, historical comparisons, and large-scale features. Their data may be intentionally delayed by ingestion and transformation schedules. That is acceptable when the task contract allows it.

An aggregate should carry its definition, time window, data cutoff, population, and version. “Average order value: $127” is ambiguous without currency, segment, interval, exclusions, and computation time. The model can phrase a precise answer only when the pipeline supplies precise semantics.

Do not synchronously run an unbounded analytical scan because an agent decided a statistic might help. Precompute common features, constrain query templates, enforce cost and time budgets, and fall back explicitly when the analytical result is unavailable.

## Inventory the Contributors

For one representative agent task, create a source inventory before changing the prompt. List every contributing input, its authority, scope, selection operation, freshness requirement, and failure behavior. Then capture an assembly trace showing which candidates were retrieved, which were excluded, what transformations ran, and what the model received.

This is how the chapter thesis improves reliability: context is assembled from distributed state, so the assembly must be treated as an observable, authorized data product. Better source contracts do not guarantee a correct model response, but they make missing, stale, conflicting, and over-broad inputs detectable before those inputs silently shape an action.
