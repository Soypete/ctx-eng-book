# ch07.04 Hydration Coverage and Retrieval Success

## Availability Is Not Context Readiness

An agent can call every dependency successfully and still assemble inadequate context. A search may return irrelevant documents. An API may return a stale projection. A required field may be absent from an otherwise valid response. Conversely, an optional source may fail without affecting the task.

The system needs to compare what the task required with what the pipeline produced. This chapter calls that comparison *hydration coverage*. The term is a proposed engineering metric in this book, not an established industry standard.

## Define Requirements Before Measuring Coverage

A raw ratio of retrieved sources to expected sources is easy to compute and easy to misread. Suppose a refund workflow retrieves CRM and support history but cannot retrieve the current refund policy. Two of three sources succeeded, yet the agent has zero basis for authorizing a refund.

Define context requirements as typed slots:

```text
identity.customer       required   authority=identity
order.current_state     required   authority=fulfillment
policy.refund_rule      required   authority=policy
support.related_cases   optional   authority=evidence
```

A slot is hydrated only when a result satisfies its scope, schema, freshness, provenance, and authority constraints. A response that merely arrived does not count.

For monitoring, calculate at least two values:

```text
required_coverage = hydrated_required_slots / required_slots
optional_coverage = hydrated_optional_slots / optional_slots
```

Keep the numerator and denominator beside the percentage. `2/2 required, 0/3 optional` communicates more than `40%`. If requirements have different consequence levels, report them by class rather than hiding them inside arbitrary weights.

Coverage also does not measure relevance within a slot. A search slot can be technically hydrated while missing the document needed to answer. Pair coverage with retrieval precision and recall estimates, freshness, provenance coverage, and downstream task success.

## Preserve Outcome Semantics

For every required slot, record why it was or was not hydrated:

- `satisfied` — valid result met the slot contract;
- `empty` — valid query established that no matching data exists;
- `not_found` — expected entity or record was absent;
- `denied` — active principal lacked access;
- `stale` — result exceeded the allowed age or version lag;
- `timeout` or `error` — dependency did not produce a usable result;
- `invalid` — result failed schema or semantic validation;
- `excluded` — a usable candidate lost a declared budget or ranking decision.

Whether `empty` satisfies a slot depends on its semantics. “No prior tickets” can be a complete answer. “No current policy record” is a blocking integrity problem. Authorization denial is not a retrieval-quality failure, but it still means the task cannot use that slot; operational dashboards should separate the two.

## Instrument the Assembly Manifest

The manifest introduced in the previous module already contains the raw material. Compute coverage from planned slots and final inclusion decisions, not merely successful network calls.

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class Slot:
    name: str
    required: bool
    satisfied: bool


def coverage(slots: list[Slot], required: bool) -> tuple[int, int]:
    selected = [slot for slot in slots if slot.required is required]
    return sum(slot.satisfied for slot in selected), len(selected)


slots = [
    Slot("identity.customer", True, True),
    Slot("order.current_state", True, True),
    Slot("policy.refund_rule", True, False),
    Slot("support.related_cases", False, True),
]

assert coverage(slots, required=True) == (2, 3)
assert coverage(slots, required=False) == (1, 1)
```

Trace the plan version, slot outcomes, source latency, retrieval count, validation failures, budget exclusions, and final proceed/degrade/stop decision. Aggregate by task class and source. An overall average can conceal that one safety-critical workflow is consistently missing its policy slot.

Alerts should follow consequences. A drop in optional evidence coverage may reduce answer quality. A single request that proceeds with an unsatisfied required authorization slot is an integrity incident.

## Tell the Model Only What It Can Use

The model needs a task-level capability signal, not raw infrastructure diagnostics. If optional support search failed, the context can state that historical cases were unavailable and prohibit claims based on them. If current order state is missing, the host may ask the user to retry rather than invite the model to infer status.

Do not ask the model whether it wants to proceed when policy has already established that required context is absent. Model discretion is appropriate only inside a bounded choice the application permits—for example, answering a general explanation while clearly withholding a personalized determination.

## Test Coverage Against Outcomes

Failure-injection tests should verify both the metric and behavior:

- deny an optional source and expect degraded coverage plus a permitted answer;
- time out a required policy slot and expect `stop`;
- return an empty but valid history and expect the slot to be satisfied;
- return stale inventory and expect the slot to remain unsatisfied;
- retrieve a relevant document and exclude it through budgeting, then expect an `excluded` outcome;
- mutate the requirement-plan version and ensure old dashboards do not compare incompatible denominators silently.

Hydration coverage answers one narrow question: did the pipeline supply the context contract this task declared? It does not prove that the context was relevant, that the model used it correctly, or that the final action was safe. Its value is diagnostic. It separates missing context from later failures and makes silent incompleteness visible.

The remaining modules broaden the source inventory to public information and to extraction pipelines that create new queryable representations.
