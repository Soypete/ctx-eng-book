# Hydration Coverage and Retrieval Success

## Argument

Hydration coverage compares a versioned task's declared context slots with the usable results that satisfied their scope, schema, freshness, provenance, and authority contracts.

## Reliability goal

Expose missing required context without treating optional-source success, network success, or a single percentage as proof of readiness.

## Evidence status

Hydration coverage is original terminology and a proposed metric in this book. It should be evaluated empirically rather than presented as an established standard.

## Sequence

1. Distinguish dependency availability from task readiness.
2. Define required and optional typed slots before retrieval.
3. Preserve satisfied, empty, not-found, denied, stale, failed, invalid, and excluded outcomes.
4. Compute coverage from the assembly manifest.
5. Give the model only the bounded capability signal policy permits.
6. Validate metrics and decisions through failure injection.

## Code example

Executable standard-library Python calculates required and optional `(hydrated, expected)` pairs and asserts the example.

## Limitations

Coverage does not measure within-slot relevance, retrieval recall, correct model use, or action safety. Denominators are plan-version dependent.
