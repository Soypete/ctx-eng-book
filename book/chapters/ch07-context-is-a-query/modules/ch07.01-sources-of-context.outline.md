# Sources of Context

## Argument

Context is a task-specific materialized view assembled from distributed state and direct inputs; every contributor needs an explicit authority, scope, temporal, transformation, and failure contract.

## Reliability goal

Make missing, stale, inconsistent, unauthorized, and over-broad context diagnosable at the source boundary.

## Sequence

1. Distinguish stored source data from the invocation working set.
2. Define a source contract covering purpose, authority, scope, selection, time, failure, budget, and provenance.
3. Apply the contract to operational databases and APIs.
4. Treat document and index results as ranked evidence rather than authority.
5. Distinguish event sequences from current-state projections.
6. Attach definitions and cutoffs to analytical results.
7. End with a source inventory and assembly trace exercise.

## Corrections from draft

- Not every context input arrives through a query; direct user input, static policy, and workflow-generated observations also contribute.
- ACID does not guarantee cross-source consistency and depends on transaction isolation.
- Dense indexes are not inverted indexes, and lexical search does not automatically provide semantic synonym matching.
- Streams expose changes under specific ordering and delivery guarantees; they are not current truth without projection logic.

## Examples

- Parameterized, tenant-scoped order query.
- Provenance-bearing API result envelope.
- Source-contract inventory as the practical architecture artifact.
