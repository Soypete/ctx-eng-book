# Freshness, Consistency, and Partial Failure

## Argument

Distributed context combines different versions of reality; task-specific temporal, consistency, authority, retry, and degradation policies determine whether inference may safely proceed.

## Reliability goal

Prevent stale, conflicting, or unavailable required state from being serialized as ordinary evidence.

## Sequence

1. Separate event, effective, source-version, indexed, and retrieval times.
2. Define consistency from task invariants rather than a universal strong/eventual choice.
   - Mermaid flow: required input → temporal/version comparison → fresh/consistent decision → retry, degrade, or stop
3. Classify empty, denied, stale, timeout, invalid, and conflict outcomes.
4. Retry transient reads under one assembly deadline.
5. Resolve governed conflicts before serialization; preserve legitimate disagreement.
6. Measure incorrect proceed decisions as the primary reliability failure.

## Corrections from draft

- Waiting for services to synchronize does not create a strongly consistent cross-service snapshot.
- Eventual consistency is not generally correct for action-gating state.
- Partial results are acceptable only under a predefined task policy.
- Attribution alone does not resolve conflicts, and the model is not the authority boundary.
- Curriculum anchors: `09_Agent_Evals/README.md` (repeated trajectories and planted regressions) and `22_Observability/README.md` (drift and detection lag).
