# ch09.01 Lexical and Relational Retrieval

## “Right” Depends on the Query

Retrieval fails when one mechanism is asked to answer every question. “Find discussions of intermittent authentication failures” is a ranking problem. “Fetch order `2026-1841` for this tenant” is a keyed lookup. “Which policy version governed this approval?” is a temporal relational query. Similarity is useful for the first and unsafe as the authority boundary for the others.

Classify the information need before selecting the primitive:

- exact identifiers and authoritative attributes → keyed or relational query;
- literal terms, phrases, symbols, and rare names → lexical retrieval;
- paraphrases and conceptually related passages → dense retrieval;
- typed paths and variable-depth relationships → graph query;
- mixed evidence needs → planned hybrid retrieval.

The host should derive structured scope from authenticated task state. A model may propose search terms, but it must not invent tenant filters or replace an authoritative lookup with a broad search.

## Lexical Ranking Is Not Exact Matching

BM25 ranks documents using term frequency, document frequency, and length normalization. It is effective for rare identifiers, domain vocabulary, quoted phrases, and terms whose spelling matters. An inverted index also supports filters and fielded queries.

BM25 is still a ranking function, not an exact database lookup. Analysis can lowercase, stem, split, or expand terms; top-ranked documents need not contain the exact raw string. Use keyword fields, phrase queries, or structured keys when exactness is required.

The claim that lexical search “understands” neither synonyms nor domain terms is also too broad. Behavior depends on analyzers, query expansion, fields, and corpus statistics. Test the configured system rather than reasoning from the label BM25.

## Relational Retrieval Carries Authority

User tier, current order state, granted capabilities, and workflow commit status belong behind typed, scoped queries to authoritative state. Select only fields needed for the task and preserve version or effective time:

```sql
SELECT tier, effective_at, version
FROM account_entitlement
WHERE tenant_id = $1
  AND account_id = $2
  AND effective_at <= $3
ORDER BY effective_at DESC
LIMIT 1;
```

Parameterization, row-level policy, transaction isolation, and authorization determine whether this result is safe to use. A vector index over entitlement documentation cannot substitute for the current account record.

## Combine Only When the Task Requires It

A support query may use relational lookup for product version, lexical search for an error code, and dense retrieval for symptom descriptions. Apply authorization and metadata constraints before candidate generation where the backend permits it. Keep each result's source, score semantics, and retrieval version; scores from different systems are not directly comparable.

Evaluate lexical retrieval with judged queries containing rare terms, phrases, misspellings, identifier variants, and negation. Evaluate relational retrieval with wrong-tenant, missing, stale, concurrent, and superseded records. Reliability begins by sending each question to a primitive whose failure semantics match the task.
