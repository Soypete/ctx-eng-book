# ch09.02 Vector and Semantic Retrieval

## Dense Retrieval Is Candidate Generation

Dense retrieval maps queries and content into a learned representation and ranks by proximity under a chosen similarity function. It is useful when relevant passages use different wording from the request. It does not establish truth, authority, completeness, or permission.

Its output is a set of semantic candidates for downstream verification and
selection. The representation can preserve useful conceptual similarity while
still losing a required identifier, relationship, scope restriction, or
effective date. Treat those dimensions as explicit metadata or authoritative
lookups rather than assumptions hidden in the embedding.

Treat the embedding model, preprocessing, chunking, distance function, index parameters, and corpus snapshot as one versioned retrieval system. Changing any component can change rankings and requires regression evaluation.

## Chunk Around Evidence Boundaries

Embedding an entire manual can bury the applicable procedure; splitting every sentence can remove prerequisites and exceptions. Chunk around meaningful units such as a policy clause, troubleshooting step group, function, or section, and preserve document ID, location, hierarchy, and neighboring links.

Metadata should express constraints known before similarity ranking: tenant, document type, product version, validity interval, language, authority, and authorization scope. Do not place secrets or unrestricted ACL data in an index whose filtering boundary cannot enforce them.

## Separate Canonical Content from the Index

The vector index is a derived representation. Results should point to canonical content so the pipeline can fetch current text, verify access, and preserve provenance. Record ingestion time, source version, embedding version, and deletion state. Define how corrections and deletions propagate and how the index is rebuilt.

Approximate nearest-neighbor search trades retrieval accuracy for latency and memory. Tune it with a judged workload, not defaults. Measure candidate recall, latency percentiles, stale-result rate, unauthorized-candidate rate, and downstream answer support.

## Design from Queries Backward

Start with representative information needs and required filters. Decide the evidence unit and source authority, then chunk, attach metadata, choose an embedding model, and configure the index. Compare against lexical and simple structured baselines. Dense retrieval earns its place when it recovers relevant paraphrased evidence that simpler methods miss at acceptable cost.

A “knowledge store” is useful only as a named interface for these lifecycle
and query contracts. The label does not create semantic correctness or source
authority. The next module combines dense candidates with lexical candidates
and explicit graph paths.
