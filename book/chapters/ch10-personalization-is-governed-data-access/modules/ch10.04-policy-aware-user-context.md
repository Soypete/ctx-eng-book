# ch10.04 Policy-Aware User Context

## Access Is Not Permission for Every Use

A system may be allowed to read a user's address to resolve a shipment and still be prohibited from using it to infer household income, target marketing, or retain a profile. Policy-aware context carries purpose and permitted interpretation alongside access.

Before retrieving personal state, bind the authenticated principal, represented user, tenant, purpose, requested operation, jurisdiction where relevant, consent or policy basis, retention class, and policy version. Do not let the model supply trusted values for those fields.

A purchasing agent makes the distinction concrete. Giving the agent a credit card or purchasing token supplies a credential, not a usable authorization contract. The governed context might instead be represented as:

```yaml
principal: miriah
purpose: conference_supplies
merchant_categories:
  - office
  - event
max_transaction_usd: 500
max_total_usd: 2000
expires_after: PT8H
requires_confirmation_above_usd: 250
```

This object is a proposal for delegated authority, not authority merely because it appears in context. A trusted policy decision point must derive or validate it, and the payment boundary must enforce the merchant, amount, cumulative total, expiration, and approval state. The model may propose a purchase inside that envelope; it may not widen the envelope.

## Compile Policy into Store-Specific Enforcement

A single canonical ABAC layer is not always possible or desirable. Define a common decision contract, then compile or delegate enforcement to mechanisms that can uphold it: page permissions, row policies, filtered indexes, relationship policy, API scopes, and tool-side checks.

ABAC is relevant to context engineering because it structures subject, resource, action, and environment facts so authority can be evaluated deterministically. It is not the only policy model, and those attributes must come from trusted sources rather than model inference.

Adapters should report whether a requested restriction was enforced, unsupported, or failed. “Unsupported” is not permission. The assembler can choose an eligible source, narrow the task, or stop.

## Govern Inference and Persistence

Personalization often derives new state: preference summaries, segments, inferred relationships, risk scores, or recommended actions. Each derivation needs a permitted purpose, source lineage, authority label, expiration, correction path, and rules for reuse. A model inference should not silently become an authoritative profile field.

Minimize active context and durable retention separately. A field may be permitted for one invocation but not for memory. Conversely, a durable account preference may not be necessary for this task. Propagate deletion and consent changes into caches, indexes, summaries, and evaluation datasets.

## Test Policy Transitions

Test consent granted then revoked, a user moving tenants, purpose changing from support to marketing, an inferred preference contradicted by an explicit setting, a cached context after logout, and a derived artifact whose parent expires.

Measure purpose mismatch, unauthorized inclusion, unsupported-enforcement stops, minimization violations, derived-state promotion, revocation latency, and deletion completion. The reliable system can answer not only “was this user allowed to read it?” but “was this use, inference, retention, and disclosure permitted here?”
