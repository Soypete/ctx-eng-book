# ch10.01 Personalization as Governed Retrieval

## Personalization Is a Data-Access Decision

Personalization selects user- or account-specific state for a response, classification, recommendation, workflow, or action. That makes it a governed data-access problem before it is a generation problem, and it applies beyond agents to any language system that uses context about a person or account. “Memory” is a convenient user-facing metaphor for some of that state; it is not an authorization model. A prompt saying “only use data this user may see” cannot prevent an over-broad query from returning another tenant's records.

In the book's spine, personalization starts with the **Lexicon**: identify the
user, account, source, authority, freshness, and sensitivity of candidate
state. **Semantics** distinguishes an explicit preference from an inferred
one, and a current relationship from a stale or ambiguous one. **Pragmatics**
decides whether that state may be disclosed, used for the declared purpose,
or allowed to influence an action.

The system must bind every request to an authenticated principal, acting agent, tenant, purpose, action, and resource scope. The model may interpret a user's intent; it must not establish identity or grant itself access.

## Separate Decision from Enforcement

Authorization may be decided by a policy service, database policy, application code, or another trusted decision point. It must be enforced at every relevant query and action boundary. “Authorization belongs at the storage layer” is too narrow when APIs, search indexes, caches, graphs, and tools also expose data.

A retrieval request can carry a structured envelope:

```json
{
  "principal": "user:184",
  "actor": "agent:support",
  "tenant": "acme",
  "purpose": "resolve_support_case",
  "action": "read",
  "resource_type": "account_preference",
  "request_id": "req-91"
}
```

The host derives this envelope from authenticated state and task policy, not model-generated arguments.

## ABAC Is One Policy Model

Attribute-based access control evaluates subject, resource, action, and often environment attributes. It can express purpose, tenant, classification, time, and relationship conditions that coarse roles do not. It also creates attribute-quality, policy-complexity, and explainability costs.

RBAC, relationship-based policy, capabilities, and combinations may be more appropriate for a given boundary. Chapter 11 covers least-privilege capabilities. Chapter 10's responsibility is narrower: whatever model is chosen, retrieval adapters must carry trusted identity and enforce the decision before returning context.

## Personal Data Needs More Than Read Permission

Access does not imply every use is permitted. User context may have consent, retention, purpose, jurisdiction, correction, deletion, and inference restrictions. A support agent permitted to read an address for shipment resolution may not persist an inferred household relationship for marketing.

Record the purpose and policy version with the retrieval. Minimize fields, expire context artifacts, and prevent derived state from escaping the source restriction. Test cross-tenant identity, confused-deputy requests, changed consent, purpose mismatch, revoked access, and cached results after logout.

Reliable personalization means the system can explain whose data was used, for which permitted purpose, what it meant, under which policy, and where that decision was enforced. The next module applies this contract across heterogeneous stores.
