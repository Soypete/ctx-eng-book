# ch10.00 Guardrails and Ontology-Based Validation

## A Guardrail Needs an Enforcement Point

“Add guardrails” is not an architecture. A production system must state what condition is checked, where it is enforced, what evidence the check uses, and what happens when it fails.

Engineered context can give a model better evidence. It cannot guarantee a supported answer or safe action. Validation narrows recognized structure and policy permits or denies effects. Neither makes every generated claim true.

## Place Checks at the Boundary They Protect

- **Input boundary:** authenticate the principal; validate request shape, referenced entities, and task scope.
- **Retrieval boundary:** authorize candidate generation and hydration before content becomes model-visible.
- **Model-output boundary:** parse typed output and validate schema, references, quantities, modality, and required evidence.
- **Execution boundary:** re-authorize the exact action and resource; enforce business invariants, confirmation, idempotency, and version checks.
- **Postcondition boundary:** verify committed state and record audit evidence.

Post-generation filtering alone is insufficient. Sensitive context may already have reached the model, and an invalid tool proposal must be stopped before side effects—not cleaned up in prose afterward.

## Ontologies Describe; Shapes and Policy Validate

An ontology provides vocabulary and entailment semantics. A knowledge graph contains assertions. Neither is automatically a closed-world validator. As Chapter 8 established, RDFS/OWL domain and range semantics may infer types rather than reject records.

Operational checks may use JSON Schema, database constraints, application invariants, SHACL shapes, policy decisions, or ontology-aware query validation. Select the mechanism whose semantics match the requirement. A graph query can confirm that a known relationship exists in a versioned dataset; it cannot prove that the dataset is complete or the source assertion is true.

For an expense action, useful checks include:

```text
request schema valid
  -> employee and report identities resolved
  -> principal may read report
  -> policy version is current
  -> amount and category satisfy policy
  -> required approval exists
  -> proposed payment re-authorized at commit
```

The model may propose fields. The host owns every transition.

## Failure Is Part of the Contract

Each validator needs explicit outcomes: reject, request clarification, retrieve missing evidence, route to review, degrade to a non-actionable answer, or stop. Automatic “repair” is safe only when the repaired value can be validated and does not broaden authority or change user intent.

Log policy and schema versions, decision inputs after appropriate redaction, result codes, evidence identifiers, and the final action. Test malformed output, unknown entities, stale policies, contradictory facts, unauthorized paths, numeric boundary cases, prompt-injected instructions, and validator outages.

Measure rejection precision, unsafe escape rate, false rejection, clarification success, policy-decision latency, and postcondition failures. The reliability question is not how many guardrails exist. It is whether every consequential boundary rejects the failures it was designed to contain.

The remaining modules apply this principle to governed personalization, scoped retrieval, provenance, and user-context policy.
