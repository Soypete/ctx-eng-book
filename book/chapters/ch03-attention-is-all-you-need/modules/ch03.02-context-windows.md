# Context Windows and Positional Limits

## Position Encoding Preserves Order

Without position encoding, attention would treat tokens as a bag of words—it would know what tokens exist but not their order. "The dog bit the man" and "the man bit the dog" would be semantically equivalent, which is obviously wrong.

The original transformer used sinusoidal positional encodings, while later model families use learned positions, rotary position embeddings, relative-position methods, or other variants. These mechanisms make order available to the network. They do not themselves establish that recent information is more important or that cause precedes effect.

Models can use information unevenly across a long input. On multi-document question answering and key-value retrieval, Liu et al. found task- and model-dependent performance differences based on where relevant information appeared, often favoring the beginning or end [Liu et al., 2024](https://aclanthology.org/2024.tacl-1.9/). That result should not be reduced to a universal recency bias caused by positional encoding or generalized beyond the evaluated settings without testing.

Poor ordering can degrade generation even when retrieval found the right
passage. The remedy is empirical: test placement policies such as evidence
before instructions, instructions after evidence, summaries before detail,
and repeated task statements. These are syntactic presentation choices; they
do not replace semantic structure or pragmatic enforcement. Do not infer a
universal ordering rule from one model family.

## A Context Window Is Invocation-Scoped Input

The advertised context window is the maximum token budget a model interface
accepts for an invocation, with input and generated output accounted for
according to the interface's rules. Text outside the submitted input cannot
influence that invocation unless the system retrieves or reconstructs it.

Window sizes change quickly and advertised capacity is not the same as
effective task utilization. This book intentionally avoids a capacity table;
deployment documentation and the specific workload near its limit are the
appropriate sources for that operational decision.

The useful mental model is an invocation-scoped working set, not a memory
store. Attention does not read it as a simple linear tape, but the sequence is
bounded and ordered. The model cannot query a previous conversation or
document unless the application includes it in the input or exposes a tool
that can retrieve it. The application should make that working set inspectable
through a context manifest: the sources and entities included, their
provenance and authority, applicable versions and timestamps, policy or
authorization scope, serialization choices, and what was omitted or deferred.

Everything required for one model decision must fit in that invocation's
available input budget or be reachable through a tool during the workflow.
When the assembled input exceeds the budget, the system—not an implicit
tokenizer truncation policy—should decide what to reject, retrieve at finer
granularity, summarize with provenance, or defer to another step. Record that
decision in the context manifest so a later reviewer can distinguish missing
lexicon, changed semantics, and a pragmatic scope decision from a model error.

## Why Context Is Expensive

Context costs money and latency. Understanding why helps you make better engineering decisions.

**For metered APIs:**
- Pricing commonly accounts for input and output tokens, sometimes with caching or tier-specific rules.
- More submitted context increases input work, but current dollar examples become stale quickly and belong in a dated calculation rather than timeless prose.

**For self-hosted models:**
- Time to first token (TTFT) scales with context length. The model has to process all those tokens before generating anything.
- KV cache memory grows with context. A 128K context window needs gigabytes of GPU memory just to store the attention keys and values.
- Throughput drops as context grows. Same GPU, more work, fewer requests per second.

The practical question isn't just "what fits in the window" but "what's the right signal-to-cost ratio?" Adding more context always increases computation. It only sometimes increases quality. If your retrieved documents are irrelevant, adding them just adds noise and cost.

## Sequence Position Is Not Event Time

Position is a property of the serialized input. Temporal context is a
property of the information being represented and the workflow using it:
event time, source time, retrieval time, version time, and authorization
validity can all differ. Putting a recent-looking record later in the input
does not make it newer, and putting an old record first does not make it
authoritative. Preserve relevant timestamps, effective intervals, versions,
and freshness decisions in the context manifest; let the semantic and policy
layers determine which time relation matters for the task.

The operational question is not “how much can I fit?” It is “what minimum
governed working set preserves task success under latency and cost budgets?”
Track submitted tokens, context-manifest decisions, time to first token,
end-to-end latency, retrieval recall, source recovery, and task outcome
together. The next module examines what happens when the working set must be
compacted.
