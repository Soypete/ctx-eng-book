# Context Windows and Positional Limits

## Argument
The context window is an invocation-scoped token budget, not persistent memory. Position affects model utilization, but current evidence does not justify a universal recency-bias explanation.

## Why it matters (reliability goal)
Tie to Pragmatics pillar: the reliability question "what information can the model actually see?" depends entirely on context window mechanics. Understanding position encoding and window limits is prerequisite to any context engineering.

## Beats

1. **Position Encoding Preserves Order** — evidence: existing prose + research/attention-is-all-you-need-notes.md
   - Without position encoding, "the dog bit the man" = "the man bit the dog"
   - The original transformer used sinusoidal encodings; later models use several position methods
   - Long-context utilization varies by model, task, content, and placement

2. **Context Windows Are Fixed Memory** — evidence: existing prose
   - Vendor window sizes require dated official citations
   - Think of it as an invocation working set, not a linearly read tape
   - Prior state must be included or retrieved through a tool

3. **Why Context Is Expensive** — evidence: existing prose, ledger (context cost of composition)
   - API: per-token pricing, input + output billed
   - Self-hosted: TTFT scales with context, KV cache needs GB of GPU memory, throughput drops
   - The question isn't "what fits" but "what's the right signal-to-cost ratio?"

4. **Order Matters for Attention Weights** — evidence: existing prose
   - Poorly ordered context degrades even correct information
   - Definition before example, summary before detail—attention needs logical flow
   - The model reasons about sequence

## Conclusion to reach
The reader should understand that context windows are hard limits, not flexible memory. What doesn't fit gets dropped. What gets dropped determines what the model can see. Position affects attention distribution, and cost scales with every token.
