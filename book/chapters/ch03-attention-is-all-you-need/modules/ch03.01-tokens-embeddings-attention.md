# Tokens, Embeddings, and Attention

## What the Model Actually Sees

When you send text to a language model, the model's tokenizer converts it into token IDs. An embedding table maps those IDs to vectors, positional information is added or applied, and successive transformer layers compute contextual representations. Attention is one mechanism in that computation, not a separate relevance service bolted onto the prompt.

The reliability question for any AI system is simple: **What information can the model actually see?**

The answer matters more than most engineers realize. If you can't answer this question precisely, you can't debug why your system failed. You can't optimize for cost. You can't reason about what the model will get right versus what it'll miss. Everything depends on understanding what's in the context window and how attention distributes across it.

## Tokens Are Not Words

The first thing to internalize: tokens are not words. They're subword units that the model has learned to recognize based on statistical patterns in training data.

A token might represent:
- A complete word ("the")
- A common suffix ("ing", "tion")
- A rare word broken into pieces ("unhappiness" → "un", "happ", "iness")

Tokenization varies across models, so the same sentence can produce different token counts across model families. What counts as one token depends on the tokenizer, and this affects:
- Context window limits (measured in tokens, not words)
- Pricing (billed per token)
- Where sentence boundaries fall for retrieval

When you build a context pipeline, count with the tokenizer used by the target model rather than converting from words with a fixed ratio. Source language, code, punctuation, and tokenizer vocabulary can change that ratio substantially.

## Embeddings Represent Tokens and Text

Once text is tokenized, each token ID maps to a learned input embedding. Transformer layers then produce contextual representations: the representation of a token changes with the sequence around it. These internal representations are related to, but not interchangeable with, the document embeddings commonly used by retrieval systems.

Embedding spaces can encode useful statistical relationships, but “nearby” depends on which representation, layer, model, pooling method, and similarity measure you inspect. A retrieval embedding compresses a passage into a vector optimized for a retrieval objective; it is not simply the model's token embedding copied into a vector index.

An embedding has a fixed dimensionality for a given model and interface, but those dimensions rarely correspond to human-readable fields. Similarity is a learned proxy for relevance. It is not evidence that two records are identical, authorized, current, or suitable for the same action.

This is why retrieval can fail in counterintuitive ways. A passage may be semantically related but wrong for an exact identifier lookup, or lexically different yet operationally relevant. Diagnose this at the retrieval boundary with labeled queries and recall measurements rather than explaining every miss as a vague failure of model “understanding.”

## Attention Finds Relevance

Attention lets a position combine information from other positions permitted by the model's attention mask. In an autoregressive model, a token ordinarily cannot attend to future tokens. Different heads and layers learn different patterns, so there is no single attention score that explains the model's decision.

At a high level, the model derives queries, keys, and values from its current representations. Similarity between a query and permitted keys produces normalized weights used to combine values. This is a useful mechanism-level description, but attention weights alone should not be treated as a faithful explanation of why an output occurred.

The systems insight is that information absent from the model input cannot influence that invocation, while information present may influence it in ways the application does not control directly. Providers can encode roles and masks, and training can teach instruction hierarchies, but none of that turns retrieved text into trusted data or guarantees that the intended instruction wins.

This is why order and composition matter, but “every irrelevant token dilutes attention” is too mechanical. Long or distracting context can degrade performance empirically; the effect depends on model, task, placement, and content. Measure the change with controlled context-ablation tests rather than using token count as a proxy for relevance.

Liu et al. tested multi-document question answering and key-value retrieval across varying context lengths and relevant-information positions. They found that performance often changed substantially with position, commonly performing best when relevant information appeared near the beginning or end and worse in the middle [Liu et al., 2024](https://aclanthology.org/2024.tacl-1.9/). This supports position-sensitive utilization on those tasks; it does not establish that every irrelevant token degrades every model.

Vaswani et al. establish the transformer attention architecture [Vaswani et al., 2017](https://arxiv.org/abs/1706.03762). The distinction this book draws is an engineering inference: attention transforms information already supplied to the model; context engineering decides which information and authority reach the invocation in the first place.

For an agent, that produces a concrete debugging sequence: record the exact serialized input, count it with the target tokenizer, trace where each retrieved passage came from, remove one context source at a time, and compare task outcomes.
