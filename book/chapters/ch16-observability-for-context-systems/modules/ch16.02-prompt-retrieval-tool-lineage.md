# Input, Transformation, and Effect Lineage

A trace says that operations occurred. Lineage explains which versioned inputs became which outputs. Reliable diagnosis needs both, because a fast retrieval span does not reveal whether its result was stale, unauthorized, excluded, semantically transformed, or altered before the model saw it. Lineage should connect Lexicon sources and authority to semantic representations, pragmatic decisions, model inputs, and outcomes.

## Prompt and Context Lineage

Store the template identifier and version, rendering code version, model and tokenizer version, parameter configuration, instruction layers, demonstration identifiers, context-manifest identifier, and a digest of the rendered request. Record the ordered model input by role, including source authority, semantic representation versions, policy or scope decisions, and any transformations such as filtering, translation, summarization, or compaction. Dynamic values should point to governed source records rather than being copied into an unrestricted trace.

Prompt lineage alone is incomplete. The same template can render different context under different identity, purpose, policy, time, retrieval, or compaction decisions. Record the ordered manifest of admitted items and their roles. If exact replay is required, preserve protected snapshots or immutable references under the source data’s retention rules.

A digest can verify that two captured payloads match; it cannot reconstruct content, prove semantic equivalence, or make sensitive low-entropy values safe from guessing. Treat lineage references as protected metadata.

## Retrieval Lineage

For each retrieval route, capture:

- query or query-reference identifier and transformation version;
- source, index, embedding, schema, and policy versions;
- identity, purpose, and authorization-decision references;
- candidates, scores, filters, reranking, and exclusion reasons;
- canonical record versions and freshness timestamps; and
- which passages were admitted, compacted, or dropped under the context budget.

For each semantic transformation, capture the input and output record references, transformation type and version, entity or relationship decisions, uncertainty or loss indicators, and the policy or purpose under which it ran. For each pragmatic decision, capture the task, actor, intended effect, applicable policy version, decision, and reason code. These records let an investigator distinguish a source problem from a meaning problem or a policy problem.

Keep candidate generation separate from final admission. This distinguishes “not found,” “found but unauthorized,” “ranked below cutoff,” “stale,” and “removed by budget.” Those outcomes imply different fixes and different reliability risks.

## Tool Lineage

Tool lineage begins with a model proposal and ends with a classified effect:

```text
proposal -> schema validation -> authorization -> dispatch
         -> provider receipt -> observation -> state transition
```

Record tool/schema version, validated argument digest or protected reference, authorization result, idempotency key, attempt number, timeout and retry classification, provider receipt, redacted result reference, and resulting workflow version. Distinguish proposed, denied, dispatched, ambiguous, succeeded, compensated, and failed. Otherwise a trace can imply that an effect occurred merely because the model requested it.

Lineage enables counterfactual evaluation: rerun a new ranker against captured candidates, render a new prompt against the same manifest, or test a new validator against historical proposals. Keep diagnostic replays isolated from live side effects and mark their outputs as derived evaluation data.

Lineage improves reliability when it lets an engineer locate and reproduce a boundary failure from source authority through meaning, model input, policy decision, and outcome. It is not useful merely because every object has an identifier. Test it with incident drills: select a bad outcome and verify that an authorized investigator can reconstruct the relevant versions and decisions within the required time.
