# Tracing Context Assembly

When an agent produces a bad result, “why did the model do that?” is usually too ambitious. A trace cannot expose a faithful internal causal explanation. It can answer the operational questions that engineers can act on: what request and authority entered the system, which context was eligible and selected, what the model was sent, which actions were proposed and allowed, what observations returned, and which versions produced the outcome.

Observability makes a run reconstructable enough to diagnose system boundaries. It does not make a probabilistic model transparent.

## Trace the Context Pipeline

A useful run trace begins at the accepted task and follows context planning, retrieval, assembly, model calls, tool validation and execution, durable transitions, and the terminal outcome.

```text
run
├── authorize and plan context
├── retrieve candidates
│   ├── relational lookup
│   └── semantic search
├── assemble admitted context
├── invoke model
├── validate proposed tool action
├── execute tool
└── validate and commit outcome
```

Each operation records a stable run identifier, start and end times, status, version references, and outcome classification. Parent-child spans express nested work; span links can connect queued, retried, or fan-out work whose causal relationship does not fit one call stack. Propagate trace context across process boundaries using a documented format such as the [W3C Trace Context Recommendation](https://www.w3.org/TR/trace-context/).

Instrument decisions at the point trusted software makes them. A model span may contain the proposed operation, but the authorization span records whether the exact operation was allowed. A retrieval span records candidates; the assembly span records which evidence was actually admitted. This distinction prevents a trace from collapsing proposals and effects into one misleading event.

## Use OpenTelemetry as Transport, Not the Data Model

The [OpenTelemetry specification](https://opentelemetry.io/docs/specs/otel/) defines APIs and data models for traces, metrics, and logs, including spans, context propagation, events, attributes, and links. It provides interoperable telemetry plumbing. It does not define the book’s context manifest, authorization semantics, or causal explanation.

Adopt stable semantic conventions where they fit and version application-specific attributes. OpenTelemetry semantic conventions are themselves versioned and have varying stability, so dashboards and analysis code must record the schema they expect. Keep domain records—evidence manifests, tool receipts, policy decisions, and workflow events—in durable systems of record and link them from telemetry.

## Do Not Put the Database in the Trace

Full prompts, retrieved documents, tool arguments, outputs, credentials, and user text may contain secrets or regulated data. Recording everything can create a second, weakly governed copy of production state. Prefer identifiers, versions, hashes, counts, classifications, and access-controlled references. Capture content only under an explicit policy with redaction, encryption, retention, regional placement, access logging, and deletion propagation.

Sampling also changes what can be claimed. Head sampling can drop a failure before its outcome is known; tail sampling can retain failures but requires buffering and still needs a policy. Metrics provide aggregate coverage while exemplars or retained traces support diagnosis. Record sampling decisions so “no trace found” is not mistaken for “event did not occur.”

## Debug With Competing Hypotheses

If an answer omits a relevant policy, inspect the trace in order:

1. Was the policy source eligible under identity and purpose?
2. Did retrieval return the correct version?
3. Did ranking and budget selection admit it?
4. Was it preserved in the final model input?
5. Did the output cite or contradict it?
6. Did validation catch the contradiction?

The trace narrows the failing boundary. To test whether the model could use the policy, run a controlled replay with captured observations or an evaluation fixture. Observability supplies evidence for the experiment; the experiment supports the diagnosis.
