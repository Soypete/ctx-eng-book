# Tracing the Context-to-Outcome Pipeline

When a language system produces a bad result, “why did the model do that?” is usually too ambitious. A trace cannot expose a faithful internal causal explanation. It can answer the operational questions that engineers can act on: what request and authority entered the system, which Lexicon sources were eligible and authoritative, how their meaning was transformed, what the model was sent, which pragmatic decisions and policy checks were made, what observations returned, and which versions produced the outcome.

Observability makes a context-to-outcome run reconstructable enough to diagnose system boundaries. It does not make a probabilistic model transparent.

Jessica Talisman's [Ontology Pipeline](https://jessicatalisman.substack.com/p/the-ontology-pipeline) provides a useful adjacent model for the staged construction of semantic knowledge infrastructure: controlled vocabulary, metadata, taxonomy, thesaurus, ontology, and knowledge graph. This chapter takes that insight beyond ontology construction and asks how the broader context engineering discipline observes, versions, authorizes, evaluates, and operates the full pipeline from source data to language-system outcome. Those stages are semantic infrastructure; they do not replace the Lexicon and Pragmatics boundaries that determine which data may enter a task and what may happen afterward.

## Trace the Context Pipeline

A useful run trace begins at the accepted task and follows authority and context planning, retrieval, semantic transformation, assembly, model calls, pragmatic validation, execution where applicable, durable transitions, and the terminal outcome. The model is one participant in this pipeline; the same shape applies to search, extraction, classification, summarization, recommendation, and workflow automation.

```text
run
├── authorize and plan context
├── retrieve candidates
│   ├── relational lookup
│   └── semantic search
├── resolve and transform meaning
├── assemble admitted context
├── invoke model
├── validate output and policy
├── execute approved effect (if any)
└── validate and commit outcome
```

Each operation records a stable run identifier, start and end times, status, version references, and outcome classification. The trace should make three questions queryable at every boundary: which source or entity was used (Lexicon), what interpretation or representation was applied (Semantics), and what purpose, actor, and constraint governed the decision (Pragmatics). Parent-child spans express nested work; span links can connect queued, retried, or fan-out work whose causal relationship does not fit one call stack. Propagate trace context across process boundaries using a documented format such as the [W3C Trace Context Recommendation](https://www.w3.org/TR/trace-context/).

Instrument decisions at the point trusted software makes them. A source record should expose authority, provenance, freshness, jurisdiction, and sensitivity references. A semantic transformation should identify the schema, ontology, entity-resolution, normalization, translation, summarization, or compaction version that changed the representation. A model span may contain a proposed answer or operation, but validation and policy spans record whether it satisfied the task and whether the exact operation was allowed. A retrieval span records candidates; the assembly span records which evidence was actually admitted. This distinction prevents a trace from collapsing sources, interpretations, proposals, and effects into one misleading event.

## Use OpenTelemetry as Plumbing, Not the Category

The [OpenTelemetry specification](https://opentelemetry.io/docs/specs/otel/) defines APIs and data models for traces, metrics, and logs, including spans, context propagation, events, attributes, and links. It provides interoperable telemetry plumbing. It is not the definition of observability for context systems and does not define the book’s source manifest, semantic transformations, authorization semantics, policy checks, or causal explanation.

Adopt stable semantic conventions where they fit and version application-specific attributes. OpenTelemetry semantic conventions are themselves versioned and have varying stability, so dashboards and analysis code must record the schema they expect. Keep domain records—evidence manifests, tool receipts, policy decisions, and workflow events—in durable systems of record and link them from telemetry.

## Do Not Put the Database in the Trace

Full prompts, retrieved documents, tool arguments, outputs, credentials, and user text may contain secrets or regulated data. Recording everything can create a second, weakly governed copy of production state. Prefer identifiers, versions, hashes, counts, classifications, and access-controlled references. Capture content only under an explicit policy with redaction, encryption, retention, regional placement, access logging, and deletion propagation.

Sampling also changes what can be claimed. Head sampling can drop a failure before its outcome is known; tail sampling can retain failures but requires buffering and still needs a policy. Metrics provide aggregate coverage while exemplars or retained traces support diagnosis. Record sampling decisions so “no trace found” is not mistaken for “event did not occur.”

## Debug With Competing Hypotheses

If a result omits a relevant policy, inspect the trace in order:

1. Was the authoritative policy source eligible under identity, purpose, and time?
2. Did retrieval return the correct source and version?
3. Did resolution or transformation preserve the relevant meaning?
4. Did ranking and budget selection admit it into the model input?
5. Did the output follow the task semantics and pragmatic constraints?
6. Did validation or policy enforcement catch a contradiction or unauthorized effect?

The trace narrows the failing boundary. To test whether the model could use the policy, run a controlled replay with captured observations or an evaluation fixture. Observability supplies evidence for the experiment; the experiment supports the diagnosis.
