# Retrieval and Tool Evaluation

End-to-end answer quality cannot tell you which system boundary improved. Evaluate retrieval and tools separately, then test their composition.

## Evaluate Retrieval in Stages

Define the retrieval unit—document, passage, assertion, entity, or path—and a bounded relevance set for each task. Measure candidate recall, judged precision, ranking metrics where order matters, authorization violations, freshness, latency, and cost. Then measure final admission: which required evidence entered the model context, which was excluded, and why.

Recall denominators are often incomplete. Pool candidates from multiple systems and human search, record unjudged items, and avoid presenting partial judgments as exhaustive truth. Relevance also does not imply authority or usefulness. Evaluate citation support and downstream decisions separately.

Run retrieval ablations against the same model inputs: oracle evidence, no retrieval, each route alone, hybrid routing, and the production policy. This separates retriever failure from reader failure and shows whether extra candidates earn their cost.

## Evaluate Tools as Contracts and Effects

Test schema validation, authorization, idempotency, deadlines, retry classification, ambiguous outcomes, and postconditions with deterministic fixtures and failure injection. Measure proposal validity, correct-tool selection when a tool is required, argument correctness, denied-action rate, duplicate effects, recovery success, and terminal task outcome.

A tool-selection score is insufficient if the chosen action is unauthorized or its effect is wrong. Use sandboxed or simulated providers for destructive tests, and verify that diagnostic replay cannot execute live effects.

The evaluation stack progresses from deterministic component tests, through workflow scenarios with controlled dependencies, to repeated behavioral evaluation and guarded production measurement. Each layer localizes a different class of failure; none replaces the others.
