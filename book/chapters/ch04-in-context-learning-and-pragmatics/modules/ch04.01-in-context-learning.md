## Ambiguity Creates Unmeasured Inference

In machine learning, *inference* usually means running a trained model to produce an output. In ordinary reasoning, it means reaching a conclusion from evidence. This chapter needs both concepts, so I will be explicit: the reliability problem is not inference itself. It is asking the model to resolve important ambiguity without exposing or evaluating the assumptions it chose.

Models do not share a user's lived situation. They receive whatever history, instructions, examples, state, and retrieved evidence the application supplies, plus patterns encoded during training.

An explicit goal object can remove one source of ambiguity by separating the desired outcome from the proposed method. It does not remove the need to plan, interpret evidence, or choose tools. The harness should validate required fields and ask for clarification rather than treating `/goal` as a magic directive.

The defensible insight is narrower: hidden, unconstrained inference makes failures harder to reproduce. Context engineering makes goals, assumptions, examples, evidence, and acceptance criteria inspectable. Brown et al. demonstrated strong few-shot behavior through text interaction at scale; that result does not establish a monotonic relationship between “more inference” and lower reliability [Brown et al., 2020](https://arxiv.org/abs/2005.14165).

## Static vs Dynamic Context (Teleprompter Pattern)

It is useful to distinguish context fixed before an invocation from context obtained during a workflow:

- **Invocation context:** Instructions, examples, and evidence assembled before a particular model call. It may be generated dynamically even though it is fixed during that call.
- **Workflow context:** Tool results, retrieved documents, events, and state obtained between calls as the workflow executes.

MCP is one protocol through which a host can expose tools and resources. It is not the definition of dynamic context, and the model does not fetch anything without a host, authorization policy, and execution loop.

Invocation context is reproducible only if the system records its exact serialization and versions every contributing artifact. Workflow retrieval introduces additional failure modes—timeouts, stale reads, authorization denial, and partial results—but is necessary for fresh or task-specific information. Keep invariants versioned; retrieve changing evidence at runtime; trace both.

## Prompt Tuning — Optimizing the Signal

Instructions and few-shot examples can be optimized against an evaluation set. In this chapter, *prompt optimization* means changing discrete instructions or examples. *Prompt tuning* can also refer to learned continuous parameters, which is a different training technique.

The key insight: **prompt performance is measurable**. Given a task and evaluation criteria, you can systematically improve the prompt. This is no different from tuning any other system parameter.

**What to tune:**
- Instruction wording — "Analyze the following" vs "Extract key insights from"
- Example selection — which few-shot examples produce the best results
- Order effects — do high-quality examples work better at the start or end
- Constraint framing — "never do X" vs "avoid doing X"

**What not to tune on:**
- Single examples — prompt performance has variance; test across diverse inputs
- One-off evaluations — prompts that work on one query may fail on others

## Domain Expansion — LLMs Adapt Without Retraining

One powerful capability of LLMs for information extraction: they can recognize novel entity types without retraining.

Many supervised NER systems are trained for fixed label sets, so changing the ontology may require new labels, rules, or training. A prompted LLM can attempt a newly described entity type without updating weights. That makes prototyping faster, but “describe it and the model extracts it” is not a reliability guarantee.

This is especially valuable for:
- **Multilingual extraction**: A multilingual model may reduce the number of language-specific pipelines, but quality must be evaluated per language and domain
- **Domain-specific entities**: Extract specialized concepts (medical, legal, scientific) by describing them in context
- **Rapid prototyping**: Test new entity types before investing in training data
