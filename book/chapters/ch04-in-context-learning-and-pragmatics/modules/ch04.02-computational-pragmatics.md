# ch04.02 Computational Pragmatics

Pragmatics is the question of what an actor is trying to accomplish with a
meaning, and what may appropriately follow from it. It is not a synonym for a
prompt, an instruction template, or an agent loop. Prompts, examples, schemas,
clarifying questions, policy checks, and workflow gates are techniques for
making pragmatic assumptions explicit and enforceable.

The chapter applies the **context engineering framework**. Lexicon supplies
the available sources, entities, and authorities. Semantics supplies the
meaning of those entities and their relationships. Pragmatics resolves the
purpose, referent, actor, and permissible consequence. Syntax—the wording or
serialization used to carry that context—is necessary for delivery, but a
well-formed instruction does not by itself establish meaning, scope, or
authorization.

## Speech Act Interpretation

Jurafsky's computational pragmatics identifies four inferential problems:
1. Reference resolution — what does "it" refer to?
2. Speech act interpretation — what did the user mean?
3. Discourse coherence — how does this relate to what was said?
4. Abduction — what explains this utterance?

One important failure mode is **speech-act interpretation**: the system has relevant information but has not established what action the user intends. The repository does not contain evidence that this is the most common AI failure.

Getting the intended action wrong can lead to an incorrect answer, extraction, classification, recommendation, workflow step, or tool call. Reference resolution, discourse coherence, and abductive assumptions can be equally important depending on the task. Jurafsky identifies reference resolution, speech-act interpretation, discourse structure and coherence, and abduction as four core inferential problems studied in computational pragmatics [Jurafsky, *Pragmatics and Computational Linguistics*](https://web.stanford.edu/~jurafsky/prag.pdf). The source establishes the taxonomy, not a ranking of production-agent failures.

ReAct interleaves reasoning traces with actions and observations [Yao et al., 2022](https://arxiv.org/abs/2210.03629). Chain-of-thought prompting elicits intermediate reasoning on some tasks [Wei et al., 2022](https://arxiv.org/abs/2201.11903). Planning interfaces can separate proposal from execution. These are optional computational patterns, not foundations of pragmatics, and none establishes the user's intent; a system that acts on “fix the API” without clarifying scope has merely structured its guess.

A user says “fix the API” but means “find the bug in the auth handler.” A safer harness identifies missing fields—target service, observed failure, allowed changes, and acceptance test—and asks or retrieves evidence before granting write authority. Reasoning text is not a substitute for that gate.

## What "Doing the Inference Work" Actually Looks Like

When model output was advisory, a wrong assumption often produced a bad answer. When output crosses an execution boundary, the same assumption can trigger unauthorized access, destructive changes, or unbounded cost. The difference is authority, not a new kind of inference.

DSPy provides abstractions and optimization methods for language-model programs [Khattab et al., 2023](https://arxiv.org/abs/2310.05914). It can serve as an optional example of optimizing an interface or program contract. Calling that “injecting pragmatics” is this book's interpretation, not the paper's terminology.

Users will remain vague because they are describing needs, not implementing workflow contracts. The product must decide when to clarify, when authenticated state resolves the reference, and when the safest response is to refuse action.

## Scope and Data Access — The Indexicality Problem

**What is indexicality?**

Indexical expressions such as “I,” “you,” “here,” “now,” and “this” depend on the utterance context: speaker, addressee, time, place, or demonstrated object. Jurafsky describes computational pragmatics as concerned with indexicality and with relations between utterances, action, discourse, place, time, and environment [Jurafsky, *Pragmatics and Computational Linguistics*](https://web.stanford.edu/~jurafsky/prag.pdf).

In context engineering: when a user says "the data," they may mean a
different dataset than another user. When they say "my files," the referent
depends on identity and scope. Without explicit scoping, the same phrase has
different referents.

The user's example: "analyze the past month's sales data and compare to other monthly reports" — but if you pull in marketing data instead of sales data, you get the wrong result. Not a hallucination — just **wrong scope**. This is unreliable behavior.

The deeper question: when you say "the data," which data? The same query means different things to different users in different contexts.

For any system resolving “my files”—a file search, summarizer, classifier, or
agent—resolution requires an authenticated principal and a policy-scoped
resource set. That is reference resolution joined to authorization; it does
not mean the underlying files change semantic meaning for each user.

The system might query marketing data instead of sales data—not a hallucination,
but wrong scope. Enforce the scope before retrieval, record how each indexical
reference was resolved, and test ambiguous requests for clarification rather
than silent guessing.
