# ch04.03 Examples, Instructions, and Structured Outputs

## Few-Shot as Teaching

Examples can demonstrate a task and output contract, but they do not program model actions in the deterministic sense. They influence a probabilistic output that the harness must still validate.

**A good few-shot example:** Represents a real input class, shows the expected output, and makes boundary cases or abstention behavior visible.

**A bad few-shot example:** Ambiguous, too complex, or shows wrong behavior that the model learns anyway.

Few-shot examples can teach labels, transformations, style, and boundary decisions. Avoid assuming they teach a faithful internal reasoning process. What matters operationally is whether the selected examples improve held-out task outcomes.

## Tool Formatting — How Models Choose Actions

Tool formatting is one bridge between intent and execution. When a model proposes a function call, it must identify a tool and produce arguments the host can parse. Formatting is one common failure boundary, alongside selection, authorization, execution, and result interpretation.

The problem: models are trained on text, not tool schemas. They need explicit instruction on:
- What tools exist and when to use each one
- The exact argument format each tool expects
- What a valid response looks like vs. what to skip

Tool formatting requires explicit instruction on what tools exist, when to use each one, the exact argument format, and what a valid response looks like.

**Tool formatting best practices:**
1. **Schema-first**: Define tools with JSON Schema or equivalent. The schema becomes part of the prompt.
2. **Discriminating examples**: Add examples where they clarify confusing tool boundaries or difficult arguments; do not spend context on one example per tool by default.
3. **Failure handling**: Tell the model what to do when a tool call fails — retry, fall back, or escalate.

When tool descriptions overlap or arguments are underspecified, the model may choose the wrong function or produce malformed arguments. Improve the interface, but retain a model-capability category: some models fail tool-use evaluations even with a clear schema.

## Structured Outputs — Reliability Through Schema

Structured outputs constrain model behavior to known shapes. Instead of free-form text, the model outputs JSON, XML, or typed objects that downstream systems can parse reliably.

**Why this matters for reliability:**
- **Parseable**: No regex extraction, no fragile string matching
- **Validated**: Schema violations fail fast, before they cause downstream errors
- **Auditable**: Every output has a known structure to inspect

Validation does not guarantee parseable output; it detects output that does not conform. Provider-enforced schemas or grammar-constrained decoding can guarantee syntactic membership in a supported language, but neither guarantees semantic correctness or safe values.

The pattern: constrain the output space. The more you specify what the output should look like, the more reliable the model behaves. This is why function calling was one of the earliest reliable agent patterns — it constrains output to a known schema.

**Structured output patterns:**
1. **Schema prompting**: Ask for JSON matching a schema, then treat conformance as untrusted until validated
2. **Grammar-based generation**: Use constrained decoding to only allow valid tokens
3. **Generate, parse, validate**: Parse the response, validate fields and invariants, then reject, repair through bounded retry, or escalate

## The Reliability Question — How Do We Communicate Intent Clearly?

This chapter started with a question: **how do we communicate intent clearly to the model?**

The answer, through the lens of in-context learning and pragmatics:

1. **Expose important assumptions**: State the outcome, scope, permissions, and acceptance criteria. Ask for clarification when required fields are missing.

2. **Scope the data**: Address indexicality directly. "The data" means nothing — "the sales data from the past 30 days for account A" means something precise.

3. **Use representative examples**: Demonstrate difficult boundaries and abstention behavior, then evaluate on held-out cases.

4. **Separate versioned invariants from runtime evidence**: Record the exact invocation context and trace every workflow retrieval, regardless of protocol.

5. **Constrain outputs**: Tool formatting and structured outputs reduce the model's output space to what your system can reliably parse.

6. **Measure and tune**: Prompt performance is observable and optimizable. Treat prompts as parameters to tune, not magic incantations.

### Measuring Extraction Performance

When extracting structured data (entities, relationships, tool calls), the same metrics from information extraction apply [IE NER evaluation](research/knowledge-graphs/ie-ner.md):

- **Precision** = #correct / (#correct + #incorrect) — measures correctness
- **Recall** = true positives / (true positives + false negatives) — measures completeness against labeled relevant items
- **F1** = 2 × Precision × Recall / (Precision + Recall) — balanced measure

For extraction tasks, you can also measure:
- **Slot Error Rate (SER)** depends on the task's insertion, deletion, and substitution convention; define the exact formula used by the evaluation rather than treating one shorthand as universal.

These metrics let you compare prompt variations on a labeled set. A prompt with higher precision and recall on representative held-out examples is better on those metrics. Whether it is better for the product still depends on class weighting, error cost, latency, authorization, and abstention behavior.

Context engineering makes important ambiguity and system boundaries explicit. The reliability loop is: define the contract, assemble context, validate syntax and semantics, enforce authority, and measure task outcomes.

## A Note on Harnesses

This framework is fairly reliable assuming the harness handles the tools well. If the harness can't parse the model's output, context engineering fails at execution time. For example: some models output XML by default, while the harness expects JSON. The model did everything right — but the tool call fails.

Reliable execution requires matching the model interface to what the harness can parse, then testing malformed, semantically invalid, unauthorized, and tool-error cases. A schema-valid call is the beginning of execution validation, not the end.
