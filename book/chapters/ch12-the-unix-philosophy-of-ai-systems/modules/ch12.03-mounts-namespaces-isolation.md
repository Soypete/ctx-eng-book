# ch12.03 Mounts, Namespaces, and Isolation

## A Context Namespace Has Three Boundaries

A namespace is useful when it makes the context available to a task explicit,
but its value is governed rather than merely visual:

- **Lexicon:** the namespace lists eligible sources and entities, with
  ownership, provenance, freshness, and jurisdiction.
- **Semantics:** paths and mount entries identify typed views, operations,
  relationships, and consistency guarantees; a path is not meaning by itself.
- **Pragmatics:** the authenticated task, actor, purpose, and policy determine
  what may be read, written, invoked, or promoted to an external effect.

These are logical context boundaries. Operating-system mechanisms may help
enforce them, but they do not define the book's thesis or replace backend
authorization.

## A Namespace Is Not Isolation by Itself

A logical context namespace can organize eligible sources:

```text
/task/       validated task state
/session/    bounded interaction state
/evidence/   authorized retrieved items
/tools/      tool descriptions, not credentials
/output/     proposed and accepted artifacts
/scratch/    disposable working files
```

Paths make ownership and lifecycle visible. They do not enforce tenant isolation unless every resolver and backend binds the path to trusted identity and policy. A string prefix such as `/tenant/acme` is not a security boundary.

## Use Real Isolation for Untrusted Execution

When a language system executes code or tools, use mechanisms appropriate to
the threat model: separate processes, containers or sandboxes, filesystem and
user namespaces, network policy, syscall controls, resource limits, and
distinct credentials. These are general infrastructure controls with
different guarantees and escape risks; “workspace isolation” should name
which are active.

Bind tenant and task identity outside model control. Deny undeclared network destinations, mount only required resources, use read-only views where possible, and prevent traversal through symbolic links or alternate paths. Backend authorization from Chapters 10–11 remains necessary even inside a sandbox.

## Contain Resources and Side Effects

Set CPU, memory, wall-time, process, storage, output, and tool-call limits. Capture stdout, stderr, exit status, and committed effects as typed observations. A tool crash can still exhaust shared pools or corrupt external state; process separation contains only resources actually isolated.

The common model/tool loop is not equivalent to `fork`/`exec`. It is a workflow that needs durable state, idempotency, and supervision—Chapter 13's subject. Use the process analogy only for containment and lifecycle, not as an implementation claim.

## Test the Boundary, Not the Diagram

Attempt cross-tenant path traversal, symlink escape, undeclared network access, fork bombs, disk exhaustion, oversized output, stale mounts, shared-cache leakage, and writes through read-only adapters. Kill the worker mid-operation and verify cleanup and external-state recovery.

Measure escape attempts, policy denials, resource-limit terminations, leaked mounts, cleanup time, noisy-neighbor impact, and unreconciled side effects. Isolation improves reliability when failure and compromise remain within tested boundaries.
