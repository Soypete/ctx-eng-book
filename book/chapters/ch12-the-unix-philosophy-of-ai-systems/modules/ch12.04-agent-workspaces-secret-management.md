# ch12.04 Agent Workspaces and Secret Management

## Build a Workspace for One Task

A workspace is a bounded view of state and capabilities for one execution. It should be disposable where possible and reconstructable from durable workflow state.

```text
/workspace/
  task/       validated inputs and plan version
  evidence/   authorized, provenance-bearing context
  tools/      schemas and capability handles
  output/     proposed and committed artifacts
  scratch/    quota-limited temporary state
  audit/      protected event references
```

Do not mount a model-readable `/secrets` directory. Tool descriptions belong in the workspace; secret material belongs in the trusted broker or executor described in Chapter 11.

## Define Lifecycle and Ownership

Create the workspace from authenticated task state. Use an unpredictable execution identifier, explicit owner, quotas, mount manifest, and policy version. Separate durable checkpoints from scratch data. On completion, retain only declared outputs and audit evidence; expire temporary context under policy.

Concurrent workers need ownership or compare-and-set rules. Cleanup must not follow symbolic links or delete paths outside the validated workspace root. A recycled workspace, shared temporary directory, or stale mount can cross-contaminate tasks even when model prompts are separate.

## Give Executors Handles, Not Secrets

Environment variables and credential files are common process interfaces, but they can leak through child processes, crash dumps, logs, diagnostics, and accidental reads. Prefer a trusted proxy, sidecar, broker handle, or platform-native identity that attaches credentials at the outbound boundary.

If a tool truly requires a file or environment credential, expose it only to the minimal executor process, not the model-facing workspace; restrict inheritance, lifetime, filesystem permissions, and diagnostics. Rotate and revoke it independently of workspace deletion.

UNIX read/write/execute bits do not map directly to retrieval/tool/memory capabilities. Filesystem permissions can enforce some local operations; database, API, graph, and semantic restrictions remain at their resource boundaries.

## Make Recovery Observable

Record workspace creation, mount versions, policy decisions, tool handles, resource usage, outputs, cleanup, and durable checkpoints without copying secrets or unnecessary personal data. Test crash recovery, duplicate workers, orphan cleanup, stale credentials, malicious archives, symlink/junction escape, disk exhaustion, and output promotion after policy revocation.

Measure workspace leaks, cleanup failures, quota terminations, cross-task contamination, secret scans, recovery success, and discrepancies between proposed and committed output.

The UNIX lesson is not that everything should literally be a file. It is that naming, composition, isolation, and lifecycle should be explicit. Reliable AI systems use those ideas where their enforcement semantics are real, and retain typed data, policy, and workflow controls where the analogy ends.
