# Diagnosing Model Problems

Context engineering cannot make every model perform every task. The hard part is proving that a persistent failure belongs at the model boundary rather than in the context-to-outcome system around it. “The model had the right document” is not enough: the relevant passage may have been buried, malformed, unauthorized, contradicted, or lost during assembly. The model-boundary decision is what remains after the system has tested its Lexicon, Semantics, and Pragmatics, along with retrieval, authorization, orchestration, and evaluation.

Model modification should begin with a diagnosis, not frustration.

## Define the Failure Before Assigning It

Specify the evaluation unit, expected behavior, tolerances, and consequence. Preserve the complete run manifest: input, eligible evidence, retrieved candidates, final context, prompt and model versions, tool outcomes, state transitions, and evaluator result. Reproduce the failure across repeated runs and important slices.

Then test the context spine and its enforcement boundaries in order, using controlled ablations:

1. **Lexicon:** verify source eligibility, authority, freshness, provenance, identity, and the evidence actually available to the run.
2. **Semantics:** verify schemas, identifiers, relationships, definitions, ambiguity handling, and whether the task’s meaning is explicit rather than inferred from prose.
3. **Pragmatics:** verify purpose, actor, output contract, authorization, policy checks, and the boundary between a model proposal and an allowed effect.
4. **Retrieval and assembly:** verify ranking, filters, scoped hydration, serialization, context placement, and loss or contradiction during assembly.
5. **Orchestration:** replace model-led decisions with deterministic workflow steps or known-good tool observations to isolate state, sequencing, retry, and tool failures.
6. **Evaluation:** verify the evaluator against authoritative or human judgments, then test held-out slices, abstentions, and consequences rather than optimizing a proxy.

Only after these checks should model comparisons and adaptation become the primary experiment. Useful controlled interventions include:

| Intervention | What improvement suggests |
|---|---|
| Supply a short, authoritative passage directly | retrieval or context assembly problem |
| Replace prose with a typed schema and validator | interface or decoding problem |
| Replace a tool result with a known-good fixture | tool or observation problem |
| Execute the same decision in a deterministic workflow | orchestration or state problem |
| Give an oracle demonstration or reference solution | instruction or representation problem |
| Compare capable model families under identical context | possible model capability problem |

These are diagnostic signals, not proofs in isolation. Change one variable at a time and evaluate on held-out examples. If several models fail after the context spine and its boundaries have passed, the task definition or evaluator may still be wrong. If one succeeds, training the weaker model might help—but switching models may be cheaper.

## Separate Knowledge, Behavior, and Capability

Missing or changing facts usually belong in retrieval or tools because weights are a poor source of freshness and provenance. Repeated output style, terminology, or narrow formatting behavior can be candidates for adaptation once schemas and constrained decoding have been tested. A bounded task skill may be a model-capability problem when oracle context, valid interfaces, and sufficient compute still leave a stable error pattern.

Do not train a model to enforce authorization, spending limits, legal invariants, or exact side effects. Those remain software obligations even if fine-tuning reduces invalid proposals. Likewise, training cannot guarantee deterministic prose. If downstream processing requires determinism, use typed outputs, validators, and deterministic code.

## Use an Escalation Matrix

Before modifying weights, record:

- the baseline and required threshold;
- the failing slices and error taxonomy;
- context, interface, tool, and workflow ablations;
- candidate model comparisons;
- training-data availability and provenance;
- expected regression and maintenance costs; and
- a rollback and shadow-evaluation plan.

Model modification is justified when a stable, valuable failure remains after the Lexicon, Semantics, Pragmatics, retrieval, authorization, orchestration, and evaluation checks have passed; training data represents the target behavior; and held-out evaluation can detect improvement and regression. This is a boundary decision, not a claim that context engineering has ended. Context engineering is the broader discipline for NLP systems—including search, extraction, classification, recommendation, summarization, workflows, and agents—and model modification is one implementation choice within it.
