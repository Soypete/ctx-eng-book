# Context Engineering as the Research Phase

Context engineering is the research phase because it makes the task observable across the Lexicon → Semantics → Pragmatics spine. Source and retrieval experiments reveal which evidence is eligible and sufficient. Schemas and relationship checks reveal whether meaning is explicit. Authorization and output contracts reveal what the actor may say or do. Tool, state, and workflow traces reveal where orchestration fails. Evaluation turns recurring errors into a dataset. This work can justify model modification, but it remains useful if the model changes again—and it applies to search, extraction, classification, recommendation, summarization, workflows, and agents.

## Use a Reversible Decision Process

1. Define the task, actor, consequence, baseline, and threshold.
2. Verify the evaluator against human or authoritative judgments.
3. Test Lexicon: source authority, freshness, provenance, identity, and retrieval eligibility.
4. Test Semantics: schemas, identifiers, relationships, definitions, ambiguity, and representation.
5. Test Pragmatics: purpose, authorization, output constraints, tools, and execution boundaries.
6. Instrument state, orchestration, context assembly, and outcomes; run controlled ablations.
7. Choose the smallest intervention—context, workflow, model selection, adaptation, or specialization—that addresses the diagnosed cause.
8. Evaluate on held-out slices and failure injections, then deploy with versioning, rollback, and ongoing drift monitoring.

The sequence is a decision gate, not a claim that every technique must be built in a fixed implementation order. A narrow classifier may be cheaper than building elaborate retrieval, and a model switch may outperform months of adaptation. But a model-boundary conclusion should be made only after the relevant Lexicon, Semantics, Pragmatics, retrieval, authorization, orchestration, and evaluation hypotheses have been tested. Reversibility, expected information gained, consequence, and lifecycle cost determine the specific experiment order.

## Preserve System Boundaries After Training

An adapted model still needs fresh evidence, scoped retrieval, authorization, typed tools, durable state, provenance, observability, and evaluation. Training may change the rate at which the model proposes a valid action; it does not grant the action authority. Distillation may lower inference cost; it does not make the student’s claims authoritative. A specialized extractor may improve a metric; its assertions remain derived state until validated and promoted.

What persists is not necessarily a particular retrieval implementation or state schema. Those should evolve too. The durable investment is the explicit contract: source eligibility, semantic meanings, authority boundaries, state transitions, evaluation cases, lineage, and outcome telemetry.

## Know What Training Should Not Store

Do not use model weights as the primary store for changing prices, permissions, customer records, policy versions, or facts requiring citation and deletion. These need governed state with freshness and provenance. Training is better suited to stable behavior or bounded task patterns whose improvement can be demonstrated.

The chapter’s reliability question is answered through evidence: if authoritative context, explicit semantics, authorized interfaces, valid workflow state, and a trusted evaluator still expose a stable capability gap, a model intervention is credible. If the failure moves when those inputs change, keep debugging the relevant system boundary.

Context engineering does not stop when weights change. It supplies the specification, training evidence, evaluation harness, and production controls that make the change accountable. Model modification is one implementation choice inside that system—not the moment systems engineering ends.
