# Harnesses and State Machines

## Argument
The harness owns system invariants and wraps probabilistic model proposals in explicit operational states and guarded transitions. It is the deterministic boundary between assembled context and outcome.

## Why it matters (reliability goal)
The model may propose; trusted code must enforce what remains true when the proposal is wrong.

## Beats

1. **The Harness Problem** — evidence: existing prose
   - Lexicon and Semantics context assembly, Pragmatics constraints, loop management, tool execution, state persistence, observability, safety enforcement
   - Enforcement stays outside the model

2. **State Machines and Workflow State** — evidence: existing prose + ledger (Generative Agents paper)
   - Operational states can be finite without model behavior being deterministic
   - Allowed transitions, terminal states, approval guards, and optimistic concurrency

3. **State Machine Design** — evidence: existing prose
   - Model proposes transitions; software validates, authorizes, and commits them
   - Surfaces hidden complexity: decision points, conditions, failure modes

## Conclusion to reach
The reader should model states that change authority, recovery, resource ownership, progress, or later semantics—and test the failure paths for agentic and non-agentic workflows.
