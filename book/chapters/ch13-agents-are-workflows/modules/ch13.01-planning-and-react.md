# Planning and ReAct

The word *agent* suggests an autonomous worker. That framing is useful until it hides the software doing the actual work. A production agent is usually a workflow with a model at selected decision points: software assembles context, invokes the model, validates a proposed action, executes a tool, records the result, and decides whether another step is allowed.

Most agents are workflows wearing a trench coat. The model supplies judgment where rules are difficult to enumerate. The surrounding workflow supplies authority, state, limits, and recovery. Reliability depends on assigning each decision to the right side of that boundary.

This is the chapter's application of the book's context engineering framework. The framework's Lexicon, Semantics, and Pragmatics are organizing questions, not three isolated pillars or product components. The workflow first assembles a scoped lexicon: the sources, entities, evidence, and current state available to this run. It supplies semantics through schemas, identifiers, relationships, provenance, and task definitions. It then applies pragmatics: the purpose of the operation, the actor's authority, and the constraints on what a result may say or do. The model participates in this context-to-outcome pipeline; it does not own the pipeline.

```text
scoped sources and state
        ↓
assembled, typed context
        ↓
model proposal (probabilistic)
        ↓
validation + authorization (deterministic)
        ↓
execution or answer delivery
        ↓
recorded outcome → next workflow state
```

The pattern is useful beyond agents. A document extractor can propose fields, a classifier can propose a label, and a summarizer can propose a response. In each case, the surrounding workflow still decides which context is eligible, how meaning is represented, whether the result passes validation, and what downstream consequence is permitted.

## ReAct Is an Interaction Pattern

ReAct interleaves reasoning and acting so that observations from an environment can inform later actions [Yao et al., 2022](https://arxiv.org/abs/2210.03629). In an implemented agent, the useful boundary is simpler than the name suggests:

1. The model receives the current task state and available operations.
2. It proposes an action and arguments, or proposes completion.
3. The harness validates the proposal against schemas, policy, and workflow state.
4. A trusted tool executor performs an allowed action.
5. The harness records a typed observation and assembles the next context.

The model's generated explanation is not proof of how it reasoned, and it should not be treated as an authorization signal. A proposal is not workflow state and an observation is not automatically a successful outcome. The reliability benefit comes from observable proposals and effects. Software can reject an invalid action, redact an unsafe observation, stop an unproductive loop, and preserve provenance for the evidence returned by a tool.

```text
task state -> model proposal -> validation -> tool execution
     ^                                         |
     |------------ recorded observation <------|
```

A naive implementation parses free-form model text and immediately calls a function. A safer implementation requires a typed proposal, resolves a tool from an allowlist, authorizes the exact arguments for the current actor and state, assigns an idempotency key, executes only after those checks, and records the outcome before continuing. ReAct does not supply those guarantees. It only creates places where the harness can enforce them.

## A Plan Is Proposed State

Longer tasks need a representation of intended work. Keeping that plan only in the prompt makes it easy to lose during compaction, retries, or process failure. Store it as versioned workflow state instead:

```json
{
  "plan_version": 3,
  "goal": "compare the current contract with the approved template",
  "steps": [
    {"id": "retrieve", "status": "complete", "evidence_ids": ["doc-18"]},
    {"id": "compare", "status": "ready", "depends_on": ["retrieve"]},
    {"id": "publish", "status": "blocked", "requires": ["human-approval"]}
  ]
}
```

The model may propose steps, dependencies, or revisions. The harness decides whether that proposal is well formed, whether prerequisites are satisfied, whether a step is authorized, and whether changing the plan invalidates earlier work. A persisted plan is not automatically a good plan. It is inspectable state that software and operators can evaluate.

Plan refinement is often sufficient: propose a coarse plan, execute one bounded step, record the observation, and revise the remaining steps. Search methods such as tree search can be useful when candidate states can be scored by a credible evaluator. They are not a general reliability upgrade. If the model generates and judges its own candidates against a vague objective, extra search can multiply cost while repeatedly selecting the same mistake.

Use more elaborate planning only when the system has:

- a bounded action space;
- a state representation that can be copied or simulated;
- an evaluator correlated with the production outcome;
- a budget for branching and tool use; and
- a policy for reconciling a revised plan with effects already committed.

## Decide With an Evaluation, Not a Framework List

Framework names change faster than the underlying obligations. Before adopting an agent framework or workflow engine, test whether it makes these properties explicit:

- durable, versioned task and plan state;
- typed model proposals and tool observations;
- authorization before retrieval and again before side effects;
- bounded iterations, time, tokens, and money;
- idempotency and reconciliation for external effects;
- traceable state transitions and evidence lineage; and
- deterministic tests for invalid transitions and injected failures.

Start with the smallest workflow that can express the task. Add planning when the task has meaningful dependencies or needs revision after observation. Add branching search only when its evaluator earns the additional cost on representative tasks. The progression is not from a simple agent to a more magical one. It is from implicit model behavior to explicit, governable state.
