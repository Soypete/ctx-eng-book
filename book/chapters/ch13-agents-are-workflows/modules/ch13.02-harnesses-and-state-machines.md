# Harnesses and State Machines

An agent demo can hide its control flow inside a single request handler. Production systems cannot. They need a harness: trusted software that owns execution state, assembles context, validates model proposals, invokes tools, records observations, and enforces resource and authorization limits.

The harness is not packaging around the intelligence. It is the control plane that makes probabilistic decisions usable inside a deterministic system.

## Put Enforcement Outside the Model

A useful decision boundary is based on what must remain true when the model is wrong. Software should own:

- allowed states and transitions;
- authorization and credential use;
- input and output schema validation;
- deadlines, iteration limits, and budgets;
- tool timeouts, retry classification, and idempotency;
- checkpoints, concurrency control, and recovery; and
- audit records, metrics, and operator escalation.

The model can propose a tool, arguments, a plan revision, an interpretation of evidence, or a final answer. Those proposals are inputs to trusted code. Asking the model to remember its budget or obey an authorization rule may improve behavior, but it does not enforce either invariant.

## Make Workflow State Explicit

An agent can be modeled as a state machine when its relevant execution modes and allowed transitions are explicit. This does not mean every piece of model behavior is finite or deterministic. It means the system wraps that behavior in a finite set of operational states.

```text
NEW -> PLANNING -> READY -> EXECUTING -> VALIDATING -> COMPLETE
          |           |          |            |
          +---------->FAILED<-----+------------+
                         |
                      RECOVERING
```

Transitions should be commands checked by software, not labels chosen by the model. The model can propose `publish`; the reducer can require a validated artifact and an approval record before moving from `VALIDATING` to `COMPLETE`.

```python
from dataclasses import dataclass, replace
from enum import Enum


class Phase(str, Enum):
    READY = "ready"
    EXECUTING = "executing"
    VALIDATING = "validating"
    COMPLETE = "complete"
    FAILED = "failed"


ALLOWED = {
    Phase.READY: {Phase.EXECUTING, Phase.FAILED},
    Phase.EXECUTING: {Phase.VALIDATING, Phase.FAILED},
    Phase.VALIDATING: {Phase.COMPLETE, Phase.EXECUTING, Phase.FAILED},
    Phase.COMPLETE: set(),
    Phase.FAILED: set(),
}


@dataclass(frozen=True)
class Run:
    run_id: str
    version: int
    phase: Phase
    approved: bool = False


def transition(run: Run, target: Phase, expected_version: int) -> Run:
    if run.version != expected_version:
        raise RuntimeError("stale workflow update")
    if target not in ALLOWED[run.phase]:
        raise ValueError(f"invalid transition: {run.phase} -> {target}")
    if target is Phase.COMPLETE and not run.approved:
        raise PermissionError("completion requires approval")
    return replace(run, phase=target, version=run.version + 1)
```

This small reducer demonstrates three boundaries: terminal states cannot restart silently, invalid transitions fail closed, and optimistic version checks prevent two workers from committing incompatible updates. A real system would persist the transition and an outbox event in one transaction, then test authorization and domain-specific postconditions as well.

## Design From Failure Paths

Take a research workflow: search, fetch, extract, and synthesize. The happy path hides the decisions that determine reliability:

- What happens when search returns no eligible sources?
- Is a failed fetch retryable, skippable, or required?
- Which extraction result is sufficient to proceed?
- Can synthesis complete when a required claim lacks evidence?
- Who can approve publication, and is approval still valid after revision?

Each answer belongs in state, transition guards, or outcome policy. The model may help interpret an ambiguous source, but it should not turn `fetch_failed` into `evidence_verified` merely by continuing the conversation.

State machines impose costs. Poorly chosen states produce transition sprawl, and not every internal reasoning step deserves persistence. Model only states that change authority, recovery behavior, user-visible progress, resource ownership, or the meaning of later operations. Keep transient generation details in traces unless recovery requires them.

Measure invalid-transition attempts, stale-write conflicts, time spent per state, terminal outcome rates, and manual interventions. Those signals show whether the harness contains failures or merely renames them. Once transitions are explicit, the next reliability problem is preserving them across crashes and duplicate delivery.
