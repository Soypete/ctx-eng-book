# Durable and Event-Driven Execution

An agent that runs longer than one process lifetime needs durable execution. Saving the conversation is not enough. The system must preserve the workflow position, committed effects, pending work, policy and schema versions, evidence references, budgets, and enough execution metadata to decide what is safe after a failure.

Durability improves reliability only when recovery semantics are explicit. Restarting a loop from an old transcript can repeat a payment, send a second email, or act under a policy that has since changed.

## Checkpoint at Meaningful Boundaries

A checkpoint should identify at least:

- the run and workflow definition version;
- current state and optimistic concurrency version;
- plan steps and terminal outcomes;
- references to source observations and derived artifacts;
- completed and pending tool operations, including idempotency keys;
- authorization or approval references that must be revalidated;
- model, prompt, tool, schema, and policy versions; and
- elapsed attempts, time, token use, and cost.

Persist state before dispatching work, then record the outcome before advancing. For an external side effect, a crash can occur after the provider accepted the request but before the workflow recorded success. That outcome is *ambiguous*. It is not safe to assume failure and retry blindly.

```text
record intent -> dispatch with idempotency key -> record outcome -> advance state
                      |
                 crash here
                      v
            reconcile with provider before retry
```

Exactly-once execution is rarely an end-to-end property a workflow can simply declare. A practical design combines at-least-once delivery with idempotent consumers, deduplication records, provider-supported idempotency keys, and reconciliation for uncertain outcomes. When the state change and message publication share a database, a transactional outbox can prevent one from being committed without the other.

## Choose Persistence Semantics Deliberately

Different mechanisms solve different parts of the problem:

- **Transactional workflow state** can atomically update a run and its pending outbox record.
- **Event logs** preserve transition history and support audit or state reconstruction, but replay still needs versioned interpretation.
- **Queues** decouple workers and redeliver unacknowledged messages, which requires idempotent handling.
- **Sagas** coordinate multi-service work through forward and compensating actions. Compensation is another fallible business action, not a database rollback.

The choice follows from the failure semantics. A read-only research task may tolerate repeating a fetch. An email responder must deduplicate sends. A purchasing agent may need authorization at commit, a provider idempotency key, reconciliation, and operator review for an ambiguous charge.

## Events Create Ordering and Evolution Problems

Many agents start from events rather than a user-held loop: a ticket arrives, a document changes, or a deadline expires. Event-driven execution adds familiar distributed-systems obligations:

- stable event identifiers and correlation with a workflow run;
- schema versions and compatibility rules;
- duplicate and out-of-order delivery handling;
- per-entity concurrency policy where order matters;
- deadlines, backpressure, and dead-letter handling; and
- provenance linking the triggering event to every derived effect.

Two emails from one customer illustrate the ordering tradeoff. Processing them concurrently reduces latency but may generate a reply to the older message after the newer issue is resolved. Serializing all email globally destroys throughput. A useful middle ground is per-conversation ordering with a version check before sending. The correct partition key is a domain decision, not a property the model can infer reliably from whichever messages happen to be in context.

## Replay Is Evidence, Not Time Travel

Deterministic replay can reconstruct state transitions when their inputs and code versions are captured. It cannot generally reproduce a nondeterministic model response or the past state of an external service byte for byte. Decide whether replay means:

1. reconstruct the historical state from recorded outcomes;
2. re-execute pure workflow logic against captured observations; or
3. rerun tools and models under current conditions for comparison.

These are different operations and should produce different records. Never let a diagnostic replay repeat production side effects.

Evaluate recovery by injecting crashes before dispatch, after dispatch, and after outcome recording. Track duplicate effects, unresolved ambiguous outcomes, replay divergence, stuck runs, operator interventions, and time to recovery. Durable execution makes an agent reliable when it converts failures into known states with safe next actions—not when it merely starts again.
