# Planning and ReAct

## Argument
Most agents are workflows wearing a trench coat. ReAct exposes model proposals and observations to a trusted harness; planning persists intended work as versioned, governable state. The module makes the context engineering framework and the context-to-outcome pipeline explicit.

## Why it matters (reliability goal)
Reliability comes from validating model proposals, governing effects, and retaining plans outside the model context.

## Beats

1. **ReAct Pattern** — evidence: existing prose + ledger (Teleprompters vs MCP/ReAct)
   - Interleaves proposal, validated action, and observation in a loop
   - Does not prove faithful internal reasoning
   - Creates intervention points for context scope, schema, policy, authorization, execution, and loop limits

2. **Planning Patterns** — evidence: existing prose
   - Persist plan steps, dependencies, evidence, approvals, and versions outside the model context
   - Refine after bounded observations
   - Use branching search only with bounded states and credible evaluators

3. **Adoption Criteria** — evidence: systems requirements
   - Durable state, typed boundaries, authorization, budgets, idempotency, traces, and failure tests

## Conclusion to reach
The reader should treat model output and plans as proposals whose state transitions and execution remain governed by deterministic software, including in non-agent extraction and classification workflows.
