# The Future of AI Engineering

## A New Systems Skill Set for Software Engineers

Context engineering is a prediction about the systems skill set software engineers will need as agents move from prototypes into operations. The role is still software engineering. The specialization is building and maintaining agents whose information, state, authority, tools, and evaluations remain reliable in production.

This does not require “context engineer” to become a separate job title. It names a body of engineering work that cuts across familiar specialties. An engineer responsible for production agents needs enough of each area to design the boundaries, diagnose failures, and coordinate with deeper specialists.

**Data engineering for AI** builds pipelines that transform source data into governed, retrievable representations. Chunking and embeddings are optional techniques, not the definition of the job. The output remains data; context is the task-specific view assembled from it.

**Retrieval engineering** builds systems that fetch useful and authorized information for each request. Depending on the workload, that may include lexical search, vectors, structured queries, graph traversal, reranking, and result synthesis. The work balances task success, recall, precision, freshness, latency, and cost.

**State engineering** manages what persists across interactions and workflow attempts. This includes session state, user preferences, durable execution records, and agent workspaces. The work requires schemas, lifecycle rules, consistency choices, migrations, and recovery behavior. Orogat and Mansour frame long-term agent memory as a data-management workload whose correctness concerns state trajectories, and propose ingestion, revision, forgetting, and retrieval as state-level operators [Orogat & Mansour, 2026](https://arxiv.org/abs/2605.26252). That vision supports lifecycle-oriented state management; it does not establish these responsibilities as a distinct job title.

**Authorization engineering** builds the boundaries that control what a workflow can retrieve and execute. This includes role- and attribute-based policy, delegated capabilities, data classification, revocation, and audit. No engineer can promise that an AI never sees unauthorized data; the defensible goal is complete mediation, least privilege, denial testing, and observable policy decisions. The repository's former “Brandstetter et al.” citation was invalid and has been removed; Chapter 11 grounds the mechanisms in OAuth, OpenID Connect, and capability-security sources.

**Platform engineering** builds the shared infrastructure that runs these components. This includes model serving, deployment, cost controls, telemetry, incident response, and reliability practices. OpenTelemetry can standardize traces, metrics, and logs; adopting it does not by itself make the platform available or cost-effective.

**Evaluation engineering** builds the systems that measure whether changes improve the intended behavior. This includes dataset construction, scenario tests, component metrics, regression detection, human review, and production feedback. The question is not only “is the answer better?” but “which component changed, for whom, under what cost and failure tradeoff?”

Small teams will continue to combine these responsibilities, especially while discovering a product. As scale, risk, and workload diversity grow, ownership should follow the failure boundaries: data, retrieval, state, authorization, platform operations, and evaluation. The software engineer building the agent does not have to implement every platform alone, but does need to understand how those components determine the agent's behavior.

The reliability consequence is organizational: a boundary without an owner becomes a boundary nobody tests. A production team should be able to name who owns retrieval quality, state recovery, authorization policy, platform budgets, and evaluation regressions—even when one person temporarily owns several of them.
