# The Production AI Stack

## The Infrastructure Stack Beneath AI

Let's enumerate what is actually running when you make an AI request. Prompts participate in this stack, but they cannot compensate for failures in the layers that store data, enforce authority, execute work, and measure outcomes.

The bottom layer is hardware: GPUs, network interconnects, and storage systems. This is infrastructure engineering—capacity planning, cost optimization, and latency management. Most AI teams do not touch this layer directly, but it constrains what is possible. Hardware and topology determine which model can run, at what precision, throughput, latency, and availability. Those constraints can force quantization, batching, or serving choices that affect observed behavior.

Above hardware sits the inference layer: the serving infrastructure that runs the model. This includes batch inference, streaming, load balancing, and caching. The choices here determine latency, throughput, and cost. An optimized inference stack can reduce serving cost without changing application prompts. Hu et al. describe parameter-efficient adaptation with LoRA; they do not support the manuscript's former 40 percent token-cost claim [Hu et al., 2021](https://arxiv.org/abs/2106.09685).

The data layer includes document stores, search indexes, databases, event streams, and sometimes vector indexes. Potential context lives here; context itself is assembled for a particular task. Vector search is insufficient for workloads that also require exact identifiers, filters, relationships, or authoritative structured fields. Hybrid retrieval is one response, but the mix should follow evaluated query classes rather than a universal architecture. Hsia et al. show that reader robustness to noise changes whether greater retrieval depth helps or hurts across their evaluated RAG configurations [Hsia et al., 2024](https://arxiv.org/abs/2403.09040). That supports workload-specific depth evaluation, not a universal hybrid design.

The orchestration layer manages loop execution, tool calling, state transitions, and error handling. This is where agents become workflows. Many apparent agent failures are workflow failures: the harness retries the wrong error, loses state, accepts malformed output, or never defines completion. The model may still choose a bad action, but orchestration determines whether that action can cascade.

The governance layer cuts across the stack: authorization, audit trails, cost controls, retention, and rate limiting. A prompt can explain policy to the model, but the system must prevent unauthorized retrieval and execution regardless of generated text.

The model sits in the middle of this stack, consuming input from below and producing output above. Yet almost all public attention focuses on this single layer. This is like obsessing over the CPU in a database system while ignoring the query planner, the storage engine, and the transaction manager. The model is the engine, but the system is the car.

## The Rise of the AI Generalist

The job market is producing a new role: the AI generalist. These are engineers who can wire up models to APIs, write prompts, integrate vector databases, and deploy agents. They understand the full stack at a surface level.

This role emerged because the tooling is now accessible. You don't need a PhD to use a transformer model. APIs abstract away the mathematics. Open-source frameworks handle the orchestration. The barrier to entry has collapsed.

The generalist's value is in velocity: they can prototype quickly, connect systems, and validate approaches. They can get something working in hours. This is essential for exploration and experimentation.

Breadth becomes a limitation when one engineer is expected to supply deep expertise in retrieval, security, distributed state, evaluation, and operations simultaneously. A generalist can validate a product path; production ownership still requires depth in the failure-prone layers.

This is the same trajectory we saw with "full-stack developers." The term emerged when web development was accessible enough for individuals to span the stack. But the best systems were still built by specialists: database engineers, frontend experts, infrastructure teams. The generalist could ship the prototype; the specialist could make it reliable.

The generalist can connect the prototype. A cross-functional context-engineering practice supplies the specialized data, security, platform, and evaluation work needed to operate it reliably.

## What Actually Determines Production Behavior

Let's answer the reliability question directly: which layers actually determine production behavior?

The model constrains capability. Instructions influence behavior within that capability. Infrastructure, retrieval, state, authorization, orchestration, and evaluation determine whether the complete system performs consistently, within latency and cost budgets, under the correct authority. The [OpenTelemetry specification](https://opentelemetry.io/docs/specs/otel/) supplies interoperable telemetry primitives; Chapter 16 explains why those signals still require domain lineage and evaluated reliability objectives.

A model can generate perfect output and still fail in production because:

- The retrieval system returned irrelevant context, polluting the model's reasoning
- The session state was lost, breaking continuity
- The authorization layer blocked necessary data, leaving the model blind
- The orchestration loop had no exit criteria, consuming infinite tokens
- The evaluation system never caught the regression

Each failure requires a system-level fix. Better instructions may help expose intent, but they cannot restore lost state, authorize blocked data, enforce a loop budget, or detect a regression by themselves.

This is why context engineering—not prompt engineering—is the discipline that matters. Prompt engineering tunes one layer in isolation. Context engineering engineers the entire system to produce reliable outcomes.

The model is the engine. The context is the fuel. The system is the car. You can tune the engine all day, but if you're feeding it contaminated fuel and the brakes are broken, you won't reach your destination.

The car metaphor eventually runs out. The practical method is simpler: assign each failure to a component boundary, define the contract at that boundary, and measure whether the complete request succeeds after the change.

The final module asks who owns those boundaries. Its answer is a hypothesis about team design, not a prediction we can treat as settled fact.
