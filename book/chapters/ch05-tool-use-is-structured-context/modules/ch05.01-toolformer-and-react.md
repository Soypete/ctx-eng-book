# ch05.01 Toolformer and ReAct

## The Action Problem

Language models generate text. Text is unbounded—a model can produce any string of tokens. This is powerful but unreliable. When you need a model to do something specific—make a database query, call an API, execute code—you cannot rely on text generation alone.

A practical response is to expose a structured action space. Each tool is a host-controlled operation with an input contract and a result contract. The model proposes a tool and arguments; the host parses, validates, authorizes, executes, and records the result. The model may still emit free text or a bad proposal unless the interface constrains it.

This is tool use as context engineering. The tool definitions themselves are context. The tool inputs are constrained context. The tool outputs are structured context. Every tool call is a bounded action in a controlled context.

The reliability question is not only how to constrain a model's proposal. It is how to keep that proposal from acquiring authority until software verifies it.

## Toolformer and the Origin of Tool Use

Toolformer showed a self-supervised method for teaching a language model when and how to call external APIs. The method sampled candidate calls, executed them, filtered calls according to whether they improved predictions, and fine-tuned the model on the resulting augmented data [Schick et al., 2023](https://arxiv.org/abs/2302.04761). It was not simply in-context learning from tool descriptions.

Within its evaluated tools and tasks, Toolformer demonstrated that a model could learn to:
- Decide when to call a tool (not always)
- Select the right tool from a set
- Format inputs correctly according to the tool's API
- Use the tool's output to inform subsequent actions

The important shift was moving part of tool selection into the model while leaving execution outside it. That increased flexibility and introduced a new probabilistic boundary: the model might omit a useful call, choose a harmful one, or misuse a result.

Modern tool-capable models are generally trained for particular call formats. At runtime, the application supplies available tool descriptions and schemas, which influence selection and argument generation. Examples may help with ambiguous boundaries, but runtime examples are not the Toolformer training mechanism.

This is context engineering at the action level. You're not just providing information context—you're providing an action context that defines what the model can do.

## Modern Tool Calling

Today, tool calling is a first-class feature in model APIs. OpenAI's function calling, Anthropic's tool use, Google's Gemini API—all provide structured mechanisms for models to invoke external functions.

The pattern is consistent across providers:

1. Define tools with JSON schemas
2. Send tool definitions through the provider's supported request field
3. Model proposes a tool call or another allowed response
4. Host validates and authorizes the proposal before execution
5. Host records the result and returns an appropriately scoped observation

A concrete example:

```python
tools = [
    {
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "Get current weather for a location",
            "parameters": {
                "type": "object",
                "properties": {
                    "location": {
                        "type": "string",
                        "description": "City name"
                    },
                    "unit": {
                        "type": "string",
                        "enum": ["celsius", "fahrenheit"]
                    }
                },
                "required": ["location"]
            }
        }
    }
]

response = client.chat.completions.create(
    model="gpt-4",
    messages=[...],
    tools=tools
)
```

The model may propose a structured weather call instead of answering from parametric knowledge. The host still has to validate the location, apply policy and timeouts, execute the call, and attach source and freshness metadata. A tool result is external data, not automatically verified truth.

This is structured context in action. The schema narrows the shape of a proposal. The host creates the actual action boundary through validation, authorization, execution limits, and result handling.

## State of the Stack

This section surveys current tools that implement the patterns discussed in this chapter. They are examples of current engineering approaches, not endorsements or architectural requirements.

### Standards and Formats

- **JSON-Schema-like definitions**: Common across tool APIs, but providers support different subsets and behaviors. Test the exact schema features your model and SDK enforce.
- **Function Calling API Specifications**: OpenAI function calling, Anthropic tool use, Google Gemini API each define their own schema format.

### Infrastructure

- **Provider tool APIs**: OpenAI, Anthropic, and Google expose structured tool proposals with provider-specific schema subsets and enforcement modes.
- **LangChain**: Framework providing tool abstractions and execution harnesses for multiple model providers.
- **LlamaIndex**: Data indexing framework with built-in tool definitions and function calling support.

### AI-Specific Implementations

- **Tool-use training and benchmarks**: Toolformer and ToolBench are research projects with different goals. ToolBench was introduced by Qin et al. at Tsinghua University as part of ToolLLM, a dataset and framework built from more than 16,000 real-world APIs [Qin et al., 2023](https://arxiv.org/abs/2307.16789). Its scale is evidence about that benchmark, not proof that a production tool catalog should be large.
- **ReAct Implementations**: LangGraph, AutoGen, and similar frameworks implement reasoning-action loops.

### Questions to Ask Before Adoption

1. Does the model provider natively support tool calls, or must you parse free-text output?
2. What happens when tool parameters don't validate—does the system retry or fail?
3. Can the model call multiple tools in sequence, or must each call return before the next?
4. How do you handle tool failures—does the model receive error messages or nothing?
5. Is the tool schema versioned—can you evolve it without breaking existing agents?
