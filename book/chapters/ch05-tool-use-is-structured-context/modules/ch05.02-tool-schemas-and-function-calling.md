# ch05.02 Tool Schemas and Function Calling

## Schemas as Context Boundaries

JSON and XML schemas are not just for validation—they're context engineering tools. A schema defines what's possible. It tells the model: "here's the shape of valid output."

Consider a function that creates a customer record:

```json
{
  "name": "create_customer",
  "parameters": {
    "type": "object",
    "properties": {
      "email": {
        "type": "string",
        "format": "email"
      },
      "name": {
        "type": "string",
        "minLength": 1
      },
      "tier": {
        "type": "string",
        "enum": ["free", "pro", "enterprise"]
      }
    },
    "required": ["email", "name"]
  }
}
```

This schema does multiple things when the host uses a validator that supports the relevant keywords:
- Constrains syntactic inputs (`tier` must be one of three values; `format: email` may require explicit validator configuration)
- Documents what the function does (description in natural language)
- Enables validation (the system can reject malformed calls before execution)
- Narrows the proposed fields (authorization and business policy still define the action boundary)

The schema tells the model and validator which shape is recognized. It does not say who may create a customer, whether the email is verified, whether the tier change is permitted, or whether a duplicate request should be idempotent.

Schema design matters for reliability. A too-loose schema allows invalid outputs. A too-strict schema prevents valid use cases. The art is matching the schema to the actual capabilities of the underlying system.

## Tool Selection

Given a set of tools, a model predicts a call from the request, tool definitions, conversation, and behavior learned during training. Describing this as “context matching” is a useful intuition, not a specified retrieval algorithm.

The model receives:
- Tool definitions (names, descriptions, schemas)
- The user's request
- Relevant conversation history

It must match the request to the appropriate tool. This is a retrieval problem in action space. The model looks for the tool whose description best matches the user's intent.

Tool descriptions are critical. A poor description:

```
"get_user" - gets user info
```

A good description:

```
"get_user" - Retrieve a user's profile by their unique ID. Returns name, email, account tier, and registration date. Use when the user asks about their account or profile information.
```

The second description provides context: what the tool does, what it returns, and most importantly—when to use it. The "when" is the selection criteria.

Tool selection failures are context failures. If the model selects the wrong tool, it's because:
- The tool descriptions don't adequately distinguish the tools
- The user request is ambiguous
- The context doesn't clarify intent

Improve tool descriptions, add discriminating examples, reduce overlapping tools, or route deterministically when software already knows the operation. Then evaluate selection on ambiguous, adversarial, and no-tool cases. Better prose cannot repair a model that lacks the required tool-use capability.

## Constraining Action Through Tool Design

The ultimate reliability mechanism is tool design itself. You constrain model actions by designing the tool space carefully.

Principles for reliable tool design:

**Narrow tool authority.** Each tool should expose one bounded capability. A `search_documents` tool is safer than a `do_anything` tool only when resource scope, result limits, and authorization are also enforced.

**Explicit input schemas.** Don't leave format to chance. Specify exactly what fields are required, what values are valid, what the structure should be.

**Clear output schemas.** The model needs to know what it'll receive. Define the output structure so the model can properly consume it in subsequent steps.

**Purposeful descriptions.** Explain not just what the tool does, but when to use it. Include examples of appropriate calls.

**Bounded results.** Don't return unbounded data. Limit query results, truncate long outputs, paginate large responses. The model cannot consume unlimited context.

**Failure modes.** Define what happens on error. Return a consistent error format so the model can handle failures gracefully.

The host is the enforcement boundary. The schema constrains representation. The description supplies selection context. Authorization, idempotency, side-effect policy, timeouts, and audit complete the contract.

For each tool, test at least five classes: correct selection, no-tool abstention, malformed arguments, schema-valid but semantically invalid arguments, and an unauthorized request. Reliability is the host rejecting unsafe proposals as much as the model producing good ones.

## Citations

- Kodathala evaluates off-host, identity-bound authorization across 15 models and eight attack scenarios; the paper supports keeping authority outside model-visible context, with results limited to its gateway and benchmarks [Kodathala, 2026](https://arxiv.org/abs/2607.05518).
- Zhang et al. evaluate task-conditioned admission for long-term agent memory and document cross-domain leakage, sycophancy, tool-call drift, and memory-induced jailbreak risks in their tested settings [Zhang et al., 2026](https://arxiv.org/abs/2606.06054). This supports treating memory admission as a trust boundary, not a general claim about tool schemas.
