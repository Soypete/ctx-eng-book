# Toolformer and ReAct

## Argument
Tool use gives a model a structured proposal space; the host creates the action boundary through parsing, semantic validation, authorization, execution limits, and result handling.

## Why it matters (reliability goal)
Tie to Pragmatics pillar: tool definitions are pragmatic contracts that define what actions are possible. Without structured tool interfaces, models operate in unbounded text space—unreliable. With tools, they operate in bounded action space—predictable.

## Beats

1. **The Action Problem** — evidence: existing prose
   - Text generation is unbounded; tool use creates bounded action space
   - Tool definitions = context; tool inputs = constrained context; tool outputs = structured context

2. **Toolformer Origins** — evidence: existing prose + ledger (tool usage patterns)
   - Toolformer generated and filtered API-call data, then fine-tuned the model
   - Runtime tool descriptions influence a tool-capable model but are not the Toolformer training method

3. **Modern Tool Calling** — evidence: existing prose
   - First-class in OpenAI, Anthropic, Google APIs
   - Pattern: define tools → model generates call → system executes → injects result

4. **State of the Stack** — evidence: existing prose
   - JSON Schema as dominant standard
   - Infrastructure: LangChain, LlamaIndex, LangGraph, AutoGen

## Conclusion to reach
The reader should distinguish a model's structured tool proposal from the host's enforced authority and execution boundary.
