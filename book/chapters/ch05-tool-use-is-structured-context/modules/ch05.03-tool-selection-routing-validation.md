# ch05.03 Tool Selection, Routing, and Validation

## Tool Routing and Orchestration

Single-tool calls are simple. Multi-step workflows require routing—the model must decide not just which tool, but the sequence of tools, and how to pass outputs between calls.

Tool routing is a pipeline problem. The model generates a tool call, receives a result, and decides what to do next. This is an agent loop, and it requires exit criteria.

A money transfer shows why routing is more than passing outputs between calls:

```
User: "Transfer $100 to John and tell him it's for dinner"

1. Resolve "John" within the authenticated user's permitted contacts.
2. If the name is ambiguous, stop and ask the user to choose.
3. Present the resolved recipient and amount for confirmation.
4. Submit `transfer_funds` with a server-issued capability and idempotency key.
5. Record the committed transaction ID.
6. Send a message only after the transfer commits; retry messaging separately.
```

Each result can become input to the next stage, but not every value should be copied back into model context. The workflow should retain typed state, pass only required fields, and keep credentials or capability material outside the prompt.

Reliable routing requires:
- Clear tool output schemas (each tool's output must be well-defined)
- Explicit input requirements (what does each tool need?)
- Exit conditions (when is the task complete?)

Without enforced exit conditions, agents can loop. “The task is complete when the request is fulfilled” merely restates the problem. Define terminal states in software: `completed(transaction_id)`, `needs_clarification`, `denied`, `failed_retryable`, and `failed_terminal`. Bound attempts by tool and error class.

Reliable routing also requires idempotency and compensation. A timeout after `transfer_funds` does not prove the transfer failed; retrying without an idempotency key may charge twice. A message failure should not roll back a committed transfer or cause the model to repeat it.

## The Reliability Promise

Tool use converts a text proposal into an inspectable software boundary. It improves control only when the harness validates and governs that boundary.

---

But tool use introduces a new problem: state. When a model calls multiple tools in sequence, it generates artifacts—conversation history, intermediate results, accumulated evidence. Where does all that state live? Chapter 6 examines this question and argues that "memory" in AI systems is database engineering.

Without tools, generated text has no direct side effect unless another component interprets it. With tools, the model can propose one of a defined set of operations, but each operation may carry real authority. A smaller action space is easier to inspect; it is not safe by default.

The reliability question—"how do we constrain model actions?"—is answered through tool design. You constrain actions by:
- Defining narrow, well-scoped tools
- Providing explicit schemas that bound inputs and outputs
- Writing clear descriptions that guide selection
- Designing routing pipelines with explicit exit conditions

The model proposes what to do from the tools it can see. The host decides what it may do for this principal, task, and workflow state. Keep those responsibilities separate.

Reliable systems do not hope for good behavior. They make unsafe proposals rejectable, repeated side effects idempotent, failures observable, and recovery deterministic.
