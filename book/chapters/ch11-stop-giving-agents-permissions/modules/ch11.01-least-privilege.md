# ch11.01 Least Privilege for Model-Driven Systems

## Limit Authority, Not Usefulness

A model-driven component should receive only the authority required for the current task and only for as long as that authority is needed. This is ordinary least privilege applied to a component whose requests are probabilistic and whose inputs may contain adversarial text.

Broad access does not guarantee noisy context, and permissions are not the root cause of every reliability failure. Broad authority does increase blast radius: a routing error, prompt injection, identity mix-up, or compromised tool can reach more data and effects than the task required.

Chapter 10 governed what each store may return. Chapter 11 governs what authority the calling workflow holds in the first place.

## Separate Four Scopes

For each operation, constrain:

- **principal scope:** whose authority is represented;
- **resource scope:** which tenant, records, fields, paths, or services are eligible;
- **action scope:** read, search, create, update, execute, or delete;
- **temporal and quantitative scope:** expiry, maximum calls, rows, bytes, cost, and side-effect limits.

Task-scoped authority should be derived from authenticated user authority and system policy. The model may request an operation, but it cannot mint, widen, or reinterpret the grant.

## Least Privilege Is Not One Mechanism

RBAC, ABAC, relationship policy, delegated tokens, attenuated capabilities, database roles, and narrowly designed tools can all contribute. Capabilities are useful when authority can be delegated as an unforgeable reference with precise constraints. They are not the only way to implement least privilege, and a bearer token with a broad scope is not least privilege merely because it is called a capability.

Enforcement belongs at the resource server, tool host, database, or trusted proxy that controls the protected operation. Prompt instructions can help the model choose correctly but do not enforce authority.

## Treat Retrieval and Action Differently

Read access can disclose sensitive data and expose malicious instructions. Write or execution access can create irreversible effects. Give them separate grants, validation, confirmation, and audit requirements. A workflow allowed to read a draft refund policy should not therefore be allowed to approve a refund.

Test confused-deputy requests, cross-tenant identifiers, prompt-injected tool calls, expired grants, replay, excessive pagination, and a task changing after approval. Measure denied out-of-scope requests, false denials, grant breadth, lifetime, revocation latency, and effects attempted outside the task.
