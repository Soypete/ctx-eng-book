# ch11.02 RBAC, ABAC, Delegation, and Capabilities

## Authorization Models Compose

RBAC maps roles to permissions. ABAC evaluates subject, resource, action, and environment attributes. Relationship-based policy follows governed relationships. Capability systems delegate authority through unforgeable references. None is universally sufficient or inherently agent-specific.

These mechanisms turn authorization context into an enforceable decision. Principal, purpose, resource, action, approval state, delegation depth, provenance, and time are all information the workflow may need to determine what it may do. Calling them context does not make the prompt an enforcement point: trusted components must establish the attributes and protected services must apply the decision.

A production workflow may use RBAC to determine which task classes a user can initiate, ABAC for tenant and classification conditions, and a short-lived delegated grant for one operation. The enforcement point still validates the exact resource and action.

## OAuth Is a Delegation Framework

OAuth 2.0 defines a framework in which a client obtains an access token to call a resource server under granted scope [RFC 6749](https://www.rfc-editor.org/rfc/rfc6749). A model should not handle authorization codes, refresh tokens, client secrets, or raw access tokens. A trusted host, broker, or proxy performs the protocol and attaches credentials to outbound calls.

Scopes may be broad strings such as `reports.read`; they do not automatically express row, field, purpose, or transaction constraints. Resource indicators, token exchange, audience restriction, proof-of-possession, and server-side policy may further narrow delegation, depending on the system. Short expiry reduces exposure but does not replace revocation or correct audience validation.

## OpenID Connect Authenticates the User to the Client

OpenID Connect adds authentication and an ID token describing the authentication event and end user to the client [OpenID Connect Core 1.0](https://openid.net/specs/openid-connect-core-1_0.html). The ID token is not the access token and should not be sent to arbitrary resource servers as authorization.

The client validates issuer, audience, signature, nonce where applicable, and time claims. Resource servers validate access tokens according to their contract. User claims can inform policy only when their issuer, freshness, and semantics are trusted.

## Capabilities Need Explicit Semantics

A capability is an unforgeable reference to authority. It may be a protected object reference or a cryptographically verifiable token. Useful constraints include resource, action, audience, expiry, task or transaction ID, delegation depth, and quantitative bounds.

Self-contained tokens reduce authorization lookups but complicate immediate revocation and policy change. Reference tokens permit centralized decisions but add availability and latency dependencies. Bearer credentials can be replayed by whoever possesses them; sender-constrained designs reduce that risk. JWT is only a token format, not proof that a token is least-privilege or capability-safe.

## Derive Grants Outside the Model

The trusted workflow resolves authenticated identity and task, evaluates policy, obtains the narrow grant, and invokes the resource. The model sees a tool contract and a scoped result—not credentials. Record issuer, subject/actor, audience, scopes or capability, policy version, decision ID, and outcome without logging secret material.

Test token substitution, wrong audience, stale claims, replay, role change, task widening, confused deputy, and revocation. The reliability property is not “uses OAuth.” It is that every protected call carries authority no broader than the verified task and is rejected outside that envelope.
