# ch11.05 Necessary Access and Authorization Coverage

## Authorized Is Broader Than Needed

An actor may be authorized to read one thousand customer records while a task
requires three. Authorization answers whether retrieval is permitted for this
actor, purpose, resource, action, and time. Data minimization asks whether the
task needed the fields and records actually retrieved.

This chapter calls the measurable intersection *necessary-access precision*. It is proposed terminology, not an established authorization standard:

```text
necessary-access precision = authorized and task-necessary included items
                             / included items
```

Define the item—field, row, passage, graph path, or context block—and label necessity against a versioned task plan. Report unauthorized inclusion separately; a metric should not allow unnecessary-but-authorized data to hide an access-control incident.

## Bound Necessity Before Retrieval

Task templates can declare required slots, eligible sources, field projections, row/path limits, time windows, and escalation conditions. Retrieve progressively when later evidence is conditional. Ask for clarification when scope changes materially, but do not depend on ReAct traces as an enforcement mechanism.

Tool design and authorization work together. Narrow query interfaces reduce accidental breadth; resource policy prevents disallowed breadth. Graph routes can focus retrieval only when their identities and paths are trustworthy. Domain-specific agents are not automatically efficient or safe.

## Evaluate Minimization and Sufficiency Together

Optimizing only minimization can starve the task. Pair necessary-access precision with required-slot coverage, retrieval recall, task success, and safe abstention. Test a broad `SELECT *`, excessive pagination, optional prefetch, a clarification boundary, and a task whose required evidence expands after an initial result.

Measure included fields/records, necessary items, unauthorized items, bytes and tokens as cost measures, clarification rate, required-slot satisfaction, and downstream outcome. Use reviewed task fixtures because the denominator for “necessary” is not generally knowable in open-ended work.

Least privilege controls what the system may access. Necessary access controls
what it chooses to include for this task. Reliable language systems need both,
enforced and evaluated outside the model.
