# ch11.03 Scoped Credentials and Trusted Brokers

## Keep Secrets Out of Model Context

Prompts, tool results, memory, traces, and error messages are the wrong places for credentials. The model does not need to read a secret to request an authorized operation. A trusted host should obtain or reference the credential and attach it only on the protected network call.

Call this component what it is: a credential broker, token service, vault, or trusted proxy. “Knowledge store” confuses authorization artifacts with retrievable knowledge and invites them into context assembly.

## Broker Narrow Authority

The broker accepts authenticated actor and task state, requested resource/action, and policy evidence. It evaluates or calls policy, then returns a handle, reference token, or short-lived credential to a trusted executor—not to the model.

```text
model proposes tool call
  -> host validates task and arguments
  -> policy authorizes exact resource/action
  -> broker obtains narrow credential
  -> executor calls resource server
  -> credential is discarded
  -> result is scoped and returned
```

Prefer handles when possible so secret material remains inside the broker or sidecar. Bind grants to audience, actor/workload, task or transaction, action, resource, expiry, and limits supported by the resource server.

## Choose Revocation and Validation Deliberately

Self-contained credentials can be validated locally but remain valid until expiry unless the system adds revocation or introspection. Reference tokens support immediate centralized decisions but depend on the authorization service. Short lifetimes reduce exposure and increase renewal load. One-time credentials reduce replay only when the resource server enforces single use atomically.

Credential chaining and delegation require explicit attenuation: a child grant must not exceed its parent. Workload attestation can strengthen broker decisions in environments that support it, but it is not a default requirement and does not establish user intent.

## Operate the Broker as Security-Critical Infrastructure

Protect issuance, storage, audit, rotation, and recovery. Never log tokens. Record credential identifier or hash, issuer, audience, policy decision, task, expiry, and use outcome. Define behavior when the broker, revocation service, or clock is unavailable; high-risk operations should fail closed.

Test replay, wrong audience, stale policy, parent revocation, concurrent single-use, leaked handle, broker outage, and a model attempting to echo a credential field. Measure issuance failures, over-broad grants, unused grants, replay rejection, revocation latency, and secret appearance in logs or context.
