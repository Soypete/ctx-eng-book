# ch06.02 Persistent State and Retrieval

## Start with Access Patterns, Not Products

Once memory is treated as application state, the next temptation is to assign each category to a fashionable database: sessions to a cache, long-term memory to a vector store, relationships to a graph. That mapping is too simple for production systems. State type describes meaning and ownership. Storage design follows access patterns, durability, consistency, latency, retention, and authorization requirements.

A user preference may fit in a relational row because the application needs an authoritative current value and transactional updates. The evidence behind that preference may belong in an append-only event log. Searchable conversation artifacts may live in object storage with full-text and vector indexes. A workflow checkpoint may require durable compare-and-set updates even if the active execution is also cached. One logical state system can use several physical representations, provided their authority and synchronization rules are explicit.

Before choosing a store, write down:

- the record's owner and authorization scope;
- its source of truth and acceptable derived copies;
- read and write patterns;
- required durability and consistency;
- freshness and latency objectives;
- retention, deletion, and legal constraints;
- conflict and supersession rules;
- recovery and replay requirements.

“Put session state in Redis” is therefore not an architecture. A cache may accelerate a session, but it should not silently become the only copy of an expensive, safety-critical workflow. If reconstruction from an event log is the recovery plan, test the reconstruction and define how much recent work may be lost.

## The State Platform Beneath the Agent

Every stateful agent has a data platform beneath it, whether the team names it or not. The write path captures observations and tool results. Transformation jobs extract or consolidate derived records. Indexers create queryable representations. Retrieval performs scoped candidate generation and ranking. Context assembly selects a bounded working set. Policy services decide what the caller and agent may access.

This platform is not merely ETL feeding a prompt. It is a set of consistency boundaries. A durable record may commit before its search index updates. A deletion may reach the source table before a cached context fragment expires. A semantic record may be derived from an episode that is later corrected. Reliable systems make those gaps visible and decide which operations may tolerate them.

For example, an assistant may use semantic search to find prior support cases but must fetch the current refund policy by a versioned key from an authoritative policy store. Similarity is useful for evidence discovery; it is not an acceptable consistency model for a binding rule. The context assembler should label the distinction rather than present both records as equally authoritative prose.

## Govern the Read Path

Retrieval is a query plan, not a permission check. Authorization should constrain candidate generation, not merely filter a completed result or instruct the model not to mention sensitive content. Tenant, user, purpose, and capability scope belong in the retrieval request and in the storage boundary that can enforce them.

A practical read path is:

1. authenticate the principal and bind the active tenant and purpose;
2. translate the task into typed retrieval requests;
3. apply structural filters and authorization before semantic ranking;
4. fetch current records from their authoritative sources when required;
5. attach provenance, validity, and confidence metadata;
6. enforce the context budget and record what was omitted;
7. trace the supplied context through the resulting action or answer.

Letting the model issue free-form searches can improve flexibility, but it creates new failure modes: broad queries, repeated expensive retrieval, prompt-injected search instructions, and inconsistent use of filters. Tool schemas, query limits, server-side authorization, and observable plans keep that flexibility inside an enforceable boundary.

## Engineer the Write Path Too

Many “memory” designs discuss retrieval while treating writes as harmless. They are not. Model-generated summaries and extracted facts are proposed state changes. They can merge identities, promote claims into facts, discard exceptions, or persist malicious instructions.

The write path should distinguish source events from derived state. It should validate schema and scope, preserve provenance, make repeated writes idempotent, and require stronger approval for higher-authority representations. A model may propose that a user prefers SMS; application logic decides whether the observation becomes an unverified note, an effective preference, or no durable record at all.

Compaction, revision, and forgetting deserve the same rigor. Keep source links when transformations are lossy. Define how corrections supersede old state. Propagate deletions into caches and indexes. Version derived artifacts so they can be rebuilt after an extraction bug. The goal is not infinite retention. It is controlled evolution.

## Evaluate the Whole State Trajectory

Storage uptime alone does not establish memory reliability. Useful measures span the lifecycle:

- write acceptance and rejection by record type;
- duplicate and identity-merge error rates;
- index freshness and rebuild success;
- retrieval recall and precision within authorization scope;
- stale, contradictory, and unauthorized result rates;
- context-budget exclusions;
- correct model use of retrieved evidence;
- deletion propagation time;
- replay and recovery success.

Test trajectories, not only isolated queries. Create a preference, supersede it, revoke access, delete the source, rebuild the index, and replay the workflow. Then verify both the answer and the trace. This follows the useful part of the governed evolving memory framing: correctness depends on how state changes over time, not simply whether a row was valid when written [Orogat & Mansour, 2026](https://arxiv.org/abs/2605.26252).

The agents that appear to remember well have deliberate state platforms beneath them. The next module separates user, session, and workflow state so each value has a clear owner and lifecycle.
