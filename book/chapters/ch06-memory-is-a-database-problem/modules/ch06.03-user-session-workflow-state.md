# ch06.03 User, Session, and Workflow State

## State Needs an Owner and a Lifetime

An agent can produce a coherent response while corrupting the state around it. It can write one user's preference into another user's profile, lose a completed tool result after a retry, or carry a temporary instruction into the next session. These failures occur when “memory” is treated as one undifferentiated store.

User, session, and workflow state answer different questions:

| State | Governing question | Typical examples | Required properties |
|---|---|---|---|
| **User state** | What durable data belongs to this principal? | preferences, consent, account-scoped history | identity binding, authorization, correction, retention, deletion |
| **Session state** | What is relevant to this bounded interaction? | recent turns, selected entities, temporary UI choices | low latency, expiration, isolation, reconstructability where needed |
| **Workflow state** | What has this execution observed, decided, and committed? | goal, step status, tool-call IDs, approvals, outputs, retry count | durable transitions, idempotency, concurrency control, recovery, auditability |

“Long-term state” is a retention horizon, not a fourth owner. Episodic, semantic, and procedural records may persist for a long time, but they should still belong to a user, tenant, workflow, shared domain, or policy authority. Naming both the owner and the lifetime prevents a generic memory namespace from becoming an accidental authority boundary.

## User State Is Not a Transcript

User state is persistent data associated with an authenticated identity or principal. Some records are direct and authoritative, such as an account setting changed through a validated control. Others are observations or inferences, such as a preference extracted from conversation. Those categories should not overwrite one another silently.

A user-state write should carry its source, authority, effective time, scope, and deletion policy. Retrieval must bind the record to the authenticated principal and active tenant. The model should not be responsible for deciding whether two people with similar names are the same identity or whether a record from one workspace may be used in another.

The naive implementation stores “Alice prefers concise answers” after a single conversation and injects it forever. A safer iteration stores the source event and a scoped, revisable preference proposal. The application defines when that proposal becomes effective, how Alice can inspect or correct it, and when it expires. Measure cross-user leakage, stale preference use, correction latency, and deletion completion.

## Session State Is a Working Set

Session state supports one bounded interaction. It may include recent messages, references resolved during the conversation, partial form values, and context already shown to the model. Its short lifetime does not make it unimportant. A session can still contain credentials, regulated data, or instructions capable of causing side effects.

Fast access is useful, but durability depends on consequence. A casual chat cursor may be disposable. A session holding an approved transfer amount is not. If losing a value could repeat an effect, violate a confirmation boundary, or make recovery ambiguous, that value belongs in durable workflow state even when a cached copy is used for speed.

Session isolation should be tested explicitly. Rotate or expire identifiers, prevent fixation, bind sessions to principals, and define what survives logout or timeout. When context is compacted, retain enough provenance to explain which source turns produced the summary.

## Workflow State Is the Recovery Contract

Workflow state records the progress of a specific execution. It should answer: what goal is active, which inputs were validated, which approvals were granted, which tool effects committed, what remains, and whether retry is safe?

Consider an agent that submits an expense report. A prompt-only implementation keeps its plan in conversation text. If the process crashes after submission but before the assistant replies, the next run may submit the report again. A durable workflow records a stable execution ID, the approved report version, an idempotency key, and a transition from `submitting` to `submitted` based on the tool's authoritative result. Recovery reads that state before deciding whether to retry.

The model may propose the next transition, but application code enforces allowed transitions, permissions, and invariants. Optimistic concurrency or compare-and-set updates prevent two workers from advancing the same execution independently. Terminal states prevent an already completed workflow from drifting back into action. Chapter 13 develops orchestration, recovery, and replay; here the key point is that their required facts must have a durable home.

## Make Boundaries Explicit

These state categories interact, but copying between them should be a named operation:

- a session observation may propose a user preference;
- a user policy may constrain a workflow;
- a workflow result may append an episode;
- evaluated episodes may support a procedural change;
- none of those promotions should occur merely because text was similar.

Trace each promotion with source IDs and policy decisions. Test tenant changes, session expiration, duplicate delivery, concurrent workers, revoked approval, and recovery after a committed side effect. The reliability consequence is concrete: the agent no longer has to infer ownership, durability, or execution progress from conversational prose.

Before adding any value to “memory,” ask two questions: who owns this state, and what event ends its lifetime? Then ask where its authoritative copy lives and which boundary enforces its use. Those answers turn apparent continuity into a system that can be debugged, recovered, and governed.
