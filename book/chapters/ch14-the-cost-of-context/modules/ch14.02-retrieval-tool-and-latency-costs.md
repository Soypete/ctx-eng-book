# Retrieval, Tool, and Latency Costs

A correct result delivered after its deadline is not reliable for a latency-sensitive task. Retrieval and tools therefore need an end-to-end deadline, not independent hopes that each dependency will be fast.

## Allocate a Latency Budget

Measure the critical path rather than adding every component duration. Independent retrievals may run concurrently; a tool chosen from an earlier observation cannot. A useful trace separates queue time, context assembly, retrieval, model time to first token, generation, tools, validation, and persistence.

For each dependency, define a deadline and an outcome policy: required and fail closed, optional and omit with provenance, or deferrable and continue asynchronously. Report p50, p95, and p99 by task class. Averages hide the tail where timeouts and retries concentrate.

Batching and caching can reduce latency, but neither is free. Batching may delay an individual request or combine data with different authorization scopes. A cache adds invalidation, freshness, tenancy, and policy-version obligations. Parallel fan-out can reduce wall-clock time while increasing load and partial-failure probability.

## Price Retrieval as a Lifecycle

Retrieval cost begins before a query. Include parsing, chunking, embedding or indexing, duplicate removal, storage, refresh, deletion propagation, candidate generation, reranking, and canonical-source fetches. Smaller chunks do not universally improve precision, and a fixed `top_k` is not a reliability policy.

Tune retrieval against judged tasks. Compare candidate recall, final context precision, answer outcome, latency, and cost while varying chunking, filters, candidate count, and reranking. Over-retrieval is waste only when the additional candidates fail to improve a required outcome; under-retrieval is expensive when it creates unsupported answers or retries.

## Make Tool Economics Visible

A tool call can consume API credits, database capacity, network bandwidth, model tokens, and human attention. Its expected cost also includes failure and compensation:

```text
expected_tool_cost = execution_cost
                   + retry_probability * retry_cost
                   + failure_probability * recovery_cost
                   + expected_side_effect_loss
```

Return typed, bounded results rather than unbounded logs or documents. Put pagination, field selection, time ranges, and maximum result sizes in the tool contract. Apply budgets to calls, bytes, wall time, and effects—not just tool count. One expensive or destructive call can matter more than ten cheap reads.

Track cost and latency per successful terminal outcome, along with cache age, fan-out, retry class, and degraded-source decisions. Optimization then targets the actual critical path without deleting evidence merely because it is expensive.
