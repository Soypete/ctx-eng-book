# Cost-Aware Extraction Pipeline Design

Optimizing the extractor alone can make the system more expensive. A cheap extractor that produces duplicate entities, ungrounded relations, or excessive review work moves cost downstream. Cost-aware design follows an assertion from source ingestion through validation, promotion, retrieval, correction, and deletion.

## Build a Stage Ledger

For every document version, record work and outcomes across:

| Stage | Costs to record | Reliability outcome |
|---|---|---|
| Ingest | parse, normalize, deduplicate | eligible source produced |
| Extract | rules/model/LLM, batches, retries | proposed assertions |
| Resolve | candidate search, review | identity decision |
| Validate | schema, grounding, policy | accepted/rejected reason |
| Store | records, indexes, provenance | queryable version |
| Serve | retrieval, reranking, canonical fetch | evidence used |
| Maintain | correction, deletion, reprocessing | derived state reconciled |

Use stable content identifiers to avoid reprocessing unchanged inputs. Cache extraction results only with source, extractor, schema, and policy versions; otherwise the cache silently preserves obsolete semantics. Parallelism improves throughput until it saturates a dependency or review queue, so enforce backpressure and per-tenant limits.

## Optimize for Accepted Assertions

Measure cost per accepted assertion and per successful downstream task, not raw documents per second. Include false-positive investigation, missed-assertion consequences, entity-resolution errors, human review, and rebuilds. Accuracy is not interchangeable across classes: weight or constrain errors according to their downstream effect.

Run ablations: remove reranking, change chunking, route a class away from the LLM, or increase the review threshold. A cheaper configuration is acceptable only if required slices and downstream outcomes stay within bounds. Where two designs satisfy all constraints, prefer the one with lower lifecycle cost; where constraints conflict, report the frontier rather than hiding judgment inside a blended score.

## Evolve From Evidence

Begin with a small source-backed pipeline and an evaluation set. Use review decisions to improve guidelines and identify stable patterns. Promote a pattern to rules or a specialized model when measured volume and stability justify the engineering work. Keep the LLM route for the residual cases where it remains useful. Re-evaluate when the schema, source distribution, model, price, or downstream consequence changes.

This is the chapter’s answer: the cheapest reliable solution is not a particular model or architecture. It is a versioned policy that meets explicit outcome constraints, accounts for failure and maintenance, and can be replaced when evidence shows a better point on the cost-reliability frontier.
