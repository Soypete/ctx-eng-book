# Context Efficiency Beyond Token Cost

Token count is a resource measure, not a system objective. Two context policies can use different tokens, retrieval calls, memory, and latency while producing different rates of successful and unsafe outcomes. Collapsing those dimensions into one undocumented score hides the tradeoff an engineer needs to make.

## Define the Outcome First

For each task class, define success and hard constraints: required evidence coverage, factual support, authorization conformance, terminal state, latency SLO, and maximum loss from an incorrect effect. Then record the resource vector:

```text
(input tokens, output tokens, model calls, tool calls,
 retrieval compute, storage reads, wall time, memory,
 human review, recovery work, monetary cost)
```

“Context efficiency” is useful as book terminology for comparing reliable outcomes with this vector. It should not be reported as a universal scalar. Weights differ between an offline extraction job and an interactive authorization workflow, and ratios can obscure a hard reliability floor.

## Instrument the Critical Path

Trace time to assembled context separately from model time to first token and full completion. Record per-source latency, queue time, cache status and age, bytes returned, candidate counts, reranking, model and policy versions, and degraded-source decisions. Attribute every cost to a run and terminal outcome.

Precompute when repeated demand and freshness tolerance repay ingestion and storage. Load lazily when requests are rare, sources change quickly, or precomputation would create large unused derived state. The answer depends on access frequency, invalidation cost, source latency, and the consequence of staleness—not on whether the source is a database or web page.

## Compare Policies on a Frontier

A policy is dominated when another policy is no worse on every required outcome and resource dimension and is better on at least one. The remaining policies form a practical Pareto frontier. Operational constraints then select among them: perhaps latency has a hard ceiling, or review cost matters more than compute.

Prompt and pipeline optimization can search configurations against a supplied metric. DSPy is one example of compiling declarative language-model programs using demonstrations and optimization [Khattab et al., 2023](https://arxiv.org/abs/2310.03714). That does not prove that shorter prompts are better, nor does it remove the need for held-out evaluation. The optimizer will exploit a weak metric just as readily as a human will.

Run experiments on versioned representative sets and report confidence intervals or repeated-run variation where model outputs are stochastic. Include failure injection and important slices. Optimize only after establishing a baseline; otherwise a lower bill can disguise a reliability regression.

The reliable system is not the one with the lowest token count. It is the nondominated design that satisfies the task’s hard constraints and has the lowest acceptable lifecycle cost.
