# ch08.06 Property Completeness and Schema Quality

## Missing Is Meaningful Only Relative to a Requirement

A graph can contain the right entities and paths while omitting properties needed to interpret them. An `Assignment` without a due date may be unusable for “What homework is due tomorrow?” An employee without a middle name may be entirely complete for access review.

Property completeness therefore needs an applicability rule. The denominator is not every property the ontology permits. It is the set required or expected for this entity under a versioned class, task, jurisdiction, lifecycle state, and source scope.

```text
property completeness = present applicable properties / applicable properties
```

Report the pair with the percentage. `3/4` is easier to audit than `75%`, especially when the schema version changes.

## Distinguish Absence, Unknown, and Inapplicable

These states should not collapse into a missing value:

- **absent** — the expected source did not supply the property;
- **unknown** — the source explicitly states that the value is not known;
- **not applicable** — the property does not apply to this entity;
- **withheld** — the active principal is not authorized to receive it;
- **stale** — a value exists but violates the task's temporal policy;
- **invalid** — a value failed structural or semantic validation.

A withheld salary is not a population defect. An unknown end date for an active employment relationship may be correct. Preserving these states prevents cleanup jobs and models from inventing values to make a dashboard green.

## Schema Quality Is More Than Fill Rate

A high fill rate can hide a bad model. Measure whether:

- terms have precise definitions and stable identifiers;
- domains, ranges, cardinalities, units, and temporal meaning match application invariants;
- required properties are actually available from authoritative sources;
- overlapping terms have explicit equivalence or non-equivalence rules;
- deprecated terms have migration paths;
- constraints reject unsafe records without rejecting valid exceptions;
- competency questions remain answerable after model changes.

Do not make the ontology finer-grained merely to support more traversal. `ResearchProfessor` and `AdjunctProfessor` are useful only if the distinction changes a query, policy, or decision and the data can support it. Additional properties create more paths, but also more missingness, ambiguity, authorization surface, and maintenance.

## Composition Requires Contracts

Small domain models can compose around shared entities, but shared labels do not establish shared identity. An employment model and an academic model may both describe a professor while retaining different authorities and effective dates.

Define the linking identifier, ownership of each property, conflict rule, permitted disclosure, and version compatibility. External vocabularies can supply useful terms, but importing them also imports semantic commitments. Map only the concepts the system uses and test the mapping.

## Measure by Task and Consequence

For each competency question, list required properties and acceptable absence states. Then measure completeness by entity type, source, task, and schema version. Track downstream failures caused by missing or invalid properties rather than assuming completeness predicts performance uniformly.

Test a complete record, each permitted absence state, contradictory sources, a deprecated property, a unit mismatch, and an unauthorized field. Verify both the graph representation and the context serializer. A complete graph can still leak a property during retrieval; a sparse graph can still be reliable for the narrow task it was built to serve.

Property completeness is diagnostic, not a target to maximize. The goal is the smallest set of well-defined, source-backed properties that supports the declared decision without hiding uncertainty.
