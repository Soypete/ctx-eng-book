# ch08.04 Knowledge Graph Tradeoffs

## A Graph Is an Architectural Commitment

Knowledge graphs are valuable when relationships themselves are a primary query surface. They are overhead when a handful of keyed lookups and joins already answer the system's questions. Reliability does not come from choosing the most expressive representation. It comes from choosing a representation the team can populate, govern, query, and evaluate correctly.

The decision is not “graph or no semantics.” Relational schemas, API contracts, tool validation, taxonomies, and policy code all encode meaning. A graph becomes attractive when those meanings must be shared and traversed across changing paths or ownership boundaries.

## Start with Competency Questions

Before selecting a graph model or store, write the questions the system must answer and the invariants it must enforce:

- Which services are transitively affected by this deployment?
- Through which delegated relationships may this principal access a resource?
- Which suppliers connect this component to a sanctioned region?
- What evidence and time interval support this relationship?

Then implement the simplest source-backed interface that answers them. Early tools and relational queries are not a disposable stopgap. They expose domain vocabulary, authority, access patterns, and failure modes. If fixed joins remain clear and performant, a graph may never be necessary.

## Signals That a Graph May Earn Its Cost

A graph representation deserves evaluation when several of these conditions hold:

- variable-depth traversal is common and depth is unknown at design time;
- relationships have important properties such as authority, confidence, provenance, or validity intervals;
- many domains share identifiers and relationship vocabulary;
- new path patterns appear frequently enough that hard-coded joins become brittle;
- graph algorithms answer a real, evaluated operational question;
- authorization or impact analysis depends on relationship traversal;
- query explanations need to preserve the path that produced an answer.

None is sufficient by itself. Recursive SQL may handle a modest dependency graph. A join table can store relationship attributes. Policy engines may be safer than exposing authorization traversal to a general query interface. Benchmark the actual workload and failure modes.

## Signals to Stay with Existing Stores

Prefer the current operational model when:

- reads are keyed by known identifiers;
- traversal depth and joins are fixed and understandable;
- document relevance, not relationship structure, dominates retrieval;
- source systems already enforce the required transaction invariants;
- identity resolution or data ownership is not mature enough to populate trustworthy edges;
- graph freshness would depend on a fragile duplicate pipeline;
- the team cannot own schema evolution, query governance, and rebuilds.

Adding a graph beside authoritative stores creates another derived-state system. Every copied node and edge needs synchronization, deletion propagation, provenance, versioning, and recovery. A stale graph can be more persuasive than an unavailable graph because it returns structured, plausible paths.

## Domain Boundaries Without Semantic Islands

One universal enterprise graph is difficult to govern, but many disconnected topical graphs create duplicate identities and contradictory vocabularies. Use domain ownership without assuming physical isolation or forced centralization.

Each domain should own its terms, sources, lifecycle, and authorization rules. Cross-domain links require explicit contracts: identifier mapping, relationship meaning, permitted direction, freshness, and failure behavior. A shared vocabulary can help where concepts genuinely overlap; it should not erase domain distinctions for the convenience of one global schema.

Agents should not discover arbitrary domains and grant themselves access. A policy-controlled semantic router can select eligible domain interfaces from the authenticated task and purpose. Chapter 12 owns the authorization mechanics.

## Traversal Does Not Require Logical Reasoning

A labeled property graph without an OWL reasoner can still be useful for explicit path queries. Conversely, an RDF graph with an ontology can still contain false assertions. Reasoning, validation, traversal, and storage are separate capabilities.

The ontology-based query-checking study discussed in 8.2 is useful evidence for one boundary: checking generated SPARQL against ontology semantics improved the authors' reported benchmark results [Allemang & Sequeda, 2024](https://arxiv.org/abs/2405.11706). It does not establish that every knowledge graph needs that reasoner or that every ontology-backed answer is correct.

Select algorithms only after naming their decision. Shortest-path algorithms require a defensible edge-cost model; mixing latency, confidence, permission, and semantic distance into one number can hide policy. Strongly connected components identify mutual reachability, not automatically coherent bounded contexts. Evaluate algorithmic output against domain judgments before making it a retrieval unit.

## Count the Full Cost

Graph adoption includes more than database licensing or query latency:

- domain modeling and stakeholder agreement;
- entity resolution and correction workflows;
- ingestion, synchronization, and deletion propagation;
- ontology and query migration;
- authorization on nodes, edges, paths, and source hydration;
- provenance and temporal modeling;
- operational backup, rebuild, and observability;
- evaluation sets for path correctness and coverage;
- expertise required to debug inference and traversal.

Compare those costs with the failure cost of the current design. If agents repeatedly miss variable-depth dependencies or cannot explain relationship-based decisions, explicit graph semantics may pay for themselves. If the problem is stale policy lookup or poor document ranking, a graph is likely a detour.

## Run a Reversible Pilot

Choose one domain question with a known answer set. Keep source systems authoritative. Build the smallest graph projection needed, preserve source identifiers and versions, and compare it with the existing query path.

Measure path precision and recall, identity errors, freshness lag, unauthorized expansion, latency, operator effort, and downstream task success. Inject source corrections and deletion, rebuild the projection, and verify replay. Adopt the graph only if it improves the target reliability outcome enough to justify its new failure modes.

Knowledge graphs are neither magic infrastructure nor an inevitable destination. They are one way to engineer relationships. The pragmatic choice is the smallest semantic system that makes the important decision more reliable and remains governable over time.
