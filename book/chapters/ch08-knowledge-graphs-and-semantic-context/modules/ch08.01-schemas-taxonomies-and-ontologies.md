# Schemas, Taxonomies, and Ontologies

## Meaning Becomes an Interface

A model can read “purchase order,” “vendor,” and “approval” and infer plausible relationships among them. That is useful language capability. It is not an application contract. A procurement system still needs to define which identifier denotes the vendor, which line items belong to the order, which approval policy applies, and what state permits fulfillment.

Semantic modeling moves those decisions out of incidental prose. It gives systems shared identifiers, named relationships, constraints, and provenance that can be queried and tested. The model may still interpret the resulting evidence, but it no longer has to invent the domain's basic vocabulary for every invocation.

This is the reliability consequence: explicit semantics narrow the set of meanings the surrounding system will accept. They do not make model reasoning deterministic, guarantee source truth, or eliminate ambiguity the model has never represented.

## Schema, Taxonomy, and Ontology Are Different Tools

These terms are often used as synonyms, which makes design discussions needlessly vague:

- A **schema** defines the shape of data: fields, types, keys, required values, and structural constraints.
- A **taxonomy** organizes concepts into a classification hierarchy or another controlled arrangement.
- An **ontology** states the concepts and relationships a domain recognizes, plus axioms that support shared interpretation or inference.

A support-ticket JSON schema can require `customer_id` and `opened_at`. A taxonomy can classify a ticket as `billing > duplicate_charge`. An ontology can distinguish a reported charge from a settled transaction, relate both to an account, and state how those concepts connect across systems.

One project may need only a schema. Another may need a controlled taxonomy for retrieval filters. An ontology earns its cost when multiple systems or teams must share relationship semantics, when traversal depends on those semantics, or when machine reasoning or validation uses them. Calling every typed record an ontology adds no reliability.

## Identity Before Relationship

Explicit relationships are useful only when their endpoints have stable identities. The string “Acme” might denote a vendor, customer, product, or unrelated organization. A graph edge attached to the wrong Acme is precise but false.

A semantic identifier should have a documented namespace and ownership policy. It may map several source-system identifiers to one domain entity, but the mapping remains a governed assertion with provenance and time bounds. Chapter 8.3 covers entity resolution; for now, the rule is simple: a globally shaped identifier does not prove global identity.

Relationship types need the same discipline. `supplies`, `manufactures`, and `distributes` should have definitions, expected participants, temporal meaning, and source authority. If `supplies` means “has an active contract to supply” in procurement but “appeared in a historical shipment” in analytics, reusing the label hides a contract mismatch.

## A Triple Is Sometimes Too Small

RDF popularized subject–predicate–object statements:

```text
vendor:acme  procurement:supplies  product:bolt-17
```

That relation may be adequate for discovery. A production decision may also need contract, quantity, region, effective dates, confidence, and provenance. Those attributes describe the supply assertion, not only its endpoints.

Common representations include a relationship with properties, an intermediate event or agreement node, or an RDF statement pattern that gives the assertion an identity. The correct choice follows the queries and invariants:

```text
supply-agreement:981
  supplier       vendor:acme
  product        product:bolt-17
  region         region:west
  effectiveFrom  2026-01-01
  source         contract:44
```

This is not a rejection of triples. It is recognition that attribution, modality, quantity, and temporal validity are often first-class domain data. Flattening them forces the model to reconstruct meaning that the source system could have preserved.

## Description, Inference, and Validation

Semantic models can serve three different jobs:

1. **Description** gives systems shared terms and relationship definitions.
2. **Inference** derives statements entailed by asserted facts and axioms.
3. **Validation** checks data against operational acceptance rules.

Do not assume one technology performs all three with the same semantics. RDF Schema and OWL commonly use open-world reasoning: missing information is not necessarily false, and domain or range declarations can infer types rather than reject a statement. Closed-world application requirements such as “every active order must have exactly one tenant” need a validation boundary—application code, database constraints, or a shapes language such as SHACL—chosen and tested for that purpose.

This distinction prevents a dangerous category error. An ontology can say what follows logically from a set of statements without proving that the source statements are true, complete, current, or authorized. Validation can reject a malformed graph without proving that an accepted assertion matches reality.

## Model Only What Changes a Decision

Ontology diagrams grow easily. Reliable domain models grow from competency questions and invariants:

- Which orders may this principal approve?
- Which service dependencies are affected by this deployment?
- Which policy version governed this transaction at commit time?
- Which evidence supports this derived relationship?

For each question, identify required entities, relationships, temporal semantics, authority, and expected query path. Add a concept when it changes retrieval, validation, authorization, or a system decision. Avoid importing a broad public ontology merely because matching vocabulary exists; alignment creates maintenance and identity obligations.

Version the model. Test representative valid and invalid records. Track which queries and tools depend on each term. When a relationship changes meaning, migrate or deprecate it explicitly instead of silently changing the label's interpretation.

## Explicit Does Not Mean Correct

Knowledge graphs make asserted relationships inspectable, traversable, and governable. That is a real improvement over asking a model to rediscover domain structure from prose. But the graph can still contain stale facts, incorrect identity merges, extraction errors, incomplete coverage, and unauthorized edges.

The reliability claim should therefore remain narrow: semantic modeling makes important meanings and relationships available to engineering controls. Reliability comes from the full system—source authority, identity resolution, validation semantics, lifecycle governance, scoped retrieval, and evaluation—not from graph shape alone.
