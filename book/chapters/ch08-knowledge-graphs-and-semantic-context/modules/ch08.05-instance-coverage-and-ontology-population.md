# ch08.05 Instance Coverage and Ontology Population

## A Complete Diagram Can Produce an Empty Answer

An ontology can model every concept in a domain while the graph contains almost none of the instances and relationships needed to answer a real question. The schema looks complete. The retrieval path exists on a whiteboard. At runtime, traversal stops at an unpopulated class or a relationship the ingestion pipeline never created.

I encountered this in an education graph. The source database had teachers, students, assignments, tests, and grades, but it had no explicit classroom entity connecting a group of teachers and students to a subject and time period. That relationship had to be derived from enrollment data. Without it, the graph could not reliably traverse from a student to the work due in a particular class or to the lecture covered that day.

The lesson is not that every missing concept should be inferred. It is that ontology design and population design are separate tasks. A class in the model needs an authoritative source, a derivation rule, or an explicit declaration that it will remain unpopulated.

## “Instance Coverage” Needs a Denominator

The formula “populated entities divided by modeled entities” mixes instances with classes and produces a percentage that has no stable meaning. Four modeled classes and a thousand customer instances cannot sensibly yield 25,000 percent coverage.

Coverage must be defined against an expected population or a task requirement. Useful views include:

- **Class population coverage:** required classes with a usable population divided by classes required for a competency question.
- **Source-record coverage:** eligible source records represented in the graph divided by eligible records in the authoritative source, for a stated snapshot and scope.
- **Relationship coverage:** expected source-backed relationships represented divided by relationships derivable under a specified rule and snapshot.
- **Competency-question coverage:** benchmark questions the populated graph can answer with required evidence divided by the benchmark questions it is intended to support.

Each denominator needs a version, tenant or domain scope, cutoff time, and eligibility rule. If the authoritative source cannot provide a denominator, report counts, samples, or bounds rather than inventing a precise percentage.

## Measure the Path, Not Just the Nodes

Node counts are useful operational signals but weak measures of usefulness. A million `Student` nodes do not answer “What homework is due?” if the graph lacks `enrolled_in`, `assigned_in`, and due-date relationships.

For the education question, a minimal path might be:

```text
Student
  -[enrolled_in]-> CourseOffering
  -[has_assignment]-> Assignment
  -[due_at]-> Timestamp
```

Population monitoring should test whether required paths exist for eligible entities, whether the endpoints resolve to authoritative records, and whether temporal predicates select the correct offering. This is closer to task readiness than global edge density. Dense graphs can be full of duplicate or low-value relationships; sparse graphs can answer their intended questions precisely.

## Population Is an Ingestion Contract

For every class and relationship required by a competency question, document:

- authoritative source or approved derivation;
- source-to-graph identity mapping;
- eligibility and exclusion rules;
- transformation and validation version;
- refresh or event-processing policy;
- expected lag and deletion behavior;
- ownership and authorization scope;
- reconciliation and rebuild procedure.

Derived classroom relationships should retain the enrollment records and rule version that produced them. If an enrollment is corrected, the derived edge must be revised. If the source record is deleted under policy, the projection and its indexes must follow. A graph that cannot be rebuilt from source-backed inputs has quietly become an ungoverned source of truth.

## Decide What to Materialize

The graph does not have to copy every operational fact. It can store identifiers and relationships while hydrating volatile attributes from source systems, or it can materialize a projection when traversal latency and snapshot consistency justify the duplicate state.

The choice is workload-specific. Slowly changing reference data is often easier to project than high-volume events, but change rate alone does not decide placement. Transaction boundaries, query latency, source availability, deletion requirements, and replay cost matter too.

Materialization creates staleness. Federation creates runtime dependency and partial failure. Record the tradeoff per relationship instead of adopting “the graph links; sources store facts” as a universal rule. Sometimes the relationship itself is the operational fact and belongs in the source system.

## Separate Population from Hydration

Population coverage is a property of the graph projection relative to its declared sources and questions. Hydration coverage, introduced in Chapter 7, is a property of one context-assembly attempt relative to its required slots.

A graph can be fully populated for a task while a runtime query times out, producing poor hydration. It can also return every requested slot from a projection that never ingested half the eligible source records. The first is an assembly failure. The second is a population failure. Mixing the metrics hides the responsible subsystem.

Trace the chain:

```text
authoritative source
  -> eligible records
  -> accepted graph instances and relationships
  -> query result
  -> included context
  -> model use
  -> task outcome
```

Each boundary needs its own measure. Reliability work becomes faster when the team can locate where coverage disappeared.

## Validate with Missingness and Replay

Create a small gold set for each competency question. Include ordinary cases and structural absences: a student without an active offering, an assignment missing a due date, a corrected enrollment, a course shared across terms, and a record outside the active tenant.

Then test:

- source-to-graph record reconciliation;
- required-path coverage;
- invalid and unresolved identity rates;
- projection lag and stale-edge rate;
- deletion and correction propagation;
- full rebuild equivalence;
- competency-question answer coverage;
- downstream retrieval and task success.

A useful ontology is not one with the most classes. A useful graph is not one with the most nodes. The system is ready when its populated, authorized, temporally valid paths support the questions it claims to answer—and when missing paths are visible rather than left for the model to guess around.
