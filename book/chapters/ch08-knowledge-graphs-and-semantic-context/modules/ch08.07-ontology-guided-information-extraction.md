# Ontology-Guided Information Extraction

## Constrain the Proposal Space

Chapter 7 treated extracted facts as proposed derived state. An ontology can narrow that proposal space by defining the entities, relationships, roles, and temporal distinctions the application recognizes.

That does not mean “extract only known terms.” A closed ontology improves consistency but can erase genuinely novel information. The pipeline needs an explicit policy: map supported concepts, preserve source text, and route out-of-model candidates to review rather than silently discarding or auto-extending the ontology.

## Compile Semantics into an Extraction Contract

Do not paste an entire ontology into a prompt and call the result governed. Compile a task-specific contract containing:

- allowed entity and event types;
- relationship direction and participant roles;
- required qualifiers such as time, attribution, negation, and units;
- output schema and controlled identifiers;
- examples and counterexamples;
- permitted `unknown`, `ambiguous`, and `out_of_scope` outcomes;
- source-span and provenance requirements.

The contract is smaller, testable, and versioned. The ontology remains the semantic source; the extraction interface contains only the subset needed for this document class and task.

## Separate Guidance from Validation

Ontology guidance can reduce invalid proposals, but model output must still cross deterministic checks. The pipeline is:

```text
source retention
  -> candidate extraction
  -> schema validation
  -> entity resolution
  -> domain constraint checks
  -> source-entailment review
  -> accept, reject, or review
  -> graph projection
```

Domain and range checks can detect a relationship used in an unsupported direction. They cannot prove that the source asserted the relationship or that the resolved entities are correct. Cardinality checks may expose conflicts, but open-world ontology axioms and closed-world ingestion rules must remain distinct as established in 8.2.

## Handle Novelty Deliberately

When an extractor repeatedly emits an out-of-model concept, collect the source passages and evaluate whether the domain model is missing something. Ontology evolution should require definition, ownership, source authority, migration, and competency-question tests. Letting extraction output create new relationship types automatically converts model variability into schema drift.

Measure invalid-type and invalid-path rates, out-of-model frequency, source-entailment errors, unresolved identities, review yield, and downstream task outcomes by contract version. Compare guided extraction with a simpler baseline; ontology guidance earns its cost only if it reduces consequential errors without unacceptable loss of relevant information.

The ontology is a design-time source of semantic constraints. The extraction contract brings those constraints to the ingestion boundary. Validation and policy—not the model's compliance with a prompt—decide what becomes durable graph state.
