# RDF, OWL, SPARQL, and Shapes

## Four Jobs, Four Semantics

RDF, RDF Schema, OWL, and SPARQL are mature Semantic Web standards, but they do different work. Treating them as one “knowledge graph stack” obscures the reliability properties each can and cannot provide.

- **RDF** supplies a graph data model built from subject–predicate–object statements.
- **RDF Schema (RDFS)** supplies vocabulary for classes, properties, subclass relationships, and domain and range semantics.
- **OWL** supplies a more expressive ontology language with formal entailment semantics.
- **SPARQL** supplies graph-pattern query and update facilities over RDF datasets.

Operational systems often add **SHACL**, a W3C recommendation for validating RDF graphs against shapes. Its role is different from OWL reasoning: shapes can express closed-world acceptance expectations that an ingestion or API boundary checks directly.

The specifications are authoritative: [RDF 1.1 Concepts](https://www.w3.org/TR/rdf11-concepts/), [OWL 2 Overview](https://www.w3.org/TR/owl2-overview/), [SPARQL 1.1 Query](https://www.w3.org/TR/sparql11-query/), and [SHACL](https://www.w3.org/TR/shacl/).

## RDF: Identified Statements

An RDF triple has an IRI or blank node as its subject, an IRI as its predicate, and an IRI, blank node, or literal as its object. IRIs provide globally usable names, but two systems using different identifiers do not become aligned automatically, and two systems reusing the same identifier can still disagree about its meaning.

```turtle
@prefix ex: <https://example.com/procurement/> .

ex:vendor-42 a ex:Vendor ;
    ex:supplies ex:product-17 .

ex:product-17 a ex:Product .
```

This representation makes the asserted relation addressable and composable with other RDF data. It does not prove that vendor 42 currently supplies product 17. Provenance, effective time, authorization scope, and source authority still need representation and policy.

## RDFS and OWL: Entailment, Not Ordinary Form Validation

RDFS domain and range statements describe semantic implications. If `ex:supplies` has domain `ex:Vendor`, an RDFS reasoner can infer that a subject using the property is a vendor. It does not necessarily reject data because the subject lacked a pre-existing vendor type.

OWL adds constructs for class equivalence and disjointness, property characteristics, and cardinality restrictions, among others. A reasoner can determine entailments or detect logical inconsistency within the selected OWL profile and implementation. Under the open-world assumption, absence of a `supplies` statement does not normally prove that a vendor supplies nothing.

That behavior is useful for integrating incomplete knowledge. It is a poor substitute for a transactional rule such as “an active vendor record must include at least one approved product before publication.” Put operational acceptance rules in a boundary whose failure behavior is explicit.

## SHACL: Validate an Operational Boundary

A SHACL shape can state that a node targeted as an active vendor must have a tenant identifier and at least one `supplies` value of the expected class. Validation produces a report the host can use to reject or quarantine an ingestion proposal.

```turtle
@prefix ex: <https://example.com/procurement/> .
@prefix sh: <http://www.w3.org/ns/shacl#> .

ex:ActiveVendorShape a sh:NodeShape ;
    sh:targetClass ex:ActiveVendor ;
    sh:property [
        sh:path ex:tenantId ;
        sh:minCount 1 ;
        sh:maxCount 1
    ] ;
    sh:property [
        sh:path ex:supplies ;
        sh:minCount 1 ;
        sh:class ex:Product
    ] .
```

Shapes do not establish source truth either. They establish that a data graph conforms to declared structural expectations under the validator's rules. Test the targeted nodes, entailment regime, severity handling, and behavior for missing or extra values; those choices determine what “valid” means in the application.

## SPARQL: Declarative Graph Patterns

SPARQL matches graph patterns and returns bindings, constructs graphs, asks whether a pattern exists, or describes resources. A bounded query for vendors that supply products in a category might be:

```sparql
PREFIX ex: <https://example.com/procurement/>

SELECT ?vendor ?product
WHERE {
  ?vendor a ex:Vendor ;
          ex:supplies ?product .
  ?product ex:category ex:electronics .
}
ORDER BY ?vendor ?product
LIMIT 100
```

The query is deterministic relative to a particular dataset, entailment regime, and query engine behavior. Reliability still requires tenant scoping, authorization, limits, timeouts, dataset versioning, and tests for missing or duplicate paths. A syntactically valid query can traverse a semantically wrong property direction, which is why generated queries need validation against the intended model.

Allemang and Sequeda tested that boundary in a specific enterprise question-answering benchmark. Their Ontology-based Query Check compared LLM-generated SPARQL paths with ontology semantics and supplied detected errors to an LLM repair step. They report 72% overall accuracy, another 8% classified as “I don't know,” and a 20% error rate on that benchmark [Allemang & Sequeda, 2024](https://arxiv.org/abs/2405.11706). This is evidence that ontology-aware query checking can improve one text-to-SPARQL pipeline, not that an ontology guarantees correct answers across domains. Miriah's essay [“Data as an AI Guardrail: Using Ontologies to Ground Agentic AI”](https://soypetetech.substack.com/p/data-as-an-ai-guardrail) develops the architectural inference from this result and related sources; it should be read as the author's systems argument, not additional benchmark evidence.

## RDF and Property Graphs Are Not Just Syntax Variants

Property graphs model nodes and edges that can carry properties. RDF models statements as triples with standardized semantics and identifiers. Many domains can be represented in either, but translation choices matter: edge identity, multiple identical edges, statement metadata, schema semantics, and inference do not map automatically or losslessly in every design.

Choose from the required behavior:

- RDF is useful when standards-based interchange, shared identifiers, ontology reasoning, or SPARQL federation matters.
- A property graph can be useful when edge-centric properties and operational traversal tooling match the workload.
- A relational schema can be sufficient when relationships and query depth are known, constraints are transactional, and joins remain manageable.

A relational database that stores nodes and edges is still a relational database. It can implement graph semantics and recursive traversal without becoming a native graph engine. Conversely, installing a graph extension does not create a useful ontology. Representation, semantics, storage, and query execution are separate architectural choices.

## Build the Smallest Semantic Stack That Enforces the Invariant

Begin with a competency question and failure mode. If a foreign key and a parameterized join answer the question under the required transaction boundary, use them. If systems need shared RDF interchange, adopt RDF. If logical entailment changes the answer, select and test the necessary OWL profile. If ingestion must reject nonconforming RDF, add shapes or equivalent application validation. If variable graph patterns dominate retrieval, evaluate a graph query engine.

This layered choice improves reliability because each mechanism has a named responsibility. It avoids assuming that an ontology validates records, that a database infers meaning, or that a model should repair semantic errors after retrieval.
