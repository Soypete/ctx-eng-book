# Entity Resolution and Relationship Traversal

## A Precise Edge Can Connect the Wrong Things

A graph can encode a relationship perfectly and still produce dangerous context because one endpoint is wrong. The CRM's `customer-123`, billing's `account-456`, and support's `requester-789` may represent one person, a household, a business account, or three unrelated identities. Similar names and shared contact details do not settle the question.

Entity resolution is the process of deciding which records refer to the same domain entity under a stated policy. It is not clerical cleanup. A false merge can leak one person's orders into another person's context; a missed match can hide evidence required for a decision.

## Preserve Records; Assert Identity

Do not destroy source identity when creating a canonical entity. Preserve each source record and link it to a domain identifier through a versioned resolution assertion:

```json
{
  "domain_entity": "customer:789",
  "source_record": "billing:account-456",
  "relation": "represents",
  "method": "verified_account_link",
  "evidence": ["identity-link:event-981"],
  "effective_at": "2026-08-06T10:00:00Z",
  "policy_version": "customer-resolution-v3",
  "status": "accepted"
}
```

This makes a mistaken merge reversible and supports replay when the resolution policy changes. A canonical entity is a governed view over source records, not necessarily a new source of truth for every attribute. Billing may remain authoritative for plan state while CRM remains authoritative for contact preferences.

## Match in Tiers of Evidence

Resolution signals have different strength:

- a source-owned immutable identifier or verified cross-system link may support automatic acceptance;
- normalized email, phone, address, or name can generate candidates but may be shared, recycled, mistyped, or changed;
- fuzzy string, phonetic, embedding, and relationship similarity can rank candidates but rarely justify an irreversible merge alone;
- graph neighborhoods can help distinguish candidates, but shared neighbors can represent households, employers, or common services rather than identity.

Use thresholds to route decisions, not to manufacture certainty. A high-confidence tier can accept a reversible link under policy. An ambiguous tier goes to review or remains unresolved. A reject tier keeps records separate. Record features and policy versions needed to audit the decision without retaining unnecessary sensitive data.

Evaluate by entity type and consequence. Precision is usually more important where a false match crosses authorization boundaries; recall may matter more for low-risk discovery. Include common-name collisions, shared inboxes, renamed organizations, identifier reuse, transliteration, and adversarially similar records in the test set.

## Traversal Is a Scoped Query Plan

Once a starting identity is established, graph traversal selects connected evidence. It should not mean “walk everything nearby.” A reliable traversal names:

- the authenticated starting entity and purpose;
- allowed relationship types and directions;
- temporal and source-authority filters;
- maximum depth, paths, nodes, cost, and latency;
- authorization checks for nodes, edges, and fetched source data;
- cycle and duplicate handling;
- required provenance for returned paths.

Authorization must be enforced during expansion. Filtering the final subgraph is too late if intermediate nodes influence ranking, leak through counts, or trigger remote fetches. A visible edge also does not automatically authorize the object it points to.

## Query Known Paths; Discover Carefully

Known business questions should use typed patterns. For “which services depend on this database?” the system can follow `depends_on` in the reverse direction under an environment and tenant scope. A variable-depth query is justified because dependency depth is unknown, but relationship type and termination rules are known.

Open-ended discovery needs stricter budgets. Degree can grow quickly, cycles can repeat paths, and high-degree hubs can dominate results. Ranking at each hop may reduce volume, but the ranking features and pruning decisions become part of the retrieval policy. Record which paths were excluded so a missing answer can be diagnosed.

Graph traversal and semantic search are complementary candidate generators. Search can find an unlinked incident document; traversal can follow an explicit dependency chain. Neither should be described as universally exploratory or deterministic. Both need scope, evaluation, and a path back to authoritative evidence.

## Test Identity and Traversal Together

An evaluation that assumes perfect canonical identities misses the most consequential failure mode. Test end-to-end cases:

1. resolve the task's starting record;
2. execute the authorized path pattern;
3. retrieve source-backed facts;
4. assemble a bounded subgraph;
5. verify the answer or action against expected evidence.

Inject a false candidate merge, a split identity, a revoked edge, a stale relationship, a cycle, a high-degree hub, and a cross-tenant neighbor. Measure false-merge and missed-match rates, unresolved cases, unauthorized expansions, path recall, irrelevant path rate, traversal cost, and downstream task success.

Identity resolution gives traversal its starting point. Traversal amplifies every identity decision that precedes it. Reliable graph context therefore depends less on owning a graph database than on making identity assertions reversible and path expansion enforceable.
