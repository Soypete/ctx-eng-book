**Source:** GoogleCloudPlatform — Open Knowledge Format (OKF), Version 0.1 — Draft (July 2026)
**URL:** https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md
**Related:** Google Cloud launch article, Knowledge-Centric Information Systems (arXiv:2607.02609), Conversational Analytics in BigQuery GA

---

## Initial Framing

OKF is Google's attempt to standardize a portable knowledge-artifact format for AI agents. It is intentionally minimal: a directory of Markdown files with YAML frontmatter. The specification defines what OKF requires, permits, and explicitly declines to standardize — and the boundaries are as informative as the features.

The key insight is that OKF packages **potential context** but does not itself constitute a context platform. This distinction mirrors the data-platform analogy: a directory of Parquet files is not a data platform.

---

## What OKF Defines

### Knowledge Bundle

A self-contained hierarchical collection of knowledge documents. Unit of distribution — can be shipped as Git repository, tarball, or subdirectory. Git is recommended because it supplies history, attribution, and diffs.

### Concept Document

One UTF-8 Markdown file per concept with YAML frontmatter and Markdown body. A concept may describe a table, API, metric, policy, runbook, or abstract idea. The file path (excluding `.md`) becomes the concept ID.

### Required and Recommended Metadata

Only `type` is required. Recommended fields include `title`, `description`, `resource`, `tags`, `timestamp`. Producers may add arbitrary fields. Consumers must tolerate unfamiliar fields.

This is intentionally permissive — supports experimentation and portability, but does not create a shared semantic contract.

### Progressive Disclosure

An optional `index.md` at any directory level lists available concepts and subdirectories. Creates a basic traversal pattern: Root index → Domain index → Concept summary → Full concept → Related concept.

This is one of the most important OKF mechanisms for context engineering because it gives agents a way to navigate instead of loading the entire corpus.

## Agent Model

OKF explicitly targets two broad agent roles:

1. **Enrichment agents** — write OKF by walking datasets, drafting concepts, performing model passes, adding citations, schemas, and join paths. Creates a producer pipeline that must handle hallucination persistence as a distinct failure mode.

2. **Consumption agents** — inspect directory index, select relevant concept, read description and body, follow connected concepts, inspect citations, retrieve underlying resource. Combines metadata filtering, hierarchical navigation, lexical/semantic search, and graph traversal.

The architecture expects knowledge to be authored by humans, generated by agents, exchanged across organizations, and consumed by both. This creates a knowledge lifecycle that is a stateful system, not a prompt pattern.

---

## Link Graphs vs Knowledge Graphs vs Linked Data

OKF creates a link graph (documents are nodes, hyperlinks are directed edges), but the specification explicitly states that consumers commonly treat links as **directed, untyped edges**.

The relationship type (e.g., "governed by", "joins with", "supersedes") remains latent in natural language prose. A knowledge graph makes entities and relationships explicit with typed edges. Linked Data adds stable identifiers, resolvable URIs, and machine-readable predicates.

This distinction matters for agents: a link graph is useful for exploratory navigation but weaker for deterministic planning. An agent can follow a link without knowing whether the relationship means "calculates", "contains example", "is deprecated", or "contradicts."

## Data Pragmatics

The phrase **data pragmatics** describes much of what OKF carries:

- **Semantics** — what a concept means (entity definitions, schemas, field meanings)
- **Pragmatics** — how meaning should be interpreted or used in a situation (when to use a table, which join path, whether authoritative, which policy applies)

OKF bodies naturally carry pragmatic information because they support explanatory prose, examples, playbooks, links, and citations.

> Semantics helps the system identify what something is. Pragmatics helps the system determine how it should be used here.

OKF can describe pragmatic guidance but does not make the guidance executable or enforceable. The contract and policy system converts written pragmatics into system behavior.

---

## What OKF Does NOT Solve

OKF does not define:
- A domain ontology
- Typed graph edges
- Canonical identity across organizations
- Authorization
- Freshness guarantees
- Provenance semantics
- Retrieval algorithms
- Contradiction resolution
- Context assembly
- Tool policy
- Agent behavior
- Evaluation

The specification has no authorization model. A concept existing in a bundle does not imply permission to retrieve or act on it.

---

## Security and Governance

Google's Conversational Analytics architecture does not rely on OKF alone. It combines Knowledge Catalog, context bundles, glossaries, BigQuery Graph, verified queries, custom agent instructions, embeddings, citations, inherited BigQuery permissions, and query auditing.

This product architecture is evidence for the book's thesis: **The format provides knowledge, but the surrounding platform provides trust.**

## Failure Modes

1. **Hallucination persistence** — model-generated interpretation stored as reusable knowledge artifact and later treated as authoritative
2. **Untyped-edge ambiguity** — link interpreted as dependency when it was only an example
3. **Type fragmentation** — different domains use `Metric`, `Business Metric`, `KPI`, `Measure` without shared semantics
4. **Prompt injection** — retrieved Markdown contains instructions mistaken for trusted system guidance
5. **Authorization leakage** — search or graph index exposes concept that should have been filtered
6. **Context bloat** — consumer loads too many connected documents instead of using progressive disclosure
