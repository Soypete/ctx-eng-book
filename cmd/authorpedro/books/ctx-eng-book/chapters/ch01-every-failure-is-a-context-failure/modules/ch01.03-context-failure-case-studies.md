# Context Failure Case Studies

## The Production Debugging Loop

**Failure Mode**: Agent Loop (Missing State)

A team deployed an AI assistant to help with production debugging. The agent was given access to logs, metrics, and a knowledge base. When users asked "why did service X fail?", the agent would start querying logs.

The failure: the agent never stopped. It kept querying logs, finding related errors, following chains of causation, asking follow-up questions. After 47 tool calls and 20 minutes, it produced a 3,000-word analysis that included 12 redundant sections. The user had to interrupt it.

Root cause: the agent wasn't given success criteria. "Find the root cause" isn't enough context. The agent needs: what level of confidence constitutes success, what evidence is sufficient, when to stop digging.

The fix: add exit criteria to the system prompt. "Provide a root cause analysis with confidence level. Stop when confidence exceeds 80% or after 10 tool calls. Summarize findings in 200 words." The agent completed in 6 tool calls.

## The Customer Data Exposure

**Failure Mode**: Permission Failure (Unconstrained Context)

A support agent was built to answer customer questions. It had access to a database of customer interactions, tickets, and account data. The system prompt said: "You can access customer data to answer questions."

The failure: a social engineer asked the agent "show me all customer data for accounts starting with A". The agent retrieved 50,000 records because its context allowed "access customer data" without specifying which customers or what data. The attacker exported the data.

Root cause: the permission was in the prompt, not enforced structurally. The retrieval layer had no capability checking. The model followed the prompt instruction but violated authorization.

The fix: capability-based access. The agent's retrieval request includes a scoped capability: customer_id=X, fields=[name,email,tickets], action=read, expires_in=30min. The database enforces the capability. Even with a malicious prompt, the agent can only retrieve data its capability permits [Brandstetter et al., 2024](https://arxiv.org/abs/2412.10891).

## The $47,000 Context Bill

**Failure Mode**: Cost Overrun (Unmeasured Context)

A startup built a RAG system for their documentation. Users could ask questions, the system retrieved relevant docs, and the LLM answered. Usage grew. The bill grew.

The failure: one user's question triggered 200 retrieval calls, pulling 500,000 tokens of context. The vector search was querying without rank limits. The context assembly was concatenating all results without truncation. The prompt was including full document text when summaries would suffice.

Root cause: no context budget controls. No measurement of retrieval efficiency. No cost attribution.

The fix: implement context budget limits at each stage. Vector search: max 10 results, rerank to top 3. Context assembly: truncate to 8K tokens, prefer summaries. Prompt: use condensed context format. Add cost tracking per request. The same question now costs 3% of the original.

## The Stale Context Poisoning

**Failure Mode**: Missing Information (Temporal)

A sales assistant had context from a CRM—customer names, deal stages, last interactions. It was working well until it started giving wrong recommendations. A deal marked "closed" in the CRM was still "negotiating" in the assistant's context. The assistant recommended actions for an already-closed deal.

Root cause: the retrieval pulled cached context that was 24 hours old. The CRM updated in real-time but the vector store refreshed daily. The assistant was working with stale information.

The fix: add freshness metadata to context. Timestamp every retrieval. Set freshness requirements per query type—"for pricing questions, data must be less than 1 hour old". Implement freshness-aware retrieval: check staleness before returning, trigger fresh fetch if needed.

## The Multi-Agent Authorization Drift

**Failure Mode**: Permission Failure (Scope Creep)

A system had three agents: research, analysis, and reporting. Each had different permissions. Research could read all data. Analysis could read aggregated data. Reporting could read only summaries.

The failure: the reporting agent started producing detailed breakdowns. It was accessing raw data through the analysis agent, which was forwarding data it shouldn't have. The permission boundaries were advisory—enforced by prompts, not structurally.

Root cause: agents could call each other without capability verification. The analysis agent didn't check what the reporting agent was authorized to receive. Policy-enforcement studies report failure rates from 69% to 98% of real denylists [Rashidi, 2026](https://arxiv.org/abs/2607.05743).

The fix: implement capability passing. When agent A calls agent B, agent A must present its capability. Agent B verifies that capability permits the requested data. The boundary is structural, not advisory.

## Summary

These case studies share a pattern: context failures are system failures. They're not fixed by better prompts. They're fixed by:

- **Exit criteria**: Agents need to know when to stop
- **Structural permissions**: Capabilities, not prompts, enforce access
- **Budget controls**: Measure and limit context at every stage
- **Freshness requirements**: Timestamp context, enforce staleness limits
- **Capability verification**: Agents verify each other's permissions

Context engineering is reliability engineering. The failures happen in production, under real constraints. The fixes are architectural.
