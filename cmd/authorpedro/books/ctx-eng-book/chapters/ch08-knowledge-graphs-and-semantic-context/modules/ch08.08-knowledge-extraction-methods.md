# Knowledge Extraction Methods

## The Extraction Landscape

Building a knowledge graph requires extracting entities and relationships from data. Different methods suit different scenarios:

- **Named Entity Recognition (NER)** — identifies instances of predefined concept classes
- **Open Information Extraction (OpenIE)** — extracts relationships without predefined schema
- **Rule-based extraction** — uses linguistic patterns for high precision
- **LLM-based extraction** — uses language models for flexible, context-aware extraction

## Named Entity Recognition (NER)

NER identifies mentions of entities in text: people, organizations, locations, dates, quantities. Classical NER uses sequence labeling (CRF, BiLSTM-CRF) trained on annotated corpora.

For knowledge graphs, NER serves a specific purpose: finding mentions of entities that belong to ontology classes. The output isn't just entity spans—it's typed entities ready for relationship extraction.

Key considerations:
- **Predefined types** — NER requires known entity classes (Person, Organization, Location)
- **Domain adaptation** — General-purpose NER models underperform on domain-specific entities
- **Nested entities** — "CEO of Apple" contains both Person and Organization

## Open Information Extraction (OpenIE)

OpenIE extracts relationships without a predefined schema. It identifies subject-verb-object tuples: (Apple, founded, 1976), (Steve Jobs, co-founded, Apple).

Advantages:
- No schema required — extract all relationships, decide validity later
- Novel relationship types — captures relationships the developer didn't anticipate
- Scalable — works on large corpora without manual annotation

Disadvantages:
- No canonicalization — "founded" and "established" are different strings for the same relation
- Noise — extracts many irrelevant or incorrect relationships
- No typing — relationships aren't constrained to valid ontology types

## Rule-Based Extraction

Rule-based extraction uses linguistic patterns for extraction:

- POS tag patterns: `NNP + VBZ + NNP` → (subject, predicate, object)
- Dependency parse patterns: nsubj → dobj paths
- Regex patterns: dates, phone numbers, email addresses

Advantages:
- High precision — patterns capture specific structures
- Interpretable — rules are explicit, auditable
- No training data needed

Disadvantages:
- Low recall — patterns miss variants
- High maintenance — rules must be updated for new patterns
- Domain-specific — rules don't generalize across domains

## LLM-Based Extraction

LLMs compress the NLP pipeline: what required separate tokenization → POS → NER → coreference → relation extraction now happens in one model with a well-crafted prompt.

Key capabilities:
- **Novel entity types** — "Can identify entities that don't match predefined categories" [knowledge graph book]
- **Context-aware classification** — "Given an ontology, LLMs can classify extracted entities into the correct concept classes using in-context learning" [knowledge graph book]
- **Relation extraction** — Extract relationships between typed entities
- **Coreference resolution** — "she", "Jane", "the CEO" → same entity

The cost tradeoff: "Traditional: High capex, low opex. LLM: Low capex, high opex." [relation-extraction research]

## Method Selection

| Method | Precision | Recall | Schema | Training Data |
|--------|-----------|--------|--------|---------------|
| NER | High | Medium | Required | Annotated corpora |
| OpenIE | Low | High | None | Unlabeled text |
| Rule-based | High | Low | None | Linguist expertise |
| LLM-based | Medium | High | Required | In-context examples |

Hybrid approaches work best: use LLM for initial extraction, rules for validation, NER-style classifiers for canonicalization.
