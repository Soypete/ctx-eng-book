# Entity Resolution and Relationship Traversal

## The Identity Problem

Knowledge graphs assume entities have identity. But in reality, the same entity exists across multiple systems with different identifiers. Customer "Jane Doe" in the CRM is "jane.d@example.com" in the billing system and "user_789" in the support system. The graph needs to know these are the same person.

This is entity resolution: the process of determining that two or more records refer to the same real-world entity. Without resolution, the knowledge graph has duplicate nodes for the same entity. Queries return fragmented context. The model sees inconsistent information.

Entity resolution is hard because:
- No universal identifier exists across systems
- Identifiers change (email addresses, employee IDs)
- Similar names don't guarantee identity ("John Smith" × 500)
- Some matches are ambiguous—a person might share a name with a different person

## Resolution Strategies

**Deterministic matching** uses exact rules: if email addresses match, it's the same entity. This is fast and reliable but misses cases where identifiers differ. A common pattern: match on email, phone number, or employee ID. If any exact match, merge.

**Fuzzy matching** uses similarity scoring: if names are 90% similar and addresses are 80% similar, it's likely the same entity. This catches more matches but introduces false positives. Implement with edit distance (Levenshtein), phonetic similarity (Soundex), or embedding similarity.

**Graph-based resolution** uses relationships to infer identity. If entity A and entity B both connect to entity C, they might be the same. A customer with the same address as another customer might be the same household. This catches cases where direct attributes don't match.

The practical approach: layer these strategies. Start with deterministic matching (high precision). Add fuzzy matching for obvious near-matches (high recall). Use graph resolution as a fallback for ambiguous cases.

## Canonicalization

Once resolved, entities need canonical form—a single, authoritative representation. The graph stores one node per entity. All identifiers from all source systems map to that node.

The canonical node includes:
- The primary identifier (system-of-record ID)
- Alternate identifiers (IDs from other systems)
- Merge history (which records were resolved into this node)
- Confidence score (how certain is the resolution)

For context engineering, canonicalization means the agent sees one view of the customer, regardless of which system it queries. The CRM returns customer 123. The billing system returns billing_id=456. The graph maps both to canonical_customer_id=789. The agent sees consistent context.

## Relationship Traversal

Given a starting node, how does the system find relevant context?

The simplest approach: direct neighbors. Start at the user node, retrieve connected orders, tickets, and preferences. This is one hop. It works for simple cases.

Multi-hop traversal: the agent needs context beyond direct neighbors. A user's recent order connects to items, which connect to categories, which connect to recommendations. Three hops to assemble complete context.

The challenge: traversal explodes combinatorially. User has 100 orders. Each order has 10 items. Each item has 5 categories. That's 5,000 potential paths. You can't retrieve all of them.

Controlled traversal strategies:

**Path finding**: Find specific relationship types. "Find all orders from the last 30 days, not their items." Use path patterns, not general traversal.

**Bounded depth**: Limit hops. Maximum two hops from the starting node. Beyond that, require explicit expansion.

**Pattern matching**: Use SPARQL or Cypher to express traversal patterns. "Find customers who ordered products in category X, where X is related to category Y." The query language handles optimization.

**Ranking at each hop**: Score potential paths and retrieve only the highest-ranked. The ranking considers: relevance to the current task, freshness of the connected data, access permissions, and retrieval cost.

## Traversal as Context Assembly

The key insight: relationship traversal is context assembly. The graph doesn't just retrieve nodes—it assembles a subgraph relevant to the current inference.

The agent asks: "What context do I need to answer this question?" The traversal engine finds the minimal subgraph that provides sufficient context. Not everything connected to the user—just what's relevant.

This is different from vector search. Vector search retrieves similar documents. Graph traversal retrieves connected facts. The distinction matters:

- Vector search: "what documents are semantically similar to the query?"
- Graph traversal: "what facts are structurally related to the starting entity?"

Use both. Vector search for exploratory retrieval ("find anything about topic X"). Graph traversal for structured retrieval ("get all facts about entity Y").

## Implementation Patterns

For production systems:

1. **Pre-compute traversal paths**: Analyze common query patterns. Pre-compute likely traversal paths. Cache results for fast retrieval.

2. **Index by relationship type**: Don't just index nodes. Index edges. "Give me all customers who ordered product X" is an edge query, not a node query.

3. **Materialize common subgraphs**: If users frequently need the full context around an order (customer + items + shipping + billing), materialize that subgraph. Don't reconstruct it each time.

4. **Lazy expansion**: Start with one-hop context. Expand to multi-hop only when the agent explicitly requests it. Most queries don't need deep traversal.

## Summary

Entity resolution and relationship traversal are the operational challenges of knowledge graphs.

- Entity resolution: match records across systems, canonicalize to one node
- Resolution strategies: deterministic (exact match), fuzzy (similarity), graph-based (relationship inference)
- Traversal: find paths through the graph, not just nodes
- Controlled traversal: bounded depth, path patterns, ranking
- Context assembly: the graph assembles relevant subgraphs, not full dumps

The knowledge graph's value isn't just storing relationships—it's navigating them intelligently to provide the right context for each inference.

## State of the Stack

This section surveys current tools that implement the patterns discussed in this chapter. They are examples of current engineering approaches, not endorsements or architectural requirements.

### Standards and Formats

- **RDF**: The foundational standard for representing entities and relationships as triples. Provides global identity via URIs.
- **Turtle**: Human-readable RDF serialization for ontology source files and hand-authored vocabularies.
- **JSON-LD**: Embeds semantic identifiers into ordinary JSON for web APIs.
- **SHACL**: Validates concrete graph data against operational constraints—enforces rules like "every customer must have exactly one tenant" or "a relationship must include an effective date."

### Infrastructure

- **Neo4j**: Native property graph database with Cypher pattern-matching queries. Mature traversal and indexing. Note: a property graph is not automatically a semantic graph—additional ontology modeling is required.
- **GraphDB (Ontotext)**: RDF triplestore with SPARQL support and semantic inference. Standards-based ontology support.
- **Apache AGE**: Graph extension for PostgreSQL—useful when graph traversal is one workload among many and operational simplicity matters.
- **PostgreSQL without extensions**: Can represent adjacency lists, closure tables, materialized paths, and recursive CTE traversal. For many context systems, this is sufficient.
- **Apache Jena**: Java framework providing RDF APIs, SPARQL processing, storage, and reasoning components—shows that semantic systems can be assembled as software components.
- **RDFLib**: Python library for parsing/writing RDF, graph manipulation, and SPARQL—useful for experimentation.

### AI-Specific Implementations

- **Graphiti**: Temporal knowledge graphs for agents—explicitly treats facts and relationships as temporally changing with validity intervals and provenance.
- **MemPalace**: Combines vector store, hierarchical metadata, and temporal triples. Emphasizes verbatim storage and deterministic writes. Note: independent analysis suggests much of its performance comes from conventional vector metadata filtering rather than the "memory palace" hierarchy.

### Experimental Projects

- **Markdown-LD**: Community syntax for combining prose and RDF/Turtle-style linked data. Less mature than established serialization formats.

### Questions to Ask Before Adoption

1. Do I need global identity (URIs) or flexible local schemas?
2. Do I require semantic inference (OWL reasoning) or is graph traversal sufficient?
3. Is graph traversal my primary workload, or one among many?
4. How will I handle entity resolution—within-graph duplicates, cross-graph alignment, or both?
5. What validation rules must the graph enforce? Are those expressible in SHACL?
6. Do entities and relationships have temporal validity, or are they permanently true?
7. Who authored the semantic model—was it negotiated with domain experts?
