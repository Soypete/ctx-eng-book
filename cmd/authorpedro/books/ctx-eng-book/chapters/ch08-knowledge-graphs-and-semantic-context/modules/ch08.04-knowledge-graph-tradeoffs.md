# Knowledge Graph Tradeoffs

## Enterprise Architecture—Multiple Topical Graphs

Enterprise AI will not run on a single universal knowledge graph. The data is too diverse, the governance too varied, and the access patterns too distinct.

Instead, production systems will consist of multiple topical graphs:

- An HR graph covering employees, departments, roles, and organizational hierarchy
- A finance graph covering accounts, transactions, budgets, and approvals
- An infrastructure graph covering services, dependencies, and deployments
- A customer graph covering accounts, contacts, interactions, and opportunities
- A product graph covering catalogs, SKUs, categories, and relationships

Each graph has its own ontology, governance, authorization, and lifecycle. An agent working on infrastructure does not need access to HR data. An agent working on finance does not need to see product catalogs.

This aligns with bounded context and data mesh principles. Each domain owns its graph. Each graph exposes controlled interfaces. Agents discover the appropriate graph before retrieving information.

## The Domain-First Approach

Building knowledge graphs before understanding your domain is premature optimization. The recommended approach:

1. **Start with a database** — read-only, curated agent data with simple, well-understood structure.
2. **Put semantics into business logic of tools** — as you build tools, you learn the domain. Semantics emerge from tool relationships, not upfront modeling.
3. **Then build your knowledge store** — once you have a set of tools you understand, you have better domain knowledge. You can now model relationships meaningfully.

Without domain knowledge, RDF modeling is "basically impossible"—you cannot reason about relationships you do not understand. The knowledge graph is the end state, not the starting point. Start with tools, learn the domain, then evolve to graph-based reasoning.

## The Graph Problem: Why Dumb Tools Fail

A knowledge graph gives you a way to traverse and understand semantic relationships. It is how you get the context to add to the data for the LLM. Without a reasoner, a "graph" is just structured storage—a dumb lookup system that knows entities exist but cannot reason about how they relate.

This is the fundamental flaw in most "graph for AI" tools:

- **Brain** — stores entities, retrieves by similarity. No reasoning.
- **Graphify** — extracts triples, indexes them. No semantic constraints.
- **Mem0** — builds memory graphs from conversations. No domain logic.

These tools claim to provide "knowledge graphs" but they provide only structured storage. They know that A relates to B. They cannot tell you if that relationship is valid, required, or semantically coherent.

### The Reasoner Requirement

Sequeda et al. (2024) demonstrate what happens without a reasoner. In their Text-to-SPARQL benchmark, they found that 70% of query errors stem from **domain violations**—queries that use properties in the wrong direction, traverse invalid paths, or reference non-existent relationships. Their Ontology-based Query Check (OBQC) catches these errors by validating queries against RDFS/OWL constraints:

- **Domain rule** — the subject of a property must belong to the property's domain class
- **Range rule** — the object of a property must belong to the property's range class
- **Domain-range consistency** — chained properties must align (the range of one must be the domain of the next)

Without these rules, the LLM generates queries that "feel" correct but execute against the wrong relationships. The graph has no defense. It returns results. They are wrong.

This is why the book's thesis matters: **reliable AI systems require semantic constraints, not just structured storage.** A knowledge graph that cannot reason about its own data is not a knowledge graph—it is a labeled graph.

### The Pragmatic Path

This is why domain-specific agents and tool calls are a stopgap, not a solution. They let you engineer semantic constraints into the business logic of tools before you commit to the overhead of a knowledge graph. You can:

- **Enforce domain constraints** in tool definitions (this parameter must be a User, this action requires Manager role)
- **Validate relationships** in business logic (orders belong to customers, not to products)
- **Build traversal patterns** into agent workflows (find user → find accounts → find transactions)

These patterns are exactly what an ontology provides. The difference is that agents enforce them in code, while a KG enforces them declaratively. The long-term solution is a graph. The pragmatic path is to build the semantics in agents first, then formalize.

### The IE/IR Lesson

This mirrors lessons from information extraction and information retrieval research: you cannot extract meaning from text without linguistic constraints, and you cannot retrieve relevant information without controlled vocabularies. The NLP community learned this in the 1990s. The AI agent community is learning it now.

The graph is not optional. It is the structure that makes semantic constraints enforceable. The question is not whether to use one—the question is whether to build the constraints first in agents (pragmatic) or in the graph directly ( principled). Both paths lead to the same destination: engineered meaning, not guessed inference.

## Structured Domain Classification vs Wikis

Wikis work well for personal knowledge management but struggle with enterprise domain expansion. LLMWiki-style stores (markdown-based, domain-less search) work at moderate scale but fall apart at scale due to recursive query performance.

Structured stores with explicit classification (GBrain's schema packs, MemPalace's Wing/Room/Drawer hierarchy) handle domain expansion better because:

- **Explicit types** constrain what entities can exist
- **Typed relationships** prevent semantic drift
- **Domain-specific schemas** enable intent-aware retrieval
- **Classification hierarchies** allow agents to navigate to the right subgraph

Wing-based domain classification outperforms wiki-based approaches for production systems because the taxonomy is explicit, not emergent. Wikis are fine for personal use. For enterprise AI, you need structural guarantees.

The practical implication: build topical graphs, not a universal graph. Start with the domain that needs explicit relationships most. Expand incrementally.

## Graph Algorithms as Runtime Tools

Ontology defines meaning. Graph algorithms optimize traversal.

This distinction matters. Ontology design (defining entities, relationships, constraints) is a modeling activity. Graph algorithms (finding paths, identifying clusters, computing centrality) are operational activities.

Two classical algorithms become particularly relevant for context engineering:

**Dijkstra's algorithm** finds the shortest path between nodes. In AI systems, "distance" can represent latency, authorization constraints, confidence scores, semantic distance, or retrieval cost. Rather than asking "what is the shortest path," the system asks "what is the cheapest or highest-quality path to assemble the context required for this inference?"

This reframes Dijkstra as a context assembly algorithm. The graph becomes a cost matrix. The retrieval engine computes the optimal subgraph to provide to the model.

**Tarjan's algorithm** identifies strongly connected components—clusters of nodes where each node can reach every other node. These clusters naturally correspond to bounded contexts, organizational units, dependency graphs, or semantic neighborhoods.

Such clusters become ideal retrieval units. Instead of traversing arbitrary paths, the system retrieves entire connected components that represent coherent contexts. This is more reliable than ad-hoc path traversal because the retrieval boundaries are structurally meaningful.

These algorithms are not part of ontology design. They are part of runtime context assembly. The ontology defines what relationships exist. The algorithms determine which subgraphs to retrieve.

## The Reliability Argument

We return to the reliability question: how do we represent meaning instead of text?

Vector databases store text as embeddings. They know that words are similar. They do not know what words mean.

LLMs understand meaning probabilistically. They infer relationships from training data and context. But inference is not guaranteed. The same model might infer a relationship in one prompt and miss it in another.

Knowledge graphs make meaning explicit. Relationships are first-class data. Constraints are enforced. Provenance is tracked. The model does not guess—the graph tells it.

This is the engineering argument for knowledge graphs in AI systems:

- **Determinism**: Relationships are explicit, not inferred.
- **Governance**: Access control applies to edges, not just nodes.
- **Explainability**: The retrieval path is visible and auditable.
- **Reliability**: The model uses known relationships, not guessed ones.

The model's semantic understanding is not replaced. It is grounded. The graph tells the model exactly which relationships are authoritative. The model interprets those relationships in context.

This is the shift from hoping the model infers to encoding relationships explicitly. It is the difference between probabilistic retrieval and deterministic assembly. It is the difference between "the model probably understands" and "the system guarantees it."

Context engineering builds that guarantee. The knowledge graph is the structure that makes it possible.

## Context Sources: APIs, Linked Data, and External Knowledge

### API-First Context Acquisition

The most reliable context comes from APIs, not scraping:

- **Prefer APIs over crawling** — Most data sources (databases, services, SaaS platforms) expose APIs. These provide clean, structured, governed data. Crawling is a fallback, not a default.
- **Direct API usage in tool calls** — APIs can be wrapped as tools. The agent calls an API to fetch context at query time. This is more reliable than pre-indexed data that may be stale.
- **Linked data integration** — REST APIs, GraphQL endpoints, and database connections provide real-time context. The graph doesn't need to store everything—it can federate queries to external sources.

### Augmenting Ontologies with Public Knowledge Graphs

Your custom ontology doesn't exist in isolation. It can be augmented by public knowledge graphs:

- **Wikidata** — Millions of entities across all domains. Query to classify unknown entities ("what is this?") before mapping to your custom ontology.
- **DBpedia** — Structured Wikipedia data. Good for general entity types.
- **YAGO** — High-quality ontological annotations with temporal knowledge.
- **schema.org** — Standardized vocabulary used by search engines. Interoperable with major platforms.

The pattern: Use public KGs for "what is this thing?" classification. Use your custom ontology for "what can this user do with it?" constraints.

### Multilingual Context

LLMs dramatically simplify multilingual knowledge graphs:

- **Single model, many languages** — One LLM can extract entities and relations from dozens of languages without language-specific models.
- **Cross-lingual transfer** — Train on high-resource languages (English), apply to low-resource languages. Zero-shot transfer works with 3-5pp drop, fine-tuning closes the gap further.
- **Code-switching handling** — Modern LLMs handle mixed-language text that breaks traditional NLP pipelines.

For global systems, the LLM-based approach beats language-specific models on cost, maintenance, and coverage.

### The NLP Complexity

Building knowledge graphs involves significant NLP:

- **Named Entity Recognition (NER)** — Identifying entities (people, places, organizations)
- **Relation Extraction** — Extracting relationships between entities
- **Entity Resolution** — Mapping mentions to canonical entities (the "Jane Doe" problem)
- **Coreference** — Knowing that "she", "Jane", and "the CEO" refer to the same entity
- **Temporal reasoning** — Extracting time bounds on relationships

This is where LLMs help enormously. What required separate NLP pipelines (tokenizer → POS → NER → coreference → relation extraction) can now be done with one model and a well-crafted prompt.

> "The NLP complexity hasn't disappeared—it's been compressed. But you'll still want a linguist to review your extraction patterns, especially for edge cases."

## When Graphs Are the Right Tool

Not every problem needs a graph. Here's the decision framework:

### Start with These (Not Graphs)

- **Simple lookups** — retrieve by ID, user, session. Foreign keys handle this.
- **Document retrieval** — semantic search, keyword matching. Vector databases work.
- **Known relationships at write time** — explicit code or JOINs. No traversal needed.

A well-normalized relational database with proper foreign keys achieves basic graph semantics. Third normal form encodes relationships through foreign keys, join tables, and referential integrity.

### Graduate to Graphs When

- **Discovery is the problem** — relationships must be inferred, not asserted
- **Variable-depth traversal** — queries walk chains of unknown length
- **Relationship attributes** — edges carry meaningful metadata (provenance, confidence, temporal bounds)
- **Authorization as traversal** — access depends on walking relationship graphs
- **Multi-hop reasoning** — the model needs A→B→C paths to answer questions

The key insight: **LLMs already understand relationships from training.** Graphs are for engineering those relationships—making them explicit, auditable, and governable. Not for making the AI smart.

### Graphs Are Not Free

Real costs the book doesn't emphasize:

- **Maintenance burden** — ongoing curation, schema changes, entity resolution
- **Ingestion latency** — graph databases can be slow for high-volume streaming
- **Live data mismatch** — real-time data requires sync pipelines (a second system to maintain)
