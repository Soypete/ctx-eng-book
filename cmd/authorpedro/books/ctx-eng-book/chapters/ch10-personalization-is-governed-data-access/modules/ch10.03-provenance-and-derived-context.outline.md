# Provenance and Derived Context

## Argument
Authorization without audit is incomplete. Every piece of context the model receives should be traceable: where did this data come from, who authorized access, what attributes were evaluated? Provenance enables both security auditing and reliability debugging.

## Why it matters (reliability goal)
**Pillar:** Governance
**Reliability Goal:** Enable auditability and debuggability of model context
**Failure Mode:** Cannot trace data leaks or context-driven failures

## Beats

1. **Provenance for Audit** — evidence: existing prose + ledger (Zaveri et al.)
   - Track: source store, specific resource, subject attributes, timestamp, trigger query
   - Enables security auditing: trace what data the model received and why it was permitted
   - Enables reliability debugging: trace what context produced incorrect output

2. **Derived Context Problem** — evidence: GAP (needs research)
   - Models often synthesize new context from retrieved data
   - Derived context inherits provenance from parent—track the chain
   - When model generates a conclusion, what's the provenance of that conclusion?

3. **Provenance Metadata Requirements** — evidence: kg-quality-metrics-notes
   - Source: where did this come from?
   - Owner: who is responsible for this data?
   - Timestamp: when was this data current?
   - Confidence: how reliable is this source?
   - Authorization: was access permitted?

## Conclusion to reach
Provenance is not optional in production systems. It's the difference between "the model somehow accessed this data" and "the model accessed this data because subject=agent-7 had attribute project=aurora."
