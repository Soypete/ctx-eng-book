# Guardrails and Ontology-Based Validation

## Argument

Guardrails and context work in tandem — context reduces hallucination by providing relevant information, while guardrails validate output against structured knowledge to ensure the model stays within defined bounds.

## Why It Matters (Reliability Goal)

**Pillar:** Governance
**Reliability Goal:** Prevent hallucinations, ensure output validity, maintain semantic consistency
**Failure Mode:** Models generate plausible but incorrect, invalid, or unauthorized outputs

## Beats

### Beat 1: The Two Halves of Reliability

- **Context** supplies the model with relevant information (the "what to talk about")
- **Guardrails** constrain what the model can say and do (the "what not to say/do")
- Neither alone is sufficient — you need both

> "Context without guardrails is a model with no brakes. Guardrails without context is a model with no fuel."

### Beat 2: Ontology as Guardrails

- An ontology defines what entities and relations are valid
- Extract only what the ontology allows
- Validate every extraction against ontology constraints
- This is the core insight from Chapter 7 — the ontology guides extraction AND validates it

**Evidence:** See `research/knowledge-graphs/07-informal-text-ie.md` — "The key is providing an ontology that guides what to extract and how to structure it."

### Beat 3: Knowledge Graph as a Guardrail

- The knowledge graph IS a set of constraints
- Query the graph to validate proposed outputs
- If the output contradicts known facts in the graph, reject it
- Graph traversal can validate relationships before they're used

**Evidence:** See `research/_evidence-ledger.md` — "Guardrails reduce hallucinations" entry

### Beat 4: Types of Guardrails

1. **Entity constraints** — Only allow entities that exist in the ontology
2. **Relation constraints** — Only allow relationships defined in the schema
3. **Output schema validation** — Ensure structured outputs match expected formats
4. **Polarity/modality constraints** — Handle negation, possibility, necessity
5. **Quantity constraints** — Validate numeric claims against known values

### Beat 5: Guardrails in the Pipeline

```
User Input → Context Assembly → LLM Generation → Guardrail Validation → Output
                                        ↑
                                  Knowledge Graph
                                  (validation queries)
```

The guardrail step sits AFTER generation, validating against the graph before returning to user.

### Beat 6: Context + Guardrails Synergy

- More context = fewer guardrails needed (model has relevant info)
- More guardrails = less context needed (model is constrained)
- The optimal balance depends on the use case:
  - High-stakes: more guardrails, less trust of model
  - Low-stakes: more context, faster responses

## Conclusion to Reach

By the end of this module, readers should believe:

> "Guardrails and context are complementary — context provides relevant information, guardrails filter invalid outputs. Together they form the governance layer that makes AI systems reliable. The knowledge graph is not just a retrieval source but a validation layer."

## State of the Stack

This section surveys current tools that implement the patterns discussed in this chapter. They are examples of current engineering approaches, not endorsements or architectural requirements.

### Standards and Formats

- **JSON Schema**: Standard for validating structured output and API responses.
- **SHACL**: Shapes Constraint Language for validating RDF graphs against shapes.
- **OWL**: Web Ontology Language for semantic constraints and inference rules.
- **Constraint Validation Libraries**: Zod, Joi, and similar for JavaScript/TypeScript input validation.

### Infrastructure

- **Neo4j**: Knowledge graph for ontological constraints and validation queries.
- **GraphDB**: RDF triplestore with built-in OWL reasoning and constraint validation.
- **PostgreSQL with CHECK constraints**: Simple validation rules for structured data.
- **API Gateways**: Kong, Apigee, and similar for request/response validation at the API layer.

### AI-Specific Implementations

- **Guardrails (Confident AI)**: LLM guardrails framework for input/output validation, topic control, and fact-checking.
- **Rebuff**: Prompt injection detection and guardrails for AI systems.
- **NVIDIA NeMo Guardrails**: Open-source toolkit for building safe LLM applications with configurable guardrails.
- **Google Responsible AI**: Vertex AI's built-in content filtering and safety classifications.
- **Anthropic's Built-in Guardrails**: Native safety features in Claude API—refusal behavior, dangerous content filtering.

### Experimental Projects

- **Semantic Validation Layers**: Various research projects exploring ontology-based output validation. Most are not production-ready.

### Questions to Ask Before Adoption

1. Do you validate input (before model), output (after model), or both?
2. How do you handle validation failures—reject, redact, or attempt修复?
3. What constraints are expressible in your validation layer—entity types, relationships, schemas?
4. How does validation affect latency—synchronous check or async verification?
5. Can the model see validation rules, or are they opaque enforcement?
6. What's the coverage—do you validate all outputs or sample for testing?
