# Provenance Coverage Metrics

## Provenance as Prerequisite for Trust

When do you not need provenance? The question is really: how authoritative do you need it to be?

For customer account information: you need it to be from a system of truth. The data must be real, validated, and modeled correctly.

For Claude explaining customer performance: you want to know queries are real and validated by an analyst, metrics are modeled, data is from your sales system. The infrastructure provides this trust.

For custom tool calls with custom logic: the engineer building the agent is pulling the information through hard-coded queries and searches. That's the provenance and trust—the developer is the source.

For chat with web search: web search is your validation. The model retrieved from the web; that's the provenance.

This is why I don't like just hooking MCP up to a database. What's the trust? Was the data there? Is it drawing conclusions from the data, or just affirming what the human said?

## Defining Provenance by Task and Domain

When you build agents and design the context, provenance is defined by the task and domain:

- What is the least data needed to accomplish the tightly scoped goal?
- Does the user have access?
- Can the agent retrieve it without additional pragmatics?

This is a good pragmatics argument for verification and correctness of tool use.

In a knowledge graph, half the reasoning is from provenance. What ontology did this come from? Is it a good ontology? Is it well modeled? This should also be traced in the agent system.

## Provenance Coverage Defined

**Provenance Coverage = Context with provenance metadata / Total retrieved context**

Example: Retrieved 10KB of context, 3KB has source citation → 30% provenance coverage.

Measures:
- Source present
- Owner present
- Timestamp present
- Confidence present
- Authorization present

## The Partial Provenance Problem

Often you get source but not timestamp. Or timestamp but not confidence. Need per-dimension coverage tracking.

## Measuring in Context Assembly

Each context component should carry provenance:
- Database query: include query time, table, row identifiers
- API call: include response time, endpoint, status
- Search result: include document source, score, crawl time
- Knowledge graph: include ontology source, schema version, extraction method

## Provenance Degradation as Incident

When provenance coverage drops, AI outputs become less verifiable. Should alert when coverage falls below threshold. Track over time: is provenance improving or degrading?

The pattern: treat provenance like observability. If you can't trace it, you can't debug it.
