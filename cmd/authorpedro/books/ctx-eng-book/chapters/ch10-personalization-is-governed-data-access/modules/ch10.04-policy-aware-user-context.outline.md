# Policy-Aware User Context

## Argument
Context engineering must abstract across heterogeneous permission models into a canonical ABAC model, translating subject attributes to each store's native authorization mechanism. The model receives only permitted context, every retrieval is auditable, every decision is traceable.

## Why it matters (reliability goal)
**Pillar:** Governance
**Reliability Goal:** Unified authorization policy across heterogeneous stores
**Failure Mode:** Inconsistent permissions across stores lead to data leaks

## Beats

1. **Bridging Permission Models** — evidence: existing prose
   - Wikis: translate subject attributes to page permission checks
   - Databases: translate to RLS policies with subject identity
   - Knowledge graphs: translate to vertex and edge filters during traversal

2. **Subject Attributes Flow Through Pipeline** — evidence: existing prose
   - Context engineering system carries agent's identity to each store
   - Applies store-specific authorization mechanism
   - Aggregates permitted results with provenance metadata

3. **The Data Platform Approach** — evidence: existing prose + ledger (OKF notes)
   - Instead of hoping the prompt enforces security, build a coherent authorization layer
   - The model receives only permitted context
   - Authorization is a systems engineering problem, not prompt engineering

## Conclusion to reach
The reliability question—who is allowed to see what?—has a precise answer: the data platform decides, store by store, and the context engineering system bridges the models.
