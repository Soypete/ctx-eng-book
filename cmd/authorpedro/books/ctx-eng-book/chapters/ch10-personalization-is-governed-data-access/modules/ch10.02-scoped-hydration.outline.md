# Scoped Hydration

## Argument
Each data store has its own permission model—wiki page-level, database row-level, knowledge graph vertex/edge. Context engineering must bridge these models into a coherent authorization layer that the AI system can trust.

## Why it matters (reliability goal)
**Pillar:** Governance
**Reliability Goal:** Enforce consistent authorization across heterogeneous data stores
**Failure Mode:** Model accesses data from a store with weaker permissions than intended

## Beats

1. **Wiki Permissions** — evidence: existing prose
   - Page-level or namespace-level access control
   - Namespace grouping: engineering, marketing, etc.
   - Context engineering must query wiki permissions API and filter during retrieval

2. **Row-Level Security in Databases** — evidence: existing prose
   - PostgreSQL, SQL Server: security policies filter rows by executing user identity
   - Database enforces automatically—the query doesn't need manual filtering
   - Pattern: agent's context includes DB connection authenticated as the user

3. **Knowledge Graph Access Control** — evidence: existing prose
   - Vertex-level: entity attributes determine read permission
   - Edge-level: relationship between vertices can be sensitive (A employs B)
   - Traversal must filter during graph walk, not after—knowing A→B is itself sensitive

## Conclusion to reach
Scoped hydration is the pattern where context retrieval is permission-aware from the start, filtering at each store before returning data. The agent never sees documents it shouldn't access.
