# Planning and ReAct

The word "agent" conjures something autonomous: a thing that decides, acts, and learns. Something that roams your system like a digital worker, making judgment calls in real-time. This imagery sells products. It also obscures what's actually running in production.

Most agents are workflows wearing a trench coat. Underneath the mystical branding lies a state machine, a loop with exit conditions, a tool-calling protocol, and a harness that manages execution. The model provides the intelligence. The workflow provides the reliability. Neither alone is sufficient.

This distinction matters because it determines where failures happen. When an agent loops forever, it's rarely the model's fault—it's the workflow's exit criteria. When an agent takes the wrong action, it's rarely a reasoning failure—it's the tool definitions or the context provided. The agent is only as reliable as the workflow that runs it.

This chapter examines the systems beneath the agent: ReAct patterns, planning mechanisms, execution harnesses, state machines, durable execution, and event-driven architectures. We answer the reliability question directly: when should the model decide, and when should software decide?

## ReAct and the Reasoning-Action Pattern

The ReAct pattern—Reasoning and Acting—became the de facto standard for agent development after its 2022 introduction. The pattern interleaves thought, action, and observation in a loop:

1. The model reasons about the current state
2. The model selects and executes a tool
3. The system returns the tool's output as observation
4. The model reasons again with new context

This looks like autonomous reasoning. It's actually a structured loop with typed outputs. The "thought" is a specific tool call argument. The "action" is a function invocation. The "observation" is structured input back to the model. Every step is a contract between model and software.

```python
# ReAct loop simplified
while not done:
    thought = model.generate(context + history)
    action = parse_tool_call(thought)
    observation = execute_tool(action)
    context += [thought, action, observation]
```

The power of ReAct is constraints: it forces the model to externalize reasoning in a parseable format. This enables software to intervene. If the model calls a dangerous tool, the harness can reject it. If the model enters an infinite loop, the harness can terminate. The workflow controls the execution; the model controls the decisions within that execution.

The limitation is the same: ReAct constrains what the model can do. Complex reasoning sometimes requires breaking the pattern—holding mental state the tool schema can't express, or making decisions that don't map to available tools. The workflow enables reliability by restricting capability. This tradeoff is fundamental to agent design.

## Planning Patterns

ReAct handles single-step reasoning well. Complex tasks need planning: breaking a goal into steps, executing in order, handling failures.

### Tree Search

For complex decisions, try multiple paths. Tree search explores branching possibilities:

1. Generate N candidate actions
2. For each, simulate the outcome
3. Pick the best, execute, repeat

The model doesn't need to reason perfectly—it generates options, evaluates them, picks one. Software handles the search.

### MCTS (Monte Carlo Tree Search)

MCTS adds statistical sampling to tree search. Instead of simulating every branch, sample randomly and accumulate scores. Good for large search spaces where exhaustive exploration is impossible.

In agents: generate candidate plans, estimate success via the model itself ("Will this plan achieve X?"), pick the highest-scoring, execute.

### Plan Refinement

Start with a rough plan, refine as you go:

1. Model generates initial plan (e.g., "search for X, then filter by Y, then summarize")
2. Execute first step
3. Observe result
4. Model refines remaining plan based on what actually happened

This is "plan then react." The model plans, but the plan is soft—software executes step-by-step, model adapts.

### Why These Matter

Planning patterns move complexity from the model's context window to software infrastructure. Instead of asking the model to hold a complex plan in context, the software maintains the plan state, model generates refinements.

The reliability gain: if the model forgets the plan, software still has it. If the model diverges, software can revert to the last known good plan.

## State of the Stack

This section surveys current tools that implement the patterns discussed in this chapter. They are examples of current engineering approaches, not endorsements or architectural requirements.

### Standards and Formats

- **ReAct Protocol**: De facto standard for interleaving reasoning, action, and observation. No formal specification but consistent pattern across providers.
- **Agent Protocol ( Anthropic)**: Standard for agent-to-agent and agent-to-tool communication.

### Infrastructure

- **LangGraph**: State machine framework for agent workflows. Implements ReAct patterns with explicit state management.
- **LangChain**: Agent framework with built-in planning, tool use, and execution harnesses.
- **AutoGen**: Microsoft's multi-agent framework with conversation patterns and state management.
- **Temporal**: Durable execution platform for long-running agent workflows with automatic retry and state persistence.
- **Prefect / Dagster**: Workflow orchestration for agents with complex multi-step plans.

### AI-Specific Implementations

- **OpenAI Agents SDK**: Lightweight agent framework with built-in tool use and state management.
- **Claude Code**: Anthropic's agent implementation with built-in planning and execution.
- **OpenAI Swarm**: Experimental multi-agent orchestration framework.

### Experimental Projects

- **Agent Scaling Research**: Various projects exploring multi-agent coordination, consensus, and swarm behavior. Not production-ready.

### Questions to Ask Before Adoption

1. Does the workflow use a state machine (explicit states and transitions) or a simple loop (while not done)?
2. How are exit conditions enforced—can the model override them?
3. What's the retry policy for failed tool calls—automatic, bounded, or none?
4. Can the workflow persist state across requests, or is each request fresh?
5. How do you handle long-running agents—what happens if the request times out?
6. Is planning explicit (software maintains plan state) or implicit (model holds plan in context)?
