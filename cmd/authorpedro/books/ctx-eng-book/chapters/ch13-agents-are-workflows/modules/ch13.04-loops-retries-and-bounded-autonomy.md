# Loops, Retries, and Bounded Autonomy

## The Decision Boundary

We began with a question: when should the model decide, and when should software decide? We now have a framework to answer it.

Software should decide for:

- **Structural concerns**: Loop execution, state transitions, iteration limits, completion detection
- **Infrastructure concerns**: Error handling, timeouts, retries, checkpointing, scaling
- **Safety concerns**: Authorization, rate limiting, cost caps, dangerous action blocking
- **Governance concerns**: Audit trails, compliance requirements, access controls

Model should decide for:

- **Reasoning concerns**: How to solve the task, which tools to use, how to interpret results
- **Context concerns**: What information is relevant, how to combine multiple sources
- **Output concerns**: What to say, how to format, what details to include
- **Adaptation concerns**: How to respond to unexpected situations within the workflow

The boundary isn't fixed. Different agent architectures place different decisions in each domain. Fully autonomous agents let the model control nearly everything. Highly structured agents let the model control only tool selection. The right boundary depends on reliability requirements, task predictability, and safety constraints.

Here's a practical heuristic: if the decision can be expressed as rules, codify it in software. If the decision requires judgment beyond rule expression, let the model decide—with software guarding the boundaries.

The model decides how to reason. The workflow decides how to reason safely.

## Loops and Retries

Loops are where agents become unreliable. A loop is a context failure waiting to happen. Every iteration adds context, and context compounding is the enemy.

### Loop Patterns

The simplest loop: while not done, call model. Each iteration appends the previous output to context. After 10 iterations, the model sees 10 previous attempts. This creates:
- Context bloat (more tokens, higher cost)
- Repetition drift (model starts echoing itself)
- Hallucination accumulation (errors compound)

Better patterns:

**Fixed iteration**: Call model N times, no more. Hard limit. Context doesn't grow beyond N * output_size. Simple, predictable, but might stop before completion.

**Convergent exit**: Define convergence criteria. "If the last 3 outputs are similar enough, stop." Needs a similarity metric. More flexible but adds complexity.

**Checkpointer loop**: On each iteration, snapshot the state. If the model diverges or produces garbage, roll back to the last good state and try a different approach.

### Retry Strategies

Retries are infrastructure, not reasoning. A retry is: "That didn't work, try again." The model doesn't need to decide to retry—software should handle it.

**Exponential backoff**: Wait 1s, then 2s, then 4s. Good for transient failures (network blip, rate limit).

**Fixed retry**: Try N times with same delay. Good for flaky but eventually succeed (e.g., a service that sometimes times out but works on retry).

**Circuit breaker**: If failures exceed threshold, stop retrying and fail fast. Prevents cascade failures when a service is truly down.

### Exit Conditions

Exit conditions are software's job. The model shouldn't decide when to stop—that's the boundary.

- **Max iterations**: Hard cap, never exceed
- **Quality threshold**: If output meets quality bar, exit
- **Staleness**: If no progress in N iterations, exit
- **Resource exhaustion**: If time/money exceeds budget, exit

### Bounded Autonomy

The principle: give the model freedom within boundaries. It can decide how to solve the task, but software controls:
- How many attempts it gets
- How long it can run
- What resources it can consume
- What actions are allowed

This is bounded autonomy. The model is autonomous within its bounds, and software enforces the bounds.
