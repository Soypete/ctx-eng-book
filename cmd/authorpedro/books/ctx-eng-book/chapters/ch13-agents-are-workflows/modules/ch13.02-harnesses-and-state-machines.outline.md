# Harnesses and State Machines

## Argument
The harness is where reliability lives or dies. Most agent failures are harness failures. Agents are literally state machines—discrete states, transitions based on conditions, memory of past states.

## Why it matters (reliability goal)
Tie to Pragmatics pillar: software decides for structural/infrastructure concerns, model decides for reasoning concerns. The boundary between these domains is the first design decision.

## Beats

1. **The Harness Problem** — evidence: existing prose
   - Loop management, context assembly, tool execution, state persistence, observability, safety enforcement
   - Example: harness without iteration limits → infinite loop consuming tokens

2. **State Machines and Agent State** — evidence: existing prose + ledger (Generative Agents paper)
   - Agents as literal state machines, not metaphor
   - Simple agents: IDLE → REASONING → ACTING → OBSERVING
   - Complex agents: IDLE → PLANNING → EXECUTING → VALIDATING → (COMPLETE or RECOVERING or FAILED)

3. **State Machine Design** — evidence: existing prose
   - Model selects transitions; software enforces valid transitions
   - Surfaces hidden complexity: decision points, conditions, failure modes

## Conclusion to reach
The reader should believe that modeling agents as state machines makes behavior explicit, testable, and debuggable. The model handles reasoning within states; the state machine handles transitions between states.
