# Context Precision and Context Recall

## The Precision Overloaded Problem

Precision and recall are how we determine false positive and false negative ratios. When we use these, we can say: how accurate is our data as opposed to if we looked it up from a canonical encyclopedia? Did the agent get the correct information in the correct way?

In context engineering, especially when tool calls are how we represent information (as opposed to putting it in the system prompt directly), we have to rely on:

- IR (information retrieval)
- Data sources like Wikidata
- Inferences from data scrapers
- Data sourcing algorithms
- Data classifiers
- Knowledge graphs

The failure modes compound:

1. **Bad pragmatics** — the tool call format or instructions were wrong
2. **Tool did the wrong thing** — often a symptom of bad pragmatics
3. **Wrong relationships** — can be bad hallucination from the LLM, or caused by building a bad KG
4. **Faulty data** — the underlying source data was incorrect

Each of these layers has its own precision and recall. The Five V's (Volume, Velocity, Variety, Veracity, Value) have long been the measure of statistically evaluating data health. Now we're saying: it is a calculus on statistics — we need to take the integral over all these things to get the area under the curve.

## The Context Engineering Precision Equation

```
CP = Context Precision = Useful Context / Retrieved Context
CR = Context Recall = Relevant Context Retrieved / Relevant Context Available

The composite score is a weighted sum across all layers:

CE = Σ(w_i × P_i) / Σ(w_i)

Where:
- P_i = precision at layer i
- w_i = weight of layer i (importance for this specific task)
- Layers: IR, Wikidata, KG, Tool Call, Data Source

Or as an ODE to track quality over time:

d(CQ)/dt = Σ(w_i(t) × dP_i/dt) - λ × (1 - CQ)

Where:
- CQ = Context Quality (0-1)
- w_i(t) = time-varying weights (task-dependent)
- dP_i/dt = rate of change in precision at layer i
- λ = degradation rate (how fast quality decays without intervention)

The steady-state solution gives us our target context quality.
```

## Why This Matters for Reliability

When we don't distinguish these precision types, we can't diagnose failures. A system might have high IR precision (retrieved relevant documents) but low context precision (the documents contain mostly irrelevant information). Or high Wikidata precision (granular timestamps) but low tool call precision (the agent called the wrong tool).

The equation above gives us a framework to:
- Measure each layer independently
- Identify which layer is degrading
- Calculate composite context quality
- Track reliability over time

## Context Precision in Practice

Consider:

```sql
SELECT * FROM table WHERE created_at > x
```

But we only need 2 of 10 columns. Or 2 of 10 rows. This happens all the time when AI queries data — and honestly, when engineers explore data too.

Explicit column selection is rare. Most queries use `SELECT *` and let the consumer filter. But context precision measures: did we retrieve only what we actually needed?

**Why this matters:**
- **KGs help** — semantic relationships narrow down rows automatically
- **Columnar DBs with star schema** — dimensions narrow what to pull
- **Code parsing** — loading an entire file when you only need one function. This is where LSP navigation is more effective than full-file context injection

The principle: if the domain is well-defined, don't leave the LLM to pull and guess. Build a narrow-scoped agent with one function, model the data appropriately, give it correct information about how to use the information, and give it the least data possible.

This is how we build computationally efficient systems. More data is more bits. Reducing bits used is always good. Decreasing bits directly decreases latency.

The failure mode: we retrieve everything and let the model figure it out. High IR precision (found relevant documents), low context precision (documents contain mostly irrelevant information).

This is what made Sourcegraph such a cool tool when it first came out. Instead of loading an entire repository into context, you could navigate to exactly what you needed: this function, that reference, this symbol. Precision by navigation, not by retrieval.

## Context Recall: Bounding the Denominator

Context recall is harder to measure because we rarely know the denominator: what relevant context actually exists?

But we can bound it by domain. Consider building an agent whose job is to schedule ads for the marketing team:

1. **Start with marketing attribution data** — see what sources perform best
2. **Get a list of sources** — ad platforms, budgets, creative assets
3. **Get topics** — campaigns, audiences, verticals
4. **Get revenue goals** — targets, projections
5. **Get potential product launches** — upcoming releases

These sources can be hard-coded into the agent by:
- A domain-linked knowledge graph
- A list of fetch data tool calls for each step in a workflow
- Static queries or charts ingested from an analytics page

By giving agents narrow tasks and building ontologies for domains, you can narrow down what they need. The "relevant context available" becomes bounded.

There are still other sources they could pull from the internet — brand studies, new influencers, industry trends — but data available there is better parsed by a human until we can narrow down what is valuable and repeatable. Then the agent can act and make calls on those things.

The proxy for context recall: given a bounded domain, how many of the known-relevant sources did the agent successfully retrieve?

## The Context Efficiency Trade-off

Context = cost. In the cost/token model, every token has a price. But also: context = RAM/CPU processing on hardware. You need a large KV cache for large context processing, and that lives on GPU memory.

This creates a fundamental trade-off:

- **More context** = higher recall potential (you might find what you need), but higher cost and latency
- **Less context** = higher precision risk (you might miss something), but lower cost and faster

The model can only hold so much context at once because it's a prediction system. No matter how many instructions you provide, some will be selectively ignored. That's why context engineering is never about more information — it's about the right information, at the right time, in the right place.

The closer information is to the system prompt or the beginning of conversation, the less likely it is to be used as the plan evolves.

This is why adding more instructions doesn't fix context problems. It makes them worse. The mistake is putting everything into history and hoping the model figures it out.

**When to prioritize precision:**
- Narrow, well-defined tasks where the domain is bounded
- High-cost operations where incorrect context leads to expensive mistakes
- When you have a KG that can narrow down exactly what's needed

**When to prioritize recall:**
- Exploratory tasks where you don't know what you don't know
- Creative tasks that benefit from broad inspiration
- When the cost of missing information exceeds the cost of retrieving more

The token budget constraint forces this trade-off every time. There's always a finite window.

## Measuring in Production

Production measurement is what separates toy systems from production services. I wrote about this in my Substack post "Building Production-Grade AI in Go" and gave a talk at GoWest 2025.

The core metrics I track:

```
successful_llm_gen_count
failed_llm_gen_count
empty_llm_response_count

twitch_message_received_count
twitch_message_sent_count
```

These are measured through expvar in the actual bot code:

```go
var (
    successfulLLMGenCount = expvar.NewInt("successful_llm_gen_count")
    failedLLMGenCount     = expvar.NewInt("failed_llm_gen_count")
    emptyLLMResponseCount = expvar.NewInt("empty_llm_response_count")

    twitchMessagesReceived = expvar.NewInt("twitch_message_recieved_count")
    twitchMessagesSent     = expvar.NewInt("twitch_message_sent_count")
)
```

The request flow:

```go
RecordTwitchMessageReceived()

reply, err := b.llm.Generate(ctx, msg.Text)
if err != nil {
    RecordLLMFailure()
    return
}

if strings.TrimSpace(reply) == "" {
    RecordEmptyResponse()
    return
}

RecordLLMSuccess()
RecordTwitchMessageSent()
```

No mockups. These are actual names and increments from the repo.

This is how you make AI behave like a production service instead of a toy. The observability stack (Prometheus + Grafana) lets me watch queue depth rise, P95 latency shift, error rates spike, and GPU usage change when the audience spams the bot.

For context precision specifically, the "empty_llm_response_count" is a proxy: if the model returns empty responses, the context wasn't useful enough to generate output. The ratio of successful to empty responses tells you whether your context precision is high enough to drive useful behavior.
