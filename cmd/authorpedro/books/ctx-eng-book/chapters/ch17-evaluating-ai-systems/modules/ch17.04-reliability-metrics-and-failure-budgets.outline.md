# Reliability Metrics and Failure Budgets

## Argument
Beyond evals, you need system-level metrics (latency, error rate) and failure budgets—explicit tolerance for unreliability inspired by SRE practices.

## Why it matters (reliability goal)
Tie to Pragmatics pillar: budgets force explicit tradeoffs between reliability and cost, ensuring pragmatics decisions are data-driven, not emotional.

## Beats

1. **Reliability Metrics**
   - Latency: p50, p95, p99 — reliability under load
   - Error rate: percentage of requests producing errors
   - Track by model version, endpoint, time of day

2. **Failure Budgets** — evidence: ledger (Observability — OpenTelemetry)
   - Accuracy budget: what % of requests can produce incorrect outputs?
   - Latency budget: maximum acceptable latency
   - Availability budget: uptime percentage (99.9% = ~8 hrs/year)
   - Cost budget: maximum cost per request/day/month
   - Calculate from user needs, work backward to budget thresholds

3. **Evaluation Is Continuous** — evidence: existing prose
   - No finish line — models update, user behavior changes, failure modes evolve
   - Eval suite grows with system, incorporating every bug seen
   - Culture: treat evals as first-class artifacts

## Conclusion to reach
The reader should believe that reliability is a numbers game—you define budgets, track consumption, and make decisions systematically.
