# Context Engineering as the Research Phase

## Argument
Context engineering is the permanent investment. Model modification is the tactical adjustment. Build the context engineering platform first—modify the model only when the platform has revealed modification is necessary.

## Why it matters (reliability goal)
Tie to Pragmatics pillar: context engineering forces articulation of the problem. Model modification without this exploration wastes resources on expensive solutions to cheap problems.

## Beats

1. **The Decision Framework** — evidence: existing prose
   - Step 1: establish baseline with prompting alone
   - Step 2: build context engineering, measure reliability
   - Step 3: identify signal (retrieval, prompting, orchestration)
   - Step 4: only then consider model modification

2. **What Persists After Model Modification** — evidence: existing prose + ledger (The Scaffolding Tax)
   - Fine-tuned model still needs retrieval
   - LoRA adapter benefits from structured prompts
   - SLM requires more scaffolding
   - Retrieval system, state schema, authorization policies persist across model changes

3. **The Reliability Question** — evidence: existing prose
   - "Is this a model problem or a context problem?"
   - Most teams backtrack after fine-tuning—problem was retrieval all along
   - Context engineering first isn't conservative, it's efficient

## Conclusion to reach
The reader should believe that context engineering is the research phase; model modification is the engineering phase. Do the research first. The model will change; your context engineering system endures.
