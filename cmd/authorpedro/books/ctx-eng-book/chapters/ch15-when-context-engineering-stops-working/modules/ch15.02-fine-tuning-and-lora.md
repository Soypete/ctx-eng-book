# Fine-Tuning and LoRA

## Why LoRA Makes Sense When It Does

Full fine-tuning is expensive. It modifies all model weights, requires substantial training data, and is hard to iterate on. LoRA (Low-Rank Adaptation) offers a middle ground.

LoRA adds small trainable adapter matrices to the model while keeping the base weights frozen. This has practical advantages: you can train on modest hardware, use smaller datasets, and swap adapters without changing the base model. Multiple adapters can coexist, allowing you to specialize for different tasks.

LoRA can reduce the number of trainable parameters by 10,000 times and the GPU memory requirement by 3 times compared to full fine-tuning [Hu et al., 2021](https://arxiv.org/abs/2106.09685). It performs on-par or better than fine-tuning in model quality despite having fewer trainable parameters, higher training throughput, and—unlike adapters—no additional inference latency [Hu et al., 2021](https://arxiv.org/abs/2106.09685).

LoRA makes sense when you have stable workflows and clear evaluation criteria. You need both because LoRA training requires feedback loops. If you can't measure whether the adaptation is working, you can't iterate.

The stability requirement matters too. LoRA adapters are most effective when the task is well-defined and doesn't change frequently. If your requirements shift constantly, you'll spend more time retraining adapters than running the system. Context engineering handles variability better than trained adapters.

Here's the practical test: can you write 50-100 examples of the exact input-output behavior you want? Can you run automated evaluations comparing your LoRA model to the base model on these examples? If yes, LoRA is viable. If no, stay with context engineering.

LoRA is not a way to avoid thinking about the problem. It's a way to implement a solution you've already validated through context engineering.

## Fine-Tuning Considerations

### Full Fine-Tuning vs LoRA

Full fine-tuning:
- Modifies all model weights
- Requires substantial training data (thousands of examples)
- Needs significant GPU memory
- Can achieve highest quality for specific tasks
- Risk: catastrophic forgetting (loses general capabilities)

LoRA:
- Trains only small adapter matrices
- Requires less data (hundreds of examples)
- Runs on modest hardware
- Multiple adapters can coexist
- Lower risk of forgetting

The choice: if you have the data and compute, full fine-tuning can be more powerful. If you want to iterate quickly and keep base model capabilities, LoRA.

### Training Data Requirements

Fine-tuning needs:
- **Quantity**: Full fine-tuning = thousands of diverse examples. LoRA = hundreds of high-quality examples.
- **Quality**: Clean, consistent, representative of the target distribution. Garbage in = garbage fine-tuned.
- **Coverage**: Examples should cover the expected input space. If the model will see X but was never trained on X, it won't work.
- **Evaluation set**: Hold out data to measure actual improvement.

### Evaluation Approaches

Fine-tuning without evaluation is useless. Approaches:

- **Benchmark comparison**: Run on standard benchmarks before/after
- **Human evaluation**: Have humans rate outputs
- **Automated metrics**: Task-specific metrics (exact match, F1, BLEU)
- **A/B testing**: Deploy both, compare real-world performance
- **Regression testing**: Ensure you didn't break what was working

The key: you need a measurable signal that fine-tuning improved something. Without that, you're just guessing.

## The Gradient-Like Path: From Context to LoRA

Anthropic's J-space research (July 2026) shows that prompts work by steering the model's internal workspace - the J-space. A prompt puts certain concepts in the "verbalizable" representation space, and the model reasons with those.

This means there's a gradient-like path from context engineering to model modification:

1. **Context engineering** — Find the minimal prompt that puts the right concepts in the J-space
2. **Prompt optimization (DSPy)** — Automatically search for better prompts (jacobian minimization: try configurations, measure output, converge)
3. **LoRA adaptation** — If prompts can't achieve the desired J-space state, train an adapter to modify the model's internal representations

The jacobian connects these levels. DSPy's "gradient-like" optimization isn't just a metaphor - it's literally searching the prompt-to-output jacobian for better configurations. When that search fails, you've hit the boundary of what context can do, and model modification (LoRA, fine-tuning) becomes the next step.

This is why context engineering is the research phase. You explore the problem space through prompts, measure what's possible, and when you hit the ceiling - that's when you invest in training.
