# Fine-Tuning and LoRA

## Argument
LoRA and fine-tuning make sense only after context engineering has revealed the boundary of what's possible. LoRA is the parameter-efficient path—when you have clear input-output behavior and evaluation criteria.

## Why it matters (reliability goal)
Tie to Efficiency pillar: LoRA reduces trainable parameters 10,000x vs full fine-tuning while maintaining performance parity. This changes the cost equation for model modification.

## Beats

1. **Why LoRA Makes Sense When It Does** — evidence: ledger (LoRA Parameter Reduction, LoRA Performance Parity)
   - 10,000x fewer trainable parameters, 3x less GPU memory [Hu et al., 2021](https://arxiv.org/abs/2106.09685)
   - Performs on-par or better than fine-tuning with no additional inference latency [Hu et al., 2021](https://arxiv.org/abs/2106.09685)
   - Requires stable workflows and clear evaluation criteria

2. **Full Fine-Tuning vs LoRA** — evidence: existing prose
   - Full: all weights, thousands of examples, GPU memory, catastrophic forgetting risk
   - LoRA: adapter matrices, hundreds of examples, modest hardware, lower forgetting risk

3. **Training Data Requirements** — evidence: existing prose
   - Quantity: full = thousands, LoRA = hundreds
   - Quality: clean, consistent, representative
   - Coverage: must cover expected input space
   - Evaluation: hold out data to measure improvement

4. **The Gradient-Like Path: Context → DSPy → LoRA** — evidence: existing prose + ledger (Context Cost of Composition)
   - Context engineering finds minimal prompt
   - DSPy optimizes prompts (jacobian minimization)
   - LoRA modifies internal representations when prompts fail

## Conclusion to reach
The reader should believe that LoRA is not a way to avoid thinking about the problem—it's a way to implement a solution already validated through context engineering.
