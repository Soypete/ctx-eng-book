# Diagnosing Model Problems

## Argument
Context engineering is the research phase—it reveals whether a problem is in the context or the model. Before expensive model modification, teams must honestly answer: is this a model problem or a context problem?

## Why it matters (reliability goal)
Tie to Pragmatics pillar: context engineering first prevents wasted resources on expensive solutions to cheap problems. Model modifications are irreversible; context engineering is reversible.

## Beats

1. **The Reliability Ladder** — evidence: existing prose (prompting → context → model modification)
   - Prompting: cheap, reversible, requires expertise
   - Context engineering: development time, infrastructure, reversible
   - Model modification: compute cost, training data, committed

2. **Context Engineering as Exploration** — evidence: existing prose (reveals boundary between capability and context problems)
   - Retrieval returns right docs but model fails → model problem
   - Retrieval returns wrong docs → context problem

3. **Three Signals It's Time to Modify the Model** — evidence: existing prose
   - Signal 1: retrieval cannot solve (knowledge boundary)
   - Signal 2: prompting cannot solve (capability alignment)
   - Signal 3: orchestration cannot solve (reliability boundary)

## Conclusion to reach
The reader should believe that context engineering is the exploration phase that reveals whether model modification is necessary. The reliability question—model or context?—is the most important question in production AI.
