# Tool Schemas and Function Calling

## Argument
JSON/XML schemas are context engineering tools—not just validation, but boundary definition. Schemas tell the model "here's the shape of valid output."

## Why it matters (reliability goal)
Tie to Semantics pillar: schemas define what's possible. A well-designed schema constrains invalid outputs, enables validation, and defines action boundaries. Poor schemas = unreliable behavior.

## Beats

1. **Schemas as Context Boundaries** — evidence: existing prose
   - Schema tells model: valid inputs, required fields, allowed values
   - Multi-purpose: constrain, document, validate, define boundary

2. **Tool Selection as Retrieval** — evidence: existing prose + ledger (tool calls as encapsulated relationships)
   - Model matches user request to tool description
   - Tool descriptions are critical—must include "when to use"

3. **Tool Selection Failures Are Context Failures** — evidence: existing prose
   - Wrong tool selected = descriptions don't distinguish, request ambiguous, context missing
   - Fix: improve descriptions, add examples, provide disambiguation context

4. **Constraining Action Through Tool Design** — evidence: existing prose
   - Principles: narrow scope, explicit schemas, clear outputs, purposeful descriptions, bounded results, failure modes
   - Tool = boundary, schema = constraint, description = context

5. **Semantic Contracts** — evidence: ledger line 1352-1362
   - Tool descriptions should be pragmatic contracts: purpose, use_when, do_not_use_when, preconditions, effects, evidence_required

## Conclusion to reach
The reader should believe that tool design is the ultimate reliability mechanism—design the tool space carefully, and the model operates reliably within it.
