# Hydration Coverage and Retrieval Success

## The Context Assembly Problem

Context is assembled from multiple sources—databases, APIs, search indexes, knowledge graphs, memory stores. Any source failure creates incomplete context. The worst failures are silent.

I've seen two severe context assembly failures:

**The single chat window problem.** A user insists on one chat window for all work. After months and thousands of messages, all that information has been compacted away. The model sees a few recent turns. Everything before is gone. Context that existed is context that was lost.

**The Ollama compaction problem.** I built pedrocli over Christmas break running on my MacBook with Ollama. The context window was 32k tokens. Every ~10 tool calls, it had to compact. Each compaction restarted the session—it lost all the information it had used before. You cannot tell the model what data is important to keep. You cannot predict what it will discard.

Beyond lost context, there are data leakage failures:

- **Credit card leakage.** Early booking agents needed credit card numbers to book flights. They invented them, leaking from test data. The model hallucinated real-seeming but fake credentials.
- **Social engineering.** A podcast described a case where an employee convinced a bot that a coworker was dying—extracting emergency contact information that wasn't needed and was actually a data violation.

There's also intent drift from context. When building pedrocli, I gave it the tool "find directory." It kept calling "find_directories"—a function that didn't exist. The context it had accumulated pushed it toward the wrong tool name, and it couldn't recover.

## Hydration Coverage Defined

Context engineering needs a runtime metric: how much of the required context was successfully retrieved from distributed sources?

**Hydration Coverage = Retrieved sources / Required sources**

Example: A customer request needs context from CRM + Billing + Identity + Support = 4 sources. The system retrieves CRM + Identity = 2 sources. Hydration coverage = 50%.

This is a runtime metric, not design-time. You design the sources. You measure the retrieval.

## Failure Modes

Several things can break hydration:

- **Source unavailable** — database down, API timeout
- **Authorization denied** — scoped hydration fails, user lacks permission
- **Query fails** — bad query syntax, missing index
- **Data not found** — entity doesn't exist in the source
- **Stale data** — cache miss, TTL expired, data changed

Each failure mode produces incomplete context. The model doesn't know it's missing something. It just generates output with what it has.

## Measuring Hydration in Production

Trace each context assembly request. Record per-source success or failure. Aggregate hydration coverage over time. Alert when coverage degrades.

The pattern: instrument the context assembly layer, not the model. The model doesn't know it received partial context. Your system needs to know.

## The Partial Context Cascade

What happens when hydration is less than 100%?

The model receives incomplete context. It may hallucinate to fill the gap. Or it may ask clarifying questions—sometimes repeatedly, creating an "I need X to answer this" loop.

You need explicit "incomplete context" signals. The system should tell the model: "We retrieved CRM and Identity but Billing was unavailable. Here's what we have. Do you want to proceed with partial context or wait?"

This turns a silent failure into a handled one.
