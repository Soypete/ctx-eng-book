# Hydration Coverage and Retrieval Success

## Argument
Context engineering requires a runtime metric for how much of the required context was successfully retrieved from distributed sources.

## Why it matters
A system can have all data sources available but still fail to assemble complete context. Without hydration coverage metrics, teams can't distinguish between source failures, authorization failures, and retrieval logic failures.

## Beats

1. **The context assembly problem** — evidence: ch07.01-sources-of-context
   - Context is assembled from multiple sources (DB, API, search, graph)
   - Any source failure = incomplete context
   - Silent failures are the worst kind

2. **Hydration coverage defined** — evidence: kg-quality-metrics-notes
   - Hydration Coverage = Retrieved sources / Required sources
   - Example: Customer needs CRM + Billing + Identity + Support = 4 sources
   - Retrieved: CRM + Identity = 2/4 = 50% hydration coverage
   - This is a runtime metric, not design-time

3. **Failure modes** — evidence: GAP (needs research)
   - Source unavailable (DB down, API timeout)
   - Authorization denied (scoped hydration fails)
   - Query fails (bad query, missing index)
   - Data not found (entity doesn't exist in source)
   - Stale data (cache miss, TTL expired)

4. **Measuring hydration in production** — evidence: ch16.01-tracing-context-assembly
   - Trace each context assembly request
   - Record per-source success/failure
   - Aggregate hydration coverage over time
   - Alert on coverage degradation

5. **The partial context cascade** — evidence: GAP
   - What happens when hydration < 100%?
   - Model receives incomplete context → may hallucinate or ask clarifying questions
   - Need explicit "incomplete context" signals to the model

## Conclusion to reach
Hydration coverage is a critical runtime metric for context engineering. Teams must instrument context assembly to measure retrieval success per source, aggregate coverage over time, and treat coverage degradation as a reliability incident.
