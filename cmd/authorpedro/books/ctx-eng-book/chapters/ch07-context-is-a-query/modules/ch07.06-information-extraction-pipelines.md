# Information Extraction Pipelines

## The Role of IE in Context Assembly

Information extraction (IE) transforms unstructured and semi-structured data into structured context that AI systems can use. When your system receives emails, support tickets, social media posts, or web pages, IE pipelines convert these into entities, relationships, and attributes that can be queried, filtered, and assembled into context.

IE is the bridge between raw data and queryable context. Without IE, unstructured text is just noise. With IE, it becomes structured input for the context assembly pipeline.

## Types of IE for Context Engineering

### Named Entity Recognition (NER)

NER identifies entities in text: people, organizations, locations, dates, products. For context engineering, NER answers: what entities are mentioned in this document?

A support ticket might contain:
- Person: customer name
- Organization: company name
- Date: when the issue occurred
- Product: what product is affected

The extracted entities become filterable context. The system can query "all tickets mentioning product X" or "issues from customer Y."

### Relation Extraction

Relation extraction identifies relationships between entities. Not just that entities exist, but how they relate: "customer X purchased product Y," "employee Y reports to manager Z."

This is critical for context assembly. The context pipeline doesn't just need entities—it needs the relationships that connect them. A customer entity linked to orders, orders linked to products, products linked to support tickets creates a graph traversable for context retrieval.

[Sequeda et al., 2023](https://arxiv.org/2311.07509) found that knowledge graph representations over SQL databases improved LLM QA accuracy from 16% to 54%—the structured relations enabled better context retrieval.

### Event Extraction

Event extraction identifies what happened: orders placed, tickets opened, payments processed. For temporal context, events are the primary unit.

Event extraction from informal text (social media, chat) faces challenges: informal language, abbreviation, missing punctuation. The Knowledge Graphs book Chapter 7 covers IE from informal text, noting that hashtags provide clustering mechanisms and multi-ontology approaches are needed (location, person, event ontologies simultaneously).

### Open Information Extraction (OpenIE)

OpenIE extracts relations without predefined schemas. Instead of mapping to a fixed ontology, OpenIE extracts subject-predicate-object triples from any text.

This is useful when the domain is unknown or evolving. The extracted triples can later be mapped to schemas or used directly as structured context.

## IE as Context Transformation

IE pipelines are query engines in reverse. Whereas queries retrieve data from storage, IE transforms unstructured text into structured data that can be stored and queried.

The pipeline:
1. **Input**: raw text (emails, tickets, documents, web pages)
2. **Process**: NER, relation extraction, event extraction, OpenIE
3. **Output**: structured entities and relationships
4. **Storage**: insert into database, graph, or search index
5. **Query**: retrieved as context by the assembly pipeline

This is why the chapter thesis holds: context is assembled. IE transforms raw data into queryable form. The transformation itself is a pipeline that must be engineered for reliability.

## Reliability Questions for IE Pipelines

- **Precision vs Recall**: Does the pipeline favor catching all entities (recall) or correct entities (precision)? False entities pollute context.
- **Schema Mapping**: How are extracted entities mapped to your domain schema? OpenIE without mapping produces unqueryable triples.
- **Temporal Accuracy**: When extracting events, is the timestamp correct? Extracting "order placed" without the date is low-value context.
- **Provenance**: Which document did the entity come from? Context should include source attribution.

## State of the Stack

### Libraries and Frameworks

- **spaCy**: Industrial-strength NER, dependency parsing, entity linking
- **Stanford NLP**: Academic NER and relation extraction
- **HuggingFace Transformers**: Pre-trained models for NER, relation classification
- **LLM-based extraction**: Use LLMs for zero-shot entity extraction and relation classification [LLMs can identify entities that don't match predefined categories](research/knowledge-graphs/ie-ner.md) using in-context learning

### Platforms

- **Apache Jena**: RDF extraction and processing, SPARQL queries over extracted data
- **Amazon Neptune**: Graph storage for extracted entities and relationships
- **Neo4j**: Property graph storage for extracted relations

### IE as Knowledge Distillation

With LLMs, IE becomes knowledge distillation—extracting and structuring knowledge that exists in the LLM's training data into an explicit knowledge graph. This creates new challenges: the extracted knowledge may reflect the model's training, not the current reality. IE pipelines must validate against ground truth.

[IE with LLMs as knowledge distillation](research/knowledge-graphs/ie-ner.md): extracting and structuring knowledge that exists in the LLM's training data into an explicit knowledge graph.

## Connecting to Context Assembly

IE pipelines feed the context assembly pipeline. Extracted entities are stored in databases or graphs. Relations become traversable links. Events become temporal context.

The reliability of context depends on:
1. **Extraction quality**: Are entities and relations correct?
2. **Schema alignment**: Do extracted elements map to queryable schemas?
3. **Temporal accuracy**: Are timestamps correct?
4. **Provenance tracking**: Can you trace context back to source documents?

IE is not optional—it's the mechanism that makes unstructured data available as queryable context.
