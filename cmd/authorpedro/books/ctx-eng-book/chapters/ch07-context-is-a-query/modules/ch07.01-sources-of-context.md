# Sources of Context

## The Storage Illusion

When engineers design AI systems, they often frame the problem as storage: where do we put the context? What database holds the memory? Which vector store retains the knowledge?

This framing is wrong. Context is not stored. Context is assembled.

Every piece of information a model sees arrives via a query. The "context window" is not a container filled from storage—it's a composition built from query results. Your system runs a SQL query, calls an API, searches an index, consumes an event, or queries a lakehouse. Each operation returns data. That data is concatenated, filtered, and injected into the prompt. The model never sees stored state. It sees query results.

This distinction changes everything. Instead of asking "where do we store context," you ask: which systems contribute information, what queries retrieve it, and how do we assemble the results?

The answer is the context assembly pipeline.

## Databases Are Query Engines

Relational and document databases are the most mature query systems in your architecture. When your AI system needs structured data—user profiles, transaction history, configuration—it queries a database.

The query is the boundary. A SQL query executes against a specific schema, applies filters, aggregates results, and returns a finite set of rows. What the model receives is the result of that query. Not the table. Not the database. The query result.

Consider a support agent that needs a user's recent orders. The system doesn't load the entire orders table. It executes:

```sql
SELECT id, items, total, created_at
FROM orders
WHERE user_id = $1 AND status = 'completed'
ORDER BY created_at DESC
LIMIT 5
```

The model receives five rows. That's the context. Everything else—millions of other orders, the full schema, indexes, partitions—is invisible. The model operates exclusively on query results.

This has implications. The quality of context depends on the quality of the query. A missing WHERE clause returns too much data and dilutes relevance. A missing JOIN omits critical related information. The query is a filter that shapes what the model sees.

Database queries also provide consistency guarantees. ACID transactions ensure the query sees a coherent state. This matters for AI systems that need reliable data—if the query reads inconsistent state, the model receives contradictory context.

The reliability question for database-sourced context: does the query return the right data, with the right filters, at the right granularity?

## APIs Are External Queries

REST and GraphQL APIs are query interfaces to external systems. When your AI agent needs weather data, stock prices, or product catalogs, it queries an API.

APIs differ from databases in two ways: they're network-distributed and they're externally governed. You don't control the API's uptime, rate limits, or schema evolution. Your context pipeline must handle these constraints.

A well-designed API query for context looks like any other API call:

```
GET /users/123/preferences
Accept: application/json
```

The response JSON becomes context. The model doesn't know the API exists. It doesn't know about HTTP, headers, or authentication. It sees only the JSON payload—query results in structured format.

GraphQL adds precision. A query like:

```graphql
query GetUserContext($id: ID!) {
  user(id: $id) {
    name
    subscription_tier
    recent_activity {
      action
      timestamp
    }
  }
}
```

Returns exactly the fields needed. The query defines context boundaries. This is both powerful and dangerous—the model receives whatever the query selects. Missing fields are invisible omissions.

APIs also introduce failure modes specific to distributed systems. Timeout? The query returns nothing, and context is missing. Rate limit exceeded? The system returns an error, and context is missing. Schema changed? The response format shifts, and context parsing fails.

The reliability question for API-sourced context: what happens when the API fails, returns an error, or changes its response format?

## Documents Are Full-Text Queries

Document stores—MongoDB, PostgreSQL JSONB, Elasticsearch documents—provide full-text search capabilities. When your AI system needs unstructured text—email threads, support tickets, article content—it queries a document store.

Full-text search is a different query paradigm. Instead of exact matches on structured fields, full-text search scores relevance. The query "customer complained about billing" might return documents that mention "invoice," "payment," "charged," or "account"—documents that match semantically but not lexically.

The model receives the top-k documents by relevance score. This is query results as context, but the query is probabilistic. A different search term returns different documents. The ranking algorithm determines what the model sees.

Document queries also expose context volume problems. A full document might be thousands of tokens. Injecting an entire document into context may exceed limits or dilute relevant content. Context engineering here involves not just what to query, but how much of each result to include.

The reliability question for document-sourced context: does the search query retrieve the most relevant documents, and at what truncation point?

## Search Indexes Are Inverted Queries

Search indexes—inverted indices, BM25, dense vector indexes—are specialized retrieval systems. They don't store documents; they store mappings from terms to documents. The query inverts this mapping: given search terms, find documents.

Elasticsearch, OpenSearch, Meilisearch, and vector databases like Pinecone or Weaviate all operate on this principle. The query takes a semantic or keyword representation and returns document identifiers ranked by relevance.

For AI systems, vector search has become dominant. The query embeds a natural language question:

```python
query_embedding = embedding_model.encode("What is the user's support history?")
results = vector_store.search(query_embedding, top_k=10)
```

The model receives the top-10 most semantically similar documents. This is powerful—semantic search finds relevant content without exact keyword matches. But it's also opaque. The model receives whatever the embedding space considers similar. There's no schema enforcement, no query plan to inspect, no obvious reason why one document ranked higher than another.

BM25 provides transparency. It's a probabilistic ranking algorithm with clear term frequency and inverse document frequency components. You can explain why a document scored highly. Vector search is harder to debug.

The reliability question for index-sourced context: can you explain why the retrieved documents ranked as they did, and what recall does your query achieve?

## Event Streams Are Temporal Queries

Kafka, Pulsar, and similar event streams provide temporal queries. When your AI system needs real-time data—what just happened, what's the current state, what's changed since last query—it queries an event stream.

Event stream queries are fundamentally different from database queries. A database query returns a snapshot at a point in time. An event stream query returns a sequence of changes over time.

The model might need recent user activity:

```python
consumer = KafkaConsumer('user_events', group_id='ai-context')
events = []
for message in consumer:
    if message.timestamp > last_query_time:
        events.append(json.loads(message.value))
    if len(events) >= 20:
        break
```

The context is the last 20 events. Not a table. Not a log file. A query over a streaming system that returns a bounded sequence.

Event streams introduce consistency challenges. A consumer might miss events if it crashes mid-partition. An offset reset might replay old events. The "current state" is a derived computation over the event log, not a stored value.

For AI context, this means: the model receives a temporal slice of events. Whether that slice is complete, ordered, and representative depends on stream architecture.

The reliability question for stream-sourced context: does the consumer capture a complete, ordered, and recent slice of relevant events?

## Lakehouses Are Analytical Queries

Data lakehouses—S3 with Iceberg or Delta, Snowflake, BigQuery—provide analytical query capabilities. When your AI system needs aggregated data, historical trends, or large-scale statistical context, it queries a lakehouse.

Lakehouse queries operate at scale. A query might scan billions of rows:

```sql
SELECT
  user_segment,
  AVG(engagement_score) as avg_engagement,
  COUNT(*) as user_count
FROM fact_user_engagement
WHERE date >= DATE_SUB(CURRENT_DATE, INTERVAL 30 DAY)
GROUP BY user_segment
```

The model receives aggregated statistics, not individual records. This is query results as context—but the result is a summary, not raw data.

Lakehouse context has different reliability characteristics. Query latency might be seconds to minutes for large scans. The data might be stale—lakehouse tables often update hourly or daily. The query might fail due to compute capacity or concurrency limits.

The model receives whatever the analytical query computes. If the aggregation is wrong, the context is wrong. If the time window is misconfigured, the context is stale.

The reliability question for lakehouse-sourced context: is the query performant, is the data fresh, and does the aggregation accurately represent what the model needs?

## State of the Stack

This section surveys current tools that implement the patterns discussed in this chapter. They are examples of current engineering approaches, not endorsements or architectural requirements.

### Standards and Formats

- **SQL**: Standard for relational database queries. Most AI context pipelines query SQL databases.
- **GraphQL**: Query language for APIs providing precise field selection. Useful for fetching exactly needed context.
- **SPARQL**: Query language for RDF knowledge graphs. W3C standard since 2013, used when context comes from semantic web sources. [W3C SPARQL 1.1](https://www.w3.org/TR/2013/REC-sparql11-query-20130321)
- **Full-text Search Query DSLs**: Elasticsearch Query DSL, Meilisearch filters, BM25 scoring configurations.

### Infrastructure

- **PostgreSQL**: Primary choice for structured data context retrieval. Supports full-text search via tsvector, JSONB for flexible schemas.
- **MySQL**: Alternative relational store for simpler context retrieval needs.
- **Apache Jena**: Open-source Java framework for RDF/SPARQL queries, includes ARQ SPARQL engine, TDB triple store, and Fuseki SPARQL endpoint [Apache Jena Project](https://jena.apache.org)
- **MongoDB**: Document store for unstructured context, full-text search, and flexible schemas.
- **Elasticsearch / OpenSearch**: Full-text and semantic search over large document corpora.
- **Redis**: Fast key-value and structured data retrieval for real-time context.
- **Kafka / Pulsar**: Event streams for temporal context—what just happened, state changes.

### AI-Specific Implementations

- **Pinecone**: Managed vector database for semantic similarity search.
- **Weaviate**: Vector database with hybrid search (BM25 + vector), graph traversal, and filters.
- **Milvus**: Open-source vector database with advanced indexing and filtering.
- **Chroma**: Lightweight embedding vector store, popular for prototyping.
- **pgvector**: Vector similarity search inside PostgreSQL—simpler than separate vector DB.
- **Supabase**: PostgreSQL with built-in vector support, authentication, and edge functions.

### Questions to Ask Before Adoption

1. Which query type dominates your context retrieval—structured lookups, full-text search, or semantic similarity?
2. How do you handle query failures—does the system fail gracefully or return partial context?
3. What's the latency SLA for each query type—how does it affect overall inference time?
4. How do you handle consistency—can queries see uncommitted state?
5. What's the truncation strategy when query results exceed context window budget?
6. Do you need real-time context (event streams) or historical context (databases)?
