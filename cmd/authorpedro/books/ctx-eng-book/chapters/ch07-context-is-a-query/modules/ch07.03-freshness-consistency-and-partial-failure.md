# Freshness, Consistency, and Partial Failure

## Temporal Consistency in Context Pipelines

Context assembled from queries has a temporal dimension. Every query result is a snapshot taken at a specific time. The vector store was indexed at t₁. The database query ran at t₂. The API call completed at t₃. The model receives context from different times, potentially conflicting.

This is the freshness problem: how recent must context be to be useful?

The answer depends on the query type. User profile data can be hours old. Order status should be minutes old. Real-time pricing needs seconds old. Stock levels might be acceptable at daily freshness. The context assembly pipeline must track the timestamp of each query result and enforce freshness requirements.

Implement freshness metadata: every query result includes a timestamp and a freshness threshold. Before returning results to the model, check: is this recent enough? If not, either refetch or flag the staleness. The model can then decide how to handle stale context—perhaps using it for background context but not for real-time decisions.

## Eventual vs Strong Consistency

Distributed systems choose between eventual consistency (reads might see stale data, but writes propagate eventually) and strong consistency (reads always see the latest write). Context pipelines face the same trade-off.

Strong consistency means every query waits for all data sources to synchronize. This is slow. A user profile query might need to wait for the billing system to confirm payment status, the support system to sync ticket history, and the preferences service to load settings. Every synchronization point adds latency.

Eventual consistency means queries return immediately with whatever data is available, accepting that some sources might be slightly stale. This is fast. But it introduces the risk of contradictions: the model sees a "closed" ticket in one source and an "open" ticket in another.

For context engineering, eventual consistency is usually the right choice—with explicit staleness handling. The pipeline returns available context and marks each source's freshness. The model (or a higher-level handler) decides whether the staleness matters.

The implementation pattern: query all sources in parallel, return what arrives within a timeout, and tag each result with its source timestamp. If a critical source times out, either fail the request or escalate to the user.

## Partial Failure Modes

A context assembly pipeline with five queries might have two succeed, two time out, and one return an error. That's partial failure. The pipeline must decide: what to return when some queries fail?

The naive approach: fail the whole request if any query fails. This is safe but fragile. One slow database brings down the entire AI response.

The robust approach: partial context is acceptable, with clear failure signaling. Return the successful query results, mark the failed queries explicitly, and let the model handle degraded context.

The implementation:

1. **Timeout with fallback**: Each query has a timeout. If it exceeds, return a "query timed out" placeholder with the source identified. The model can note "timed out" and work around it.

2. **Error propagation**: Distinguish between "no data found" (valid empty result) and "query error" (failure). Errors get logged and flagged. Empty results are just empty context.

3. **Circuit breakers**: If a source fails repeatedly, stop querying it for a cooldown period. Return a "source unavailable" message instead of timing out repeatedly.

4. **Graceful degradation**: The system should produce acceptable output even with partial context. If three of five queries succeed, can the model answer the user's question? Often yes—if the failed queries weren't critical.

## Retry Strategies for Context Queries

Failed queries should retry, but with limits. Exponential backoff with jitter prevents thundering herd problems. Max retries with clear failure signaling ensures the pipeline doesn't hang.

The retry logic for context queries differs from standard API retries because context queries are often idempotent—fetching user profile twice is fine. But the pipeline must avoid excessive latency. A good pattern:

- First attempt: all queries in parallel
- On timeout: mark as "pending" and allow async refetch
- On error: retry once, then mark as "failed"
- Never block the pipeline waiting for a slow source

The pipeline returns what's available. A later request can refetch failed sources.

## Handling Inconsistent State

The final challenge: what does the model do when context is inconsistent?

The profile says the user is on plan "Basic" but the billing system shows "Premium." The order status shows "delivered" but the tracking system shows "in transit."

These contradictions happen. The context pipeline shouldn't hide them—better to present contradictory facts than to guess which is correct. The model can reason about the contradiction: "There may be a delay between billing and tracking systems."

The implementation: include source attribution for each context item. Not just "order status: delivered" but "order status from tracking API: delivered." The model can weight sources, note conflicts, and handle appropriately.

## Summary

Context from queries is temporal, potentially inconsistent, and subject to partial failure. Handle this through:

- **Freshness metadata**: timestamp every query result, enforce freshness thresholds
- **Eventual consistency**: return available data quickly, flag staleness
- **Partial failure handling**: succeed with degraded context, not fail entirely
- **Retry with limits**: exponential backoff, max retries, circuit breakers
- **Source attribution**: let the model know where each fact came from

The pipeline assembles context from unreliable sources. It must be resilient to that unreliability.
