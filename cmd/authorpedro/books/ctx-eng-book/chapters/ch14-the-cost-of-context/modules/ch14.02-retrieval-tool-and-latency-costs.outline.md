# Retrieval, Tool, and Latency Costs

## Argument
Latency is the hidden cost of context. Every retrieval call, tool invocation, and additional model call adds latency. Context engineering decisions directly affect response time—and the reliability question isn't just "does it work?" but "does it work fast enough?"

## Why it matters (reliability goal)
Tie to Pragmatics pillar: a correct answer that arrives too slowly is a failure. Understanding latency costs enables tradeoffs between thoroughness and responsiveness.

## Beats

1. **Latency as Hidden Cost** — evidence: existing prose
   - Retrieval latency: vector store, query complexity, network topology
   - Inference latency: scales with token count
   - Tool calls compound: decide → execute → process = three round-trips
   - Case study: latency budget blowout (8s → 1.2s via batching/caching)

2. **Retrieval Cost** — evidence: existing prose
   - Vector databases charge for storage and compute
   - Embedding generation costs per document
   - Over-retrieval: fetching too many, truncating half anyway
   - Fix: retrieve only what's needed, size to consumption not maximums

3. **Tool Cost** — evidence: existing prose
   - Database queries, API calls, file reads all have costs
   - Tool-happy agents: making 15-20 calls when 3-4 suffice
   - Case study: tool budget reduced costs by 70%
   - Design tool schemas for minimal output

## Conclusion to reach
The reader should believe that latency matters as much as correctness. A system that's technically correct but too slow fails the reliability test.
