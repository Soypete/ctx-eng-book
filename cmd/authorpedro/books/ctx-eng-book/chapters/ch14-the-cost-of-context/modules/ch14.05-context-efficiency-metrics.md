# Context Efficiency Beyond Token Cost

## Token Economics Is Not Enough

Token cost is important but incomplete.

System A: 1000 tokens, 10 API calls, 500ms latency
System B: 1500 tokens, 2 API calls, 100ms latency

In user experience, it's System B—in tokens per call, it's System A. In time, it's also System B. The answer depends on what you're optimizing for.

The lesson: optimizing for one dimension often makes another worse. More context tokens might mean fewer API calls, but longer inference time. Caching might reduce API calls but increase memory usage.

## Context Efficiency Defined

**Context Efficiency = Reliable output / Total resource consumption**

Resources include: tokens, retrieval latency, retrieval cost, hydration time, API calls, storage lookups. This is a multi-dimensional metric, not a single number.

A system that uses more tokens but fewer API calls may be more efficient than one that uses fewer tokens with many calls.

## Measuring Retrieval Latency

Track:
- Time to first context token
- Time to full context assembly
- Per-source latency breakdown
- Degradation alerting

### Two Latency Worlds

LLM-side latency and context-side latency are different problems:

**LLM-side metrics:**
- TTFT (Time to First Token) — how fast the model starts responding
- Tokens per second — generation speed
- Processing vs compilation vs transcription time

**Context-side metrics:**
- Tool call latency
- API latency
- Database query latency

These compound. You can have fast token generation but slow context retrieval, and the user experience still feels broken.

### Why Lazy Loading Often Fails

Lazy loading works when the data is rarely needed or when fetching is fast. Pre-compilation works when fetching is slow or data is frequently used.

Web scraping ahead of time is a waste of compute—you're doing work on data that may never be used. But a quick API like web search or Wikipedia is different. Those are fast. That's lazy loading done right.

The pattern: if the API is quick (web search, Wikipedia lookup), lazy load on demand. If the operation is slow (scraping a page, querying a database, building a graph), pre-hydrate.

Context is usually somewhere in between. The user experience of waiting for context to hydrate on every turn is worse than the cost of pre-hydrating—for slow operations. For fast ones, lazy loading is fine.

## Measuring API and Storage Costs

Track:
- API calls per context assembly
- Storage lookups per request
- Cache hit/miss ratios
- Network hops between services

## The Efficiency Trade-off Frontier

More cache = higher memory, faster retrieval. More preprocessing = higher compute, faster runtime. Two systems answering equally well—the cheaper one is objectively better. Need to track the Pareto frontier: what's the best efficiency at each resource level?

## Prompt Optimization as a Minimization Function

The DSPy compiler from Stanford NLP frames prompt optimization as a minimization problem. The compiler tries different prompt configurations, measures the output quality (via a metric you provide), and converges toward better prompts. This is gradient-like optimization—it's searching the space of possible prompts to minimize error or maximize a score.

The jacobian here isn't a matrix of derivatives—it's the relationship between prompt changes and output changes. Every prompt tweak produces a different output. The compiler samples, measures, and steers toward better configurations.

This matters for cost because:
- Better prompts = fewer tokens needed to get the same result
- Optimized prompts = fewer API calls (less retry, less clarification)
- Automated optimization = less human time spent tuning

DSPy predates native tool calling but its modules now support tools. The compiler optimizes both in-context demonstrations and tool use together. This is the cost-aware version of prompt engineering: let the system find the minimal effective prompt rather than guessing.

### The J-Space: Anthropic's Workspace Discovery

Anthropic's July 2026 paper "Verbalizable Representations Form a Global Workspace in Language Models" (J-space paper) provides the mechanistic foundation for why prompt optimization works.

The paper introduces the **Jacobian lens** - a technique that identifies internal representations in LLMs that are "verbalizable" - things the model can report, manipulate, and reason with. These form the **J-space**, a privileged subset of the model's activations that functions like a global workspace:

- The model can deliberately hold concepts in mind
- These representations are reportable (the model can "say" what it's thinking)
- Interventions on J-space vectors directly change model behavior

The insight for context engineering: prompts work by steering the model's J-space. A good prompt is one that puts the right concepts in the workspace. Prompt optimization (DSPy, evolutionary methods) is searching for the minimal prompt configuration that achieves the desired J-space state.

This connects the jacobian minimization directly to the model's internal mechanics. The jacobian in "jacobian minimization" isn't abstract - it's the actual causal map from activations to outputs that the J-lens exploits.
