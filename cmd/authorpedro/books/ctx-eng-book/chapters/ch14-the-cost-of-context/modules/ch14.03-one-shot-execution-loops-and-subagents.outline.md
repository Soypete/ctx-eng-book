# One-Shot Execution, Loops, and Subagents

## Argument
Loops multiply cost and erode reliability. The cheapest reliable solution is almost always a one-shot solution. Loops should be reserved for cases where iteration is genuinely necessary—where the problem structure requires it, not where the system design forces it.

## Why it matters (reliability goal)
Tie to Pragmatics pillar: every loop iteration is an opportunity for the model to drift, misinterpret, or compound an error. Cost and reliability align here—fewer iterations mean both cheaper and more reliable.

## Beats

1. **One-Shot vs Loops: The Reliability-Cost Tradeoff** — evidence: existing prose
   - One-shot: simplest, cheapest, most predictable
   - Loops multiply cost (3x = 3x, 30x = 30x)
   - Each iteration = opportunity for error drift
   - Case study: $100 loop → $1 batched (10x savings)

2. **Subagent Costs** — evidence: existing prose
   - Each subagent has its own context setup, prompt injection, tool access
   - Main agent spawns 5 subagents = 5x baseline cost
   - Make sense when reliability gain outweighs cost increase
   - Need explicit budgeting: max subagents, max tokens per subagent

3. **Memory Consumption** — evidence: existing prose
   - Context memory = token budget (discussed in ch14.01)
   - System RAM: model loading, vector store, session state, tool layer
   - Local models: 70B = 140GB RAM just to load
   - Vector store exceeding RAM = query latency spikes

## Conclusion to reach
The reader should believe that loops are expensive and dangerous. Reserve them for structurally necessary iteration, not design-driven complexity.
