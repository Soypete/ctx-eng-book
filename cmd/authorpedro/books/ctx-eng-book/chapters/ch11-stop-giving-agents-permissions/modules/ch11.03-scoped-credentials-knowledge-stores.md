# Scoped Credentials and Knowledge Stores

## The Credential Problem

OAuth tokens and capabilities need somewhere to live. The agent must retrieve, present, and manage credentials throughout its operation. This is the scoped credentials problem: how do you store, retrieve, and revoke credentials that are specific to a task?

The naive approach: embed credentials in the system prompt. Don't do this. Credentials in prompts are visible to the model, persisted in logs, and impossible to revoke without regenerating the prompt.

The better approach: separate credential storage from context assembly. Credentials live in a knowledge store, retrieved at runtime, and injected into the retrieval request—not the prompt.

## Knowledge Stores for Credentials

A knowledge store is a specialized backing service for credential management. It provides:

- **Issuance**: Generate scoped credentials based on authorization policy
- **Storage**: Persist credentials with metadata (grantor, scope, expiration)
- **Retrieval**: Fetch credentials for a given task and actor
- **Validation**: Verify credential validity without external calls
- **Revocation**: Invalidate credentials before expiration

The knowledge store is not the same as the context store. The context store holds user data, conversation history, and retrieved information. The knowledge store holds authorization artifacts—tokens, capabilities, and their metadata.

This separation matters for security. Credentials should never flow through the context assembly pipeline where they could be logged or leaked. They flow directly from the knowledge store to the data store.

## Capability Tokens

A capability token is a structured credential that encodes permission details. It's not just a bearer token—it's a machine-readable authorization.

Here's the structure:

```
capability {
  id: uuid
  granter: user_id or service_id
  actor: agent_id
  resources: [
    { type: "table", name: "orders", conditions: "user_id = 123" }
  ]
  actions: ["read"]
  constraints: {
    expires_at: timestamp,
    max_calls: 100,
    ip_whitelist: ["10.0.0.0/8"]
  }
  signature: cryptographic proof from granter
}
```

The data store validates the signature, checks constraints, and enforces the resources and actions. No external authorization call needed. The capability is self-enforcing.

For context engineering, capabilities are generated per retrieval operation. The knowledge store creates a capability based on the user's authorization for that specific task. The agent includes the capability in the retrieval request. The data store enforces it.

## Scoped Credential Patterns

The practical patterns for scoped credentials:

**Per-Operation Capabilities**: Generate a new capability for each retrieval operation. The capability is scoped to exactly what's needed for that operation—specific tables, specific rows, specific time windows. Capabilities expire quickly (minutes to hours).

**Credential Chaining**: A capability can grant the ability to obtain other capabilities. This creates a chain: the initial capability grants access to the knowledge store, which issues operation-specific capabilities. Limits the blast radius—compromised capability only grants access to the knowledge store, not directly to data.

**Attestation-Based Access**: The agent proves its identity to the knowledge store through remote attestation ( TPM, secure enclave). The knowledge store issues credentials based on the agent's attested identity and configuration. This prevents stolen credentials from being used on unauthorized agents.

## Implementing the Knowledge Store

The knowledge store integrates with the context engineering system at the retrieval layer:

1. **Task Request**: Agent requests to perform operation X on resource Y
2. **Credential Lookup**: System queries knowledge store for applicable capabilities
3. **Capability Generation**: If no existing capability applies, knowledge store generates one based on authorization policy
4. **Credential Injection**: Capability is added to the retrieval request (not the prompt)
5. **Enforcement**: Data store validates capability and returns only permitted data
6. **Provenance**: Metadata records which capability authorized which retrieval

The knowledge store should be a separate service with its own access controls. It should be instrumented for auditing—who requested what capability, when, and for what purpose. It's a critical security component.

## Revocation and Expiration

Capabilities must be revocable. The knowledge store maintains a revocation list and checks it during validation. If a capability is revoked, the data store rejects the retrieval.

Expiration is the first line of defense. Capabilities should have short lifetimes—minutes to hours, depending on the operation. Long-running tasks request fresh capabilities periodically.

For high-security contexts, implement capability rotation. The knowledge store issues multiple capabilities for the same operation, valid at different times. The agent uses each capability once. Compromised capability exposes only a small time window.

## Related Research

- [Brandstetter et al., 2024](https://arxiv.org/abs/2412.10891): "Traditional RBAC models fail to capture the dynamic, multi-step nature of agent actions. Capability-based access provides fine-grained, revocable permissions tied to specific actions rather than static roles."

## Summary

Scoped credentials bridge authorization policy and retrieval execution. They live in a knowledge store, separate from the context store. Capabilities are generated per-operation, scoped to specific resources and actions, and enforced at the data store.

This pattern ensures that even if an agent is compromised or misbehaves, it cannot access data outside its capabilities. The permission is structural, not advisory. It's enforced by the data store, not the model.
