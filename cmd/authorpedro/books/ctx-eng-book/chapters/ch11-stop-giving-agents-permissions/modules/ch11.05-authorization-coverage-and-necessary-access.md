# Authorization Coverage and Necessary Access

## The Real Problem: Not Authorization, Tool Design

This isn't really an access model issue. Access is user-scoped. The real problems are:

1. **Knowledge graphs narrow relationships ahead of time.** This is a domain detection exercise. The graph knows which entities relate to which. Don't query everything—just traverse the relevant paths.

2. **Pragmatics control retrieval behavior.** We have to tell the tool to behave and retrieve a certain way. `SELECT *` is expensive—for both the database and the context. We would never want our agent to do that.

The solution is providing a correct system around it via good tool calls and pragmatics: "We are doing analysis for X customers. Here are the tools to accomplish that."

## Least Privilege is User-Scoped

Scoping of access is least privilege of the user. The agent system handles the rest: the context, the tool, and the pragmatics of the task.

## The Over-Retrieval Problem

Agents often retrieve more than needed "just in case." This increases:
- Token cost
- Latency
- Hallucination risk
- Data exposure

SELECT * is the canonical example. The fix isn't authorization—it's tool design.

## Techniques for Necessary Access

- **Query-level authorization**: What did you actually ask for?
- **Result bounding**: Limit returned records
- **On-demand vs preemptive retrieval**: Don't fetch until needed
- **Competency-based context**: Only retrieve what this task type needs

## Task-Scoped Agents Are More Efficient

This is the other reason we have task-scoped agents. Within a domain, they'll be more efficient in accomplishing the task. A general-purpose agent doesn't know the domain's relationships. A domain-specific agent knows exactly which data matters.

The graph helps the reasoner. The tool design controls the query. The pragmatics explain the task. Together, they achieve necessary access without over-retrieval.

## ReAct Prompting as a Pragmatic Control

ReAct prompting can help here too. When a request is vague or has symptoms of pulling too much context, the agent can ask the user to narrow down the request.

This is a type of pragmatics: the model recognizes ambiguity, estimates the retrieval scope would be too large, and asks for clarification before doing expensive over-retrieval.

The pattern: build the pragmatics to detect "this request would pull too much" signals, then use ReAct-style reasoning to pause and ask: "Did you mean X or Y? I want to make sure I retrieve only what you need."

This is cheaper than retrieving everything and filtering—it costs a clarification question instead of a large context window.
